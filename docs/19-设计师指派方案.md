## 0. 一句话

未指定设计师的工单不再"安静地躺着"：软件**主动提示**「有 N 张待指派」，并在工单详情里**直接指派**，写回企微智能表格的「设计师（成员）」列，指派成功后机器人通知设计师——表格始终是权威，软件只是让"派活"这个动作不用切出去。

## 1. 现状与问题（一期行为回顾）

- 一期建任务条件链 = `设计师 = 本机身份` 且 状态 ∈ {审批中, 已通过} 且 非历史单 且 非待确认（docs/15 §2.2②）  
  → **未指定设计师的单永远不建任务**，只躺在「未指派」筛选里（一期已做了这个筛选和行内标记，但没有人会被提醒去看它）
- 实际后果：派单的人（管理员）只有在企微表格里翻表才能发现新单没派出去，容易积压、容易漏派
- 一期 `tickets` 表已存 `designer_userid / designer_name`（读侧字段齐全，本批写侧直接复用这两列）

## 2. 核心决策：在软件里指派，还是引导去表格改（你没考虑好的那个问题）

|              | **方案 A：软件内指派 + 写回表格**（默认推荐）                               | 方案 B：只提示 + 引导去表格改                  |
| ------------ | --------------------------------------------------------- | ---------------------------------- |
| 操作路径         | 详情弹窗选人 → 即时生效 → 后台写回                                      | 软件提示 → 点按钮打开企微表格 → 在表格里改 → 回软件手动同步 |
| 表格权威性        | 不变（写回 = 往表里写，表仍是唯一权威）                                     | 不变                                 |
| 辅助信息         | 下拉里带「在办 N 单」（表格里没有这个信息）                                   | 无                                  |
| 指派后通知设计师     | 能做（写回成功即触发）                                               | 做不了（软件不知道你在表格里改了什么，要等下轮同步）         |
| 留痕（谁派的 / 何时） | 能做（本地 `assigned_by / assigned_at`）                        | 无                                  |
| 前置条件         | ① 表格成员权限升「可编辑」② **成员列写回格式必须真表实测**（§11 第 0 步）③ 本机 CLI 授权有效 | 零前置，开发量约为 A 的三分之一                  |
| 风险           | 写回失败 / 权限不足（有 pending 补写与明确报因兜底，数据不丢）                     | 无写回风险                              |

**默认推荐 A**，三个理由：

1. `docs/16` §5 的三项拍板（2026-10-02：只有本机身份能派 / 并进本批做 / 指派后机器人通知）**本质上已经选了 A**——B 兑现不了"通知设计师"这条已拍板决策；
2. 你提的痛点是"容易漏派"，B 只解决"发现"，不解决"处理还得切出去"；
3. 写回管路（本地即时 → pending → 异步写回 → 失败补写 + 冲突三态）`docs/16` 已设计好，本批造一次，二期印刷状态写回直接复用，不白干。

**A 同时带上 B 的逃生口**：详情弹窗保留「在表格中打开」按钮（一期已有"打开审批"，同款交互）——写回失败 / 权限不足 / CLI 不在时，用户随时可以退回手工改表，软件下次同步自动对齐。

**关于你提到的 webhook**：写回**不走 webhook**，走本机 wecom-cli 直连智能表格（命令入参、权限模型、2000 行上限已在 docs/16 §1.2 实探钉死，机器人身份可代授权真人写）。webhook 路线在 docs/16 §2.4 已明确不做（CLI 直连已验证可用，先简单）。

## 3. 提示机制（"看到新增的未指派工单就提示"）

默认形态（三层，全部软件内，不弹窗骚扰）：

| 层            | 内容                                        | 触发                                   |
| ------------ | ----------------------------------------- | ------------------------------------ |
| ① 顶栏「工单」格徽标  | 「待指派 N」角标（N = 当前未指派且非历史的单数，常显存量）          | 每次同步后刷新                              |
| ② 工单视图头部提示条  | 「本轮同步新增 N 张未指派工单」+「去指派」按钮（点击 = 切到「未指派」筛选） | 仅当**本轮同步**确实新增了未指派单时出现；点掉或下次同步无新增即消失 |
| ③ 同步结果 toast | 手动同步的 toast 里补一句「其中 N 张待指派」               | 手动同步时                                |

判定口径：**"新增"= 本轮同步新入库（ticket_no 首次出现）且 designer 为空**；已存在但一直没派的算存量，只进徽标数字，不反复轰炸。

**企微机器人推送本批不做**（决策点 #2 可改）：机器人给授权人本人发"有 N 张待指派"技术上可行，但**同步只发生在软件开着的时候**（定时同步还在二期押后清单里）——软件没开就没有同步、就没有推送，价值受限。等定时同步立项时一并做。

## 4. 指派交互

```
工单详情弹窗（未指派单）
  └─ 顶部「指派设计师」区（仅「本机开关」开启的机器可见操作态，见 §10 #3）
       └─ 下拉选择（候选 = 历史设计师去重，名字后标「在办 N 单」）
            │ 选定即存（无确认弹窗——下拉本身就是明确选择；铁律③：只提示在办数，不替人选）
            ▼
本地 tickets.designer_userid / designer_name 立即更新（界面即时反馈，不等写回）
  + 标 designer_write_pending = 1 + 记 assigned_by / assigned_at
            │ 异步写回（§5 管路）
            ▼
CLI records update（record_id + 设计师列 + 成员值）
  ├─ 成功 → 清 pending → 触发通知（§6）
  └─ 失败 → 保 pending + toast 明确报因；下次同步自动补写；「在表格中打开」逃生口常在
```

- **指派给本机身份**：下一轮同步自然满足建任务条件链 → **自动建出任务包**（一期链路零改动，不额外写代码）
- **指派给别人**：只更新设计师字段，不建任务（他的机器同步到后自动建，各拉各的本地库）
- **改派已有设计师的单**：同一个下拉也能改（走同一管路）；已有任务的单改派 = 一期"改派检测"语义（标 `reassigned_to`，不删任务），两套规则天然衔接

## 5. 写回管路（沿用 docs/16 §2.2 / §2.3，第一次落地）

- 本地即时改 → 标 `designer_write_pending` → 异步写回 → 失败保持 pending，下次同步（手动）自动补写
- **冲突三态（表为准）**：
  - 表值 ≠ 本地值，本地无 pending → **采纳表值**（别人在表格里改的）
  - 表值 ≠ 本地值，本地有 pending → **本地守住不被覆盖**，本轮同步后自动补写
  - 写回成功 → 下轮同步自然收敛
- 权限不足（写回报权限错）→ toast 给明确指引「需要在企微表格里给你开可编辑权限」；**不做 webhook 兜底**（docs/16 §2.4 已拍板）
- 写回命令、入参、权限模型已实探钉死（docs/16 §1.2）；**成员列值的序列化格式（userid 怎么传）是唯一未实测的点**，施工第 0 步在真表测试行上验一次，钉死才写代码（你的要求，也是 docs/16 §11 的既有风险项）

## 6. 指派后通知设计师（已拍板：要发）

- 触发：写回**成功**后（通知失败不影响指派本身）
- 内容模板（文案走 `copy.ts`，可在线表格改）：「新工单：{标题}（{项目}），期望 {交期}，请查收」
- 已知约束：机器人**只能向「最近有消息往来的会话」或授权人本人发消息**——设计师若从未跟机器人聊过，发不出去
- 降级路径（按优先级）：① 发到工单群并 @ 他　② 退化为软件内提示（toast「已指派，通知未送达」）
- 施工第 0 步实测一次可达性（找一位没跟机器人聊过的同事）；**通知状态记 `notify_state`（null / sent / failed）防重复推送**

## 7. 冲突与边界

| 情况                      | 处理                                                            |
| ----------------------- | ------------------------------------------------------------- |
| 表格侧把设计师改成别人             | 无 pending → 采纳表值；已有任务的单按一期「改派检测」走（标 `reassigned_to`，**不删任务**） |
| 本机指派完，别人又在表格改回          | 正常冲突，后写覆盖（表为准，三态收敛）                                           |
| 待确认单 / 表里已删行（row_gone）  | **不能指派**（record_id 可能已失效，写也是白写），入口置灰 + 提示原因                   |
| 历史单                     | **不提供指派入口**（默认，决策点 #7）——对齐已拍板的「旧物料不做对应」；界面提示「历史单请在表格中处理」      |
| 电子单                     | **同样可指派**（设计师字段与印刷环节无关）                                       |
| 「设计师」列缺失 / 被改名 / 不是成员类型 | 指派入口置灰 + 提示「表格里的设计师列不可用」（列名走 meta 配置键，改名只改配置，与一期读侧同规矩）        |
| 候选池为空（从没有人被派过）          | 下拉空态提示「请先在表格里填一次设计师，软件会记住」；入口不禁用                              |
| 本机开关未开启（默认）          | 提示区降级为只读提示「等待指派」（默认只读；要派单的机器在工单设置里开开关，见 §10 #3）              |
| 本机未授权 / 授权过期            | 提示区降级为只读提示 + 去设置的入口（一期已有授权提示态，复用；开关开了但 CLI 不可用时写回走 pending 补写兜底）  |

### 第 0 步 · 真表实探（2026-10-02，证据 `_junk/wecom_probe2/`，不入库）

全部结论来自真表实测，可作施工依据：

1. **写回格式钉死**：`smartsheet records update --json`，`type: "update"`、`key_type: "field_title"`，成员列的值传**嵌套数组对象**：`"values": { "设计师": [{ "userId": "<userid>" }] }`。
   - ⚠️ CLI 的 schema 声明 `values` 是 `Record<string, string>`（值=JSON 字符串），但**按 JSON 字符串传会被拒**："值类型与列类型不符……人员列需传 `[{"userId":"..."}]` 形态"——按嵌套对象传才成功（实测两种各跑一遍对比钉死）；
   - `userName` 可不传（读回时企微自动补全），实现只传 `userId`。
2. **errcode=0 ≠ 写成功**：写失败时 errcode 也是 0，拒绝原因藏在 `helper_msg` 里（"全部 N 条 record 的单元格都不可写入/已跳过"）。**实现必须把 helper_msg 非空（或含"跳过/不可写入"字样）判为失败**，不能只看 errcode。成功时 helper_msg 为空。
3. **空数组清不掉人员列**：`[]` 会被拒（"人员字段全部被剔除、无有效内容"）。本方案只指派不清空，无影响；也意味着"改派"永远是写新值覆盖。
4. **机器人通知链路实测可用**：`message aibot send --json`，`msg_type: "markdown"`，**单聊的 chat_id = 接收成员 userid**（不用先查会话列表）。实测发给授权真人本人 `success: true`。发给"从未与机器人对话过的成员"是否可达未测（需真人配合）——实现按「发送失败 → notify_state=failed → toast 降级提示」兜底，不赌可达。
5. **真表现状**：印刷子表 252 条 + 电子子表 5 条，**设计师列全部为空**（2.0 表重做后还没人派过）→ 候选池初始为空态，首次使用会看到「请先在表格里填一次设计师」提示。实探在一条**已驳回死单**（2025 年的历史单）上写了授权真人作为设计师做探针且无法清空——零业务影响，恰好给候选池垫了一个种子（也可在表里手动删掉该格）。
6. 读侧格式复核：人员列读出 = `[{userId, userName}]`，空单元格直接缺键——与一期 `takeUser` 实现一致，零改动。
