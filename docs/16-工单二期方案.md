## 0. 一句话

工单模块从「只读」升级为「双向」：软件里能标**印刷状态**并写回企微表、**定时自动同步**不用手点、wecom-cli **打进安装包**让同事装完软件就能用（只差扫码授权一次）。

## 1. 实探结论（2026-10-01 下午，全部实测验证）

开工前把三块能力的实底都探了一遍，结论比预想好：

### 1.1 CLI 本体：单文件 exe，打包条件极好

| 项 | 实测结果 |
|---|---|
| 形态 | `@wecom/cli` 的 `bin/wecom.js` 只是启动器，**真正的 CLI 是 `wecom-cli.exe`（10 MB 单文件，零依赖）** |
| 体积 | 连 LICENSE 一起 **9.6 MB**（对比 FFmpeg 的 267 MB，可忽略） |
| 许可 | **MIT**（LICENSE 文件在包里，随安装包分发无障碍，附上即可） |
| 凭据 | 存在**用户主目录**（`%USERPROFILE%\.workbuddy\connectors\…\.credentials.v3.json`），**与 exe 安装位置无关** —— 把 exe 复制到 `D:\` 任何位置运行，授权照样有效 |
| 版本 | 1.3.2（一期用的就是它，兼容性已验证） |

### 1.2 写回：命令、入参、权限全部确认

写回命令（CLI 自带方法文档，入参已钉死）：

```
wecom-cli smartsheet records update --json '{
  "docid": "s3_xxx",
  "sheet_id": "tlD2Vr",          // 或 sheet_title
  "type": "update",
  "key_type": "field_title",      // 按列名定位（列改名即失配，与一期读侧同一规矩）
  "records": [
    { "record_id": "xxx", "values": { "印刷状态": "印刷中" } }
  ]
}'
```

- 单次上限 2000 行（我们一次只写几张单，远用不到）
- **权限确认**：CLI 身份说明原文——写入或修改「仅在在线文档、在线表格、**智能表格**、智能文档四类文档上允许跨身份操作」。智能表格写回**在授权范围内**，机器人身份可代授权真人写
- 需要的前置：表格成员权限给到「可编辑」（现在只读用的「可阅读」不够）——**管理员把要标状态的人升成可编辑**即可
- 值格式细节（values 里 select 列的值怎么序列化）留到施工第 1 步在**真表测试行**上验一次，不猜

### 1.3 授权：有独立命令，能出扫码二维码

- `auth show` → 显示当前授权状态（authorized / Bot ID）
- `auth init --noninteractive --output-qrcode <png路径>` → 跳过交互、把授权二维码输出成 PNG 图片
- 意味着**同事授权可以做成软件内点按钮**：软件调起 auth init → 弹出二维码 → 同事拿企业微信扫一下 → 软件检测到 authorized 自动刷新身份。不用开命令行
- ⚠️ 两个实探验证点（施工第 1 步做，不猜）：
  1. 扫码接入是否需要企微管理员预先配置/审批机器人
  2. 干净机器（没装过 WorkBuddy）上 auth init 把凭据落在哪、能不能自建目录

## 2. 功能设计之一：印刷状态写回

### 2.1 前置条件（需要你在表里做的）

1. **在「印刷」子表加一列「印刷状态」**，类型单选，选项建议（待拍板，§7 #1）：
   `待印刷 / 印刷中 / 已到货 / 已完结`
2. **表格权限**：要标状态的同事升成「可编辑」（只看单的保持「可阅读」）
3. 电子子表**不加**这列（电子物料没有印刷环节）

### 2.2 交互与流向

```
工单详情弹窗（印刷单）
  └─「印刷状态」下拉（选项 = 表里那组单选值）
       │ 选定即存
       ▼
本地 tickets.print_status 立即更新（不等写回，界面即时反馈）
  + 标 print_write_pending = 1（待写回）
       │ 异步写回企微表
       ▼
wecom-cli records update（record_id + 列名「印刷状态」）
  ├─ 成功 → 清 pending，完成
  └─ 失败（授权过期 / 权限不足 / 网络）→ 保持 pending + toast 明确报因
       下次同步（手动或定时）自动补写；设置里也有「重试写回」按钮
```

### 2.3 冲突规则（多机都写同一列，谁说了算）

**表是权威，最后写入者胜，软件本地永远向表看齐**：

| 场景 | 处理 |
|---|---|
| 同步拉到表值 ≠ 本地值，且本地**无**待写回 | **采纳表值**（别的机器改的，同步回来天经地义） |
| 同步拉到表值 ≠ 本地值，且本地**有**待写回（上次写回失败的积压） | **不被表值覆盖**（本机刚改的还没写出去，覆盖等于白改），本轮同步后**自动补写** |
| 写回成功后下一轮同步 | 表值 = 本地值，自然收敛 |

一句话：**正常时表说了算；只有「我改了还没写出去」的那一小段时间，本地先守住，写出去再交权**。

### 2.4 边界情况

| 情况 | 处理 |
|---|---|
| 表里还没加「印刷状态」列 | 同步时检测列缺失 → 详情弹窗状态下拉置灰 + 提示「表里还没加印刷状态列」；其余功能不受影响 |
| 电子单 | 详情弹窗不显示状态下拉（无印刷环节） |
| 待确认 / 已在表中删除（row_gone）的单 | 不能改状态（record_id 可能已失效，写也是白写） |
| 写回报 851003 / 权限不足 | 明确提示「表格权限不足：需要在企微表格里给你开可编辑权限」；**不做 Webhook 兜底**（CLI 直连已验证可用，先简单，实测写不通再议） |
| 同事手滑在表里手改了这列 | 就是正常冲突——谁后写谁胜，同步回来本地跟着变 |

### 2.5 刻意不做

- **不做操作人记录**（谁改的状态）——单选列存不下这个，二期先不搞审计
- **不做历史状态流转记录**——只有当前值
- 电子单不做任何状态写回

## 3. 功能设计之二：定时自动同步

### 3.1 行为

- 软件启动后 **15 秒**自动拉一次（配置完整才拉；避开启动高峰，不拖慢开窗）
- 之后每隔 **N 分钟**拉一次（默认 30，设置里可调 10~1440，可关）
- **防重入**：上一次同步还没结束就到点了 → 跳过本次，不排队
- 自动同步**静默失败**：授权过期等错误只在工单视图头部出一条状态提示（「上次同步失败：授权已过期」+ 去设置的入口），**不弹窗骚扰**；手动同步保持一期行为（toast 报结果）

### 3.2 界面

- 工单视图头部显示「上次同步 HH:MM」（成功/失败两种样式）
- 设置弹窗新增「自动同步」区：开关（默认**开**，待拍板 §7 #3）+ 间隔分钟数

### 3.3 技术形态

- 定时器在**主进程**（`setInterval`，退出时清掉），复用现有同步链路（fetchSheets → fetchSheetRecords → applySync）一字不改
- 新增第一个**主进程 → 界面**的推送通道 `ticket:synced`：同步完成后主动通知界面刷新（工单列表 + 上次同步时间），不用界面轮询
- 配置存 meta 表（跟工作区走，与一期同规矩）：`ticket_auto_sync`（'1'/'0'）、`ticket_sync_interval_min`（数字）

## 4. 功能设计之三：wecom-cli 打进安装包

### 4.1 打包方式

- `wecom-cli.exe` + LICENSE 放 `resources/wecom-cli/`，electron-builder `extraResources` 随包分发（**与 FFmpeg 同一模式**），安装包 +10 MB
- `ticketsWecom.ts` 的定位顺序改为：
  1. 环境变量 `WECOM_CLI_EXE`（直接指 exe，运维逃生口）
  2. **打包内置**：`process.resourcesPath/wecom-cli/wecom-cli.exe`（dev 时用项目 `resources/wecom-cli/`）
  3. 现有 `WECOM_CLI_JS` / 开发机路径兜底（一期兼容，不删）
- 内置后**直接 spawn exe**，不再需要 node 中转（比一期还少一层）

### 4.2 同事装机新流程（从三步变两步）

| 一期 | 二期 |
|---|---|
| 装软件 → **自己装 CLI** → 授权 → 表格开权限 | 装软件 → **软件里点「授权」扫码一次** → 表格开权限 |

软件内授权引导（设置弹窗）：

1. 检测到未授权（whoami 失败）→ 显示「开始授权」按钮
2. 点击 → 软件调 `auth init --noninteractive --output-qrcode <临时图片>` → 弹出二维码
3. 同事拿企业微信扫码确认
4. 软件轮询 `auth show`（最长 3 分钟）→ authorized 后自动刷新本机身份显示

⚠️ 依赖 §1.3 的两个实探验证点；若扫码接入需要管理员预先配置机器人，会在方案确认后第一时间回报，授权引导的形态可能微调（最坏情况退回「附一页授权指引文档」）。

### 4.3 刻意不做

- 不做多平台 CLI（mac/linux 二进制）——全公司 Windows
- 不做 CLI 自动升级——版本钉死随安装包走，升级 = 出新安装包

| 风险 | 对策 |
|---|---|
| auth init 扫码流程需要管理员预配置（未实探） | 施工第 0 步最先验；不通则授权引导退回指引文档形态，打包不受影响 |
