# 审批直连工单方案（主控机模式）

> 版本：v2.1（2026-11-02）　状态：**⏸ 搁置，暂不实施**
>
> 一句话：**一台机器拉审批、写表格；其余机器只读表格、只写分配。表格仍是协作中心，只是灌新单的人从官方同步换成了主控机。**
>
> v2 相比 v1 的改动：确认了四项决策、补了「副本测试环境」「升级范围」「轮询参数」三节、排期加了 S0 独立脚本。
>
> **v2.1（搁置）：** 方案本身没被否，是被排到了后面 —— 原因是"不想为此维护两个版本的软件"。
> 这个顾虑可以直接消掉（见第十五节：**一个安装包 + 一个角色开关**，本来就在设计里），
> 但当前要不要做，等以后再说。**重启时从「十五」读起，那里列了已完成的验证和未验证的三条。**

---

## 一、角色与数据流

| 角色 | 数量 | 干什么 |
|---|---|---|
| **主控机** | 1 台（本机） | 轮询审批 API → 本地库 + 表格建行；同时也能分配设计师 |
| **协作机** | 其余 | 只读表格 → 本地库；分配设计师 → 写回表格 |

```
① 新单进来（只有主控机跑）
   审批 API ──轮询 1 分钟──► 主控机软件 ──┬─► 本地库（工单队列）
                                          └─► 智能表格（新建一行）

② 分配设计师（任何机器都能做）
   界面上选人 ──写回──► 智能表格对应行的「设计师」列

③ 设计师拿到任务（每台机器都跑）
   智能表格 ──轮询 3 分钟──► 设计师软件 ──► 发现「设计师」是自己 → 建本地任务
```

**核心区分：分配 ≠ 建行。** 分配改的是已有行，几台机器并发不冲突；只有建行必须唯一，否则一张单建出两行。

## 二、已确认的决策

| # | 项 | 结论 |
|---|---|---|
| 1 | 子表 ↔ 审批模板 | **两个子表 = 两个审批模板**，按 `template_id` 分流 |
| 2 | 主控机 | **本机** |

| 5 | 写表格通道 | 沿用现有 `wecom-cli records add/update`（扫码授权），**不引入 Webhook** |
| 6 | 测试环境 | **复制两个子表做副本**，新版软件指副本，同事用原表照常工作 |

## 三、测试环境：副本方案

### 做法

1. 在同一个智能表格里，把「电子物料」「印刷物料」两个子表各**创建副本**
2. 副本改名加后缀，例如 `电子物料(测试)` / `印刷物料(测试)`
3. 新版软件的子表配置指向副本（按标题匹配）
4. 主控机拉审批 → 写副本
5. 同事的旧版软件继续用原表（官方同步照跑），**明天照常工作**
6. 测试通过后，主控机配置切回原表，副本废弃或清空

### 为什么先改名

软件是按**子表标题**匹配 `sheet_id` 的（`detectStructure`）。副本如果和原表同名，会认错表。改名后两边各自独立，互不干扰。

### 必须先看一眼

**副本左下角有没有「同步」标识。** 「创建副本」会不会继承同步关系，我没法验证。如果带标识，它每小时会被官方刷一遍，会干扰测试 —— 那种情况改用「新建空表 + 手工导数据」。

### 副本里会有什么

复制会带来现有 33 条记录。测试时主控机建的新行会和它们混在一起，靠**审批单编号**区分即可，不需要清空。

## 四、升级范围

| 机器 | 装什么版本 | 为什么 |
|---|---|---|
| **主控机（本机）** | **必须升级** | 审批直连、角色开关只在新版里 |
| **同事机器** | **建议升级，不强制** | 新版的轮询下限从 10 分钟降到 3 分钟；旧版照样能用，只是慢 |
| 版本混跑 | 允许 | 都是「读表格 → 本地库」，格式一致，互不影响 |

**注意**：轮询下限 `SYNC_MIN_INTERVAL_MIN` 是硬编码常量，配置里填 3 会被夹回 10。所以同事想变快**必须装新版**，没有别的办法。

## 五、轮询参数

| 参数 | 现在 | 改成 | 理由 |
|---|---|---|---|
| 主控机审批轮询 | — | **1 分钟** | 调的是审批 API（600 次/分上限），每轮 1 次列表 + 几张详情，压力极小 |
| 表格轮询下限 | 10 分钟 | **3 分钟** | 每次是全量拉两个子表（表里没有"最后修改时间"字段，做不了增量） |
| 表格轮询默认 | 30 分钟 | **3 分钟** | 同上 |
| 抖动 | 无 | **±30 秒** | 十几台机器同时启动会在同一秒挤请求，随机偏移摊平 |
| 失败退避 | 无 | **有** | 连续失败自动拉长间隔（3→6→12 分钟），成功一次就恢复，避免刷屏 |

**总延迟** = 主控机轮询 + 设计师轮询：

| 组合 | 最坏总延迟 |
|---|---|
| 1 分 + 3 分 | **4 分钟** ← 采用 |
| 1 分 + 1 分 | 2 分钟（收益 2 分钟，但表格请求 ×3，笔记本耗电也翻倍） |

调用量估算：10 台机器 × 每 3 分钟 2 次 ≈ **每分钟不到 7 次**，远低于任何合理上限。

## 八、关键设计决策

### 8.1 写表格用现有 CLI 通道，不引入 Webhook

取消同步后工作表就是普通表，现有的 `wecom-cli smartsheet records add/update`（扫码授权）照样能用。

- 少一套东西：不用存 URL、不用每表一个 key、不用处理"同步表禁开"的坑
- 复用现有错误处理与授权提示（`850002/850003`）

> Webhook 全字段类型已实测可用（见 `docs/58`），仅作备选：万一 CLI 在普通表上建行有问题，可平滑切过去。

### 8.2 增量水位：宁重叠，不漏单

```
本次拉取区间 = [上次水位 - 5 分钟, 当前]
```

- 无水位（首次）：拉最近 7 天
- 单次返回上限 100 条，用 `new_cursor` 翻页
- 时间跨度硬上限 31 天，水位更早则截断
- **水位只在「建行成功」之后才前进** —— 宁可重拉，不可漏单

### 8.3 去重键：审批单编号

表格「审批单编号」= 审批 `sp_no`（形如 `202610060003`），两边同源。建行前先查表：

| 表里有 | 动作 |
|---|---|
| 没有 | `records add` 建行 |
| 有、状态不同 | `records update` 更新状态（+ 审批流程） |
| 有、状态相同 | 跳过 |

### 8.4 字段映射

**系统字段**

| 表格列 | 来源 |
|---|---|
| 审批单编号 | `sp_no` |
| 申请人 | `applyer.userid`（明文，正好是成员列写法） |
| 申请人账号 | `applyer.userid` |
| 申请人部门 | `applyer.partyid` → 通讯录查部门名 |
| 提交时间 | `apply_time` → `YYYY-MM-DD HH:mm:ss` |
| 完成时间 | 末节点通过时间（无则空） |
| 提交方式 | 默认「本人提交」；`batch_applyer` 有值写「代提交」 |
| 当前审批状态 | `sp_status`：1 审批中 / 2 已通过 / 3 已驳回 / 4 已撤销 / 6 通过后撤销 / 7 已删除 |
| 审批流程 | 由 `sp_record` / `process_list` 拼文字，**格式可简化** |
| 备注 | `comments[].commentcontent` 拼接 |
| 审批链接 | 待验证（见第十节 #2） |

**模板控件字段**：按 `apply_data.contents[].title` 直接匹配列名（列名 = 控件名）。

**写入规则（已实测）**

| 类型 | 写法 |
|---|---|
| 文本 | `[{type:'text', text:'…'}]` |
| 日期 | `'2026-11-02 09:30:00'` |
| 数字 / 电话 | 原值 |
| 链接 | `[{type:'url', link, text}]` |
| **成员** | `[{userId:'明文userid'}]` —— **用加密 ID 报 40031** |
| **单选** | `[{text:'已通过'}]` —— 自动匹配选项，不用 option id |

### 8.5 失败与降级

| 失败 | 处理 |
|---|---|
| 换 token 失败 | 重试 3 次（指数退避），仍失败界面提示「授权异常」 |
| 拉单号失败 | 水位不前进，下轮重拉同区间（幂等） |
| 建行失败 | 记入 `approval_pending` 重试；界面显示待补数量 |
| 主控机长时间不可用 | 界面提示「建议临时打开官方同步兜底」 |

## 十一、分阶段实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| **S0** | **独立脚本 `tools/approval-sync.cjs`**：拉审批 → 写副本表。不碰软件主体，不动他的日常操作 | 副本里出现正确的行，字段人工比对无误 |
| **S1** | 审批 API 客户端 + 设置页「测试连接」（只打印近 7 天单号数） | 单号数与实际提交量对得上 |
| **S2** | 字段映射抽成模块 + 写入副本 | 连跑 1 天，数据质量稳定 |
| **S3** | 主控机同步主流程（水位、去重、状态回写、失败重试） | 连跑 8 小时，无重复、无漏单 |
| **S4** | 角色开关 + 轮询参数改造（3 分钟 / 抖动 / 退避） | 协作机不发审批请求；抖动作生效 |
| **S5** | 备份 / 回填「设计师 + 状态」 | 能导出、能灌回 |
| **S6** | **正式切换**：取消原表同步 → 主控机指向原表 | 新单 ≤4 分钟进表，33 条历史不重复 |

**S0~S5 全程不碰生产表**；S6 之前必须完成 S5。

## 十二、验收标准

| 项 | 标准 |
|---|---|
| 新单延迟 | 提交 → 出现在设计师队列 ≤ **4 分钟** |
| 不重复 | 连跑 8 小时，同一 `sp_no` 只有一行 |
| 不漏单 | 主控机停机 8 小时后开机，能按水位补齐 |
| 字段正确 | 抽 5 条与官方同步的行逐字段比对，除「审批流程」格式外一致 |
| 分配不变 | 两台机器分配都能写回，设计师侧能正常建任务 |
| 协作机干净 | 协作机不发审批请求（日志确认） |

## 十三、风险与回退

| 风险 | 对策 |
|---|---|
| 取消同步不可逆 | 迁移前导出备份；旧表永久保留可查 |
| 主控机关机 → 表停更 | 关机即下班，无人作业；开机按水位补拉 |
| 主控机被误设两台 | 设置页红字警告 |
| Secret 泄露 | 加密存储；只填主控机 |
| 审批模板改字段 | 映射按 title 动态匹配，自动跟随；列名变了才需人工处理 |
| 高频轮询报错刷屏 | 失败退避（3→6→12 分钟） |

**回退流程**：
1. 关掉主控机开关
2. 重新建立官方同步（**会新建一张子表**）
3. 用 S5 的备份把「设计师 / 状态」灌进新表
4. 软件按子表标题自动认到新 `sheet_id`，无需改配置

## 十五、为什么搁置，以及重启时从哪儿接

### 15.1 搁置的决定（2026-11-02）

方案本身没问题、技术路径也已经验过大半。不做的原因是**顾虑产出物变复杂**，具体两条：

1. 一套能跑通的系统里出现"两个版本的软件"，将来复制给别的公司 / 别的团队时不好解释
2. GitHub 上得同时挂主控版和非主控版

### 15.2 这个顾虑可以直接消掉：本来就是一个包

**方案里从来不需要两个安装包。** 第九章那个「角色」就是**本机配置**：

```
设置 → 审批数据源 → 角色
   ○ 主控机（本机拉审批、写表格）
   ● 协作机（只读表格）
```

同一个 `VellumDesk-1.13.0-Setup.exe`，装完在设置里选一个角色就行。代码不是分叉的，是运行时读一个存在 `meta` 里的值；
GitHub 只发一个 release，`git` 也只有一个分支。

所以「要不要加开关」这个问题不用再想了 —— **开关就是设计本身**，只不过它解决的是「分发」，不解决下面这些：

| 它解决的 | 它不解决的 |
|---|---|
| 只发一个安装包 | **配置约定**：两台都设成主控机 → 同一张单建两行（界面上有红字提示，但拦不住） |
| 换主控机 = 改个选项，不用重装 | **Secret 只该填一台**：填了没人用也不报错，但那是多一份泄露面 |
| 别的团队拿到同一份包 | **"得有一台常开的机器"这件事本身**：这是架构前提，跟版本号无关，换谁来用都成立 |

第三条才是最不优雅的地方 —— **跟装几个版本无关，跟"表格靠谁维护"有关**。所以真正要接受的是：
这套东西一旦上线，表格的更新就绑在一台机器上（哪怕它 99% 时间都在）。

### 15.3 重启时的入口

按第十一节的排期，从 **S0** 开始 —— 一个独立脚本 `tools/approval-sync.cjs`，
只做「拉审批 → 写副本表」，不碰软件主体、不动生产表。要跑起来只需要两样：

1. `corpid` + 自建应用 `Secret`（管理员在后台建应用，并把它勾进「审批 → API → 可调用接口的应用」）
2. 两个副本子表（复制电子 / 印刷两张，名字加 `(测试)` 后缀 —— 软件按**子表标题**认表，同名的会认错）

### 15.4 已经验证过的（重启时不用重做）

| 项 | 结论 | 备注 |
|---|---|---|
| 表格里的「审批单编号」列 | 值 = 审批 `sp_no`（如 `202610060003`），**两边可直接对齐** | 最大的风险项已消 |
| 智能表格 Webhook | `add_records` / `update_records` 全类型实测通过；3000 条/分/表；只要 URL 里的 key | 只作备选，主路径用 CLI |
| 成员字段 | 必须传**明文 userid**（`MaXiangYun`）；表格里读出来的是加密 ID（`woJ3...`），回写报 40031 | 踩过 |
| 选项字段 | 直接传中文（`已通过`）自动匹配 option id，不用维护映射表 | 踩过 |
| 日期 / 数字 / 链接 | 字符串日期自动转毫秒；数字直传；链接要 `{type:'url', link, text}` | 踩过 |
| 官方同步的行为 | 内置功能（`orgin=approval_sync_to_smart_table`）、连"审批中"的单也搬、搬 10 个系统字段 + 模板控件字段 | |
| 同步表禁止开 Webhook | 界面上灰显 | 决定用 CLI 的原因 |
| 取消同步 ≠ 暂停 | 重新建立同步会**新建一张子表**，回不到原来那张 | 关同步 = 一次性迁移 |
| 软件 `applySync` | **采纳表值**（除 `designer_write_pending=1`），表格被冲 = 本地也丢 | 迁移前必须先导出备份 |
| 生产表现状 | 电子 25 条 / 印刷 8 条 / 测试 1 条（空）；约 23 条已有设计师 | 重指派成本按这个估 |

### 15.5 还没验证的（重启后第一件事）

1. **官方同步撞到表里已存在的同单号行会怎样** —— 跳过 / 覆盖 / 再建一条。前两种 P3 双写可行，第三种只能接管
2. **副本子表继承不继承同步关系** —— 左下角有没有同步标识；有的话它每小时被官方刷一遍，会污染测试数据
3. **审批模板 ↔ 子表的字段对齐** —— 列名应该 = 控件名，但附件（`media_id`）和微盘文件还要单独处理

### 15.6 重启的触发条件

什么时候值得把它捞回来，按优先级：

- 有人开始抱怨"提交了半天表里没有单"（说明 0~60 分钟那一段真的影响干活）
- 或者单量涨到人工点「立即同步数据」顶不住了
- 单纯为了"技术上是通的"去做，不值 —— 收益是省下的等待时间，成本是一台常开机器 + 一个没人管的 Secret

**在此之前都维持现状**：官方同步照跑，软件轮询间隔可以调低到 10 分钟（这个不用改代码，设置里就能改）。

### 15.7 已作废的替代思路（写着免得将来又提一遍）

**① 局域网同步分配（2026-11-02 作废）**

设想：所有机器各自读审批 → 本地形成工单队列；设计师分配走局域网（同一 WiFi）广播同步，弃用智能表格。

作废原因（按重量排序）：

| # | 问题 |
|---|---|
| 1 | **单点没消掉，只是换了位置**：A 分给张三、B 分给李四，局域网上没有权威源。要么指定一台当服务端（单点又回来了，还比表格差），要么做 P2P 合并（时钟偏移、分区合并、新人补历史 —— 已经是分布式系统） |
| 2 | **Secret 从 1 份变成 N 份**，而它泄露 = 能读全公司审批单（含报销、请假、调薪）；模板一改还得全员升级解析层 |
| 3 | **丢三样产品能力**：申请人在企微里看不到进展、设计师手机上看不到、没有云端历史（某台机器硬盘坏了，它记的分配就没了） |
| 4 | **收益只有 3 分钟**：分配延迟从「3 分钟轮询」变「秒级」。为这 3 分钟重写整个协作层，不值 |
| 5 | 前提不一定成立：企业 WiFi 常开客户端隔离、Windows 防火墙拦入站、有人居家/出差/开热点就不在同一网段 |

**要不要更快的分配？** 那是另一个便宜问题：把轮询常量从 10 分钟改到 3 分钟、发一次版，零架构风险。跟局域网无关。

**② 镜像子表（更早作废）**

设想：保留官方同步，另建两个表头一样的空子表，用跨表同步/查找引用把它们"镜像"出来，对镜像表开 Webhook。

作废原因：智能表格的「跨表同步数据」出来的**仍然是同步表，同样禁止开「接收外部数据」**，而且它自己的频率也是 1 小时一次 —— 绕一圈，两处都堵着，还多一层同样的延迟。「查找引用」是只读、且不会建行，新表建出来还是空的。

**两条路的共同点**：都想绕开"智能表格是云端权威"这件事。而每一次绕开的代价（一致性、安全、产品可见性、工作量）都比保留它高。
**所以这个问题的正确答案很可能不是"换个架构"，而是"这个延迟到底值不值得治"。**
