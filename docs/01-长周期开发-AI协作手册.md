# 长周期开发 · AI 协作手册

> 解决的问题：一个要做一个多月的软件项目，怎么让 AI 始终"记得住"，不会做着做着就失忆、跑偏、推翻自己。
>
> 适用：零编程基础、靠 AI 一点点把软件做出来的人。

---

## 〇、三句话结论

1. **上下文不够是必然的。** 换任何 AI 工具都一样，这不是 WorkBuddy 的缺陷，是这类技术的物理上限。
2. **解法不是"找一个记性好的 AI"，而是"让文件记住，让 AI 每天来读文件、改文件"。**
3. 这套做法专业团队也在用，有个名字叫**上下文工程**（Context Engineering）。你只要掌握 3 个文件 + 2 句固定话术就够了。

---

## 一、为什么上下文一定会不够

先建立一个直观的量感：

- AI 一次对话能"看见"的信息量，大概相当于**一本 5～8 万字的中篇小说**。
- 而一个真实的桌面软件项目，光是代码就有几万行；再加上需求讨论、报错排查、方案反复，信息总量是它的**几十倍**。
- 更关键的是：**不是撑满了才出问题，而是装到六七成，AI 的注意力就开始稀释**——前面说过的细节它记不牢了，你会发现它把 A 功能的做法套到 B 上，或者开始编造你从没要求过的功能。

所以"开一个超长对话把项目做完"这条路，从一开始就不通。**放弃这条幻想，是项目能顺利做完的第一步。**

> 打个比方：你不会指望一个员工凭脑子记住整个项目。你会给他建一套档案，让他随时能查。AI 也一样——只不过这个员工**每天上班都会失忆**，所以档案必须写下来。

---

## 二、WorkBuddy 手里有什么牌（本机实测）

WorkBuddy 没有"项目记忆库"这种一键功能，但它给了几个零件，拼起来完全够用。

| 能力 | 具体是什么 | 对长周期开发的价值 |
|---|---|---|
| **本地文件读写** | 能直接读、改你电脑上的文件 | ★★★★★ 档案法的地基，**最重要** |
| **长期记忆（memory）** | 跨会话记住你的偏好和习惯 | ★★★ 记住"叫他兄弟""要成稿不要框架" |
| **技能（Skills）** | 把重复的流程固化成一条命令 | ★★★ 中后期提速明显 |
| **定时任务（Automations）** | 让 AI 按时间点自动执行 | ★★ 可选，锦上添花 |
| 单次对话上下文 | 一次会话内的短期记忆 | 有限，一定会满 |

**注意看第一行。** 只要 AI 能读写你电脑上的文件，长周期项目就有了**永不丢失的记忆体**——比任何"记忆功能"都可靠，因为文件在你自己硬盘上，不依赖任何服务。

---

## 三、核心方法：把项目"档案化"

### 3.1 三个必须存在的文件

在项目根目录放这三个文件，它们就是 AI 的"入职材料"：

| 文件 | 它回答什么问题 | 更新频率 |
|---|---|---|
| **`PROJECT.md`** | 这项目是干啥的？用什么技术？有哪些铁律不能违反？ | 很少改（立项时写好） |
| **`PROGRESS.md`** | 干到哪了？上次解决了什么？下一步做什么？ | **每次会话都要更新** ★ |
| **`DECISIONS.md`** | 为什么选 A 不选 B？ | 每次做技术决定时追加 |

`PROGRESS.md` 是最重要的一个。它就是**接力棒**。

### 3.2 完整目录长这样

```
素材管家/
├── PROJECT.md          ← 项目身份证（AI 必读）
├── PROGRESS.md         ← 进度台账（AI 必读 + 必写）
├── DECISIONS.md        ← 决策记录（AI 必读 + 必写）
├── README.md           ← 给人看的说明
├── docs/               ← 需求文档、设计稿、笔记
│   └── 素材管家-需求文档.md
├── src/                ← 源代码（脚手架自动生成）
└── package.json        ← 脚手架自动生成
```

**现在就已经有价值了**：你昨天那份需求文档，其实就是第一份档案。它不需要放在聊天记录里——放在 `docs/` 里，任何时候 AI 都能重新读一遍，比你复述一遍准确得多。

---

## 四、每次开新会话的标准动作

不用记，直接复制粘贴。

### 4.1 开场（新会话第一句话）

```
先读 PROJECT.md、PROGRESS.md、DECISIONS.md，
然后我们继续做：______
```

### 4.2 收尾（一段活儿干完时）

```
把这次做的改动、遇到的问题、下一步计划，
追加到 PROGRESS.md 和 DECISIONS.md
```

### 4.3 为什么这两句话这么有效

AI 读完那三个文件，等于"入职培训"完成：项目背景、技术栈、走到哪一步、为什么这么定，全都在了。你**不用从零解释**，它也不会因为不知道前情而瞎猜。

这就是为什么强烈建议**一次只推进一小块**：一小块做完，归档，接力棒交接清楚，下一块才稳。

---

## 五、接力棒：什么时候换会话、怎么换

### 5.1 出现这些信号，就该换人了

- 你发现自己**又要重复解释**已经说过的背景
- AI 开始**记混**（把 A 模块的做法套到 B 上）
- 单次会话超过 **20 轮**对话
- **一个功能做完了**（天然的分界点）

### 5.2 换人的标准流程（关键动作）

1. 先说一句：**"上下文快满了，先把进展全部写进 PROGRESS.md"**
2. 让它写一份**交接单**（模板见下节），确认落盘
3. **开一个全新会话**，按 4.1 的开场模板重新开始
4. 如果它写的信息和你想的不一样，当场纠正——**档案写错比不写还危险**

> 记住这个比喻：**每次交接前，先把接力棒放回架子上。**

## 六、让 AI 自己写交接单（提示词模板）

上下文快满时，直接发这段：

```
上下文快满了。请写一份交接文档，逐条写进 PROGRESS.md，
内容包含：
1. 当前完成度（哪些做完了、哪些没动）
2. 这次改了哪些文件，各自作用是啥
3. 还没解决的问题和已知的风险
4. 下一步该做什么，越具体越好（最好写到"打开哪个文件、改哪一行"）
5. 下次开工前需要先读哪些文件
```

第 4 条最重要——**下一个会话的你会直接受益。**

---

## 七、进阶能力（现在不用管，知道有这回事就行）

做到中后期，这两个东西能显著提速：

- **技能（Skills）**：如果某类事要重复做 5 次以上（比如"每加一个功能模块都固定是那 8 步"），可以让 AI 把流程固化成技能，以后一句话触发，不用每次重新解释。
- **定时任务（Automations）**：比如设成每天上午自动跑一遍"检查代码能不能正常启动、依赖有没有过期"，结果给你。

现在一律不动。**第一阶段只需要"文件 + 两句话术"。**

---

## 八、三条铁律

1. **不要指望 AI 记住，要让文件记住。**
2. **一次只推进一小块，每块做完必须归档。**
3. **每一步结束时，软件必须处于"能跑起来"的状态。**（不要同时改三个地方，出问题你会不知道该退回哪一步）

## 九、附录：三个文件的模板

### 9.1 `PROJECT.md`

```markdown
# 项目：素材管家

## 一句话说明
本地素材管理桌面软件，管理公司的设计物料、图片、视频素材。

## 用户是谁
公司内部设计/运营团队，5-10 人，素材全部存本地。

## 技术栈（已定，不要擅自更换）
- 桌面框架：Electron
- 界面：React + TypeScript
- 构建：electron-vite
- 数据库：SQLite（better-sqlite3）
- 关键库：sharp（图片缩略图）、FFmpeg（视频抽帧）、archiver（打包）

## 已经确定的事（不要推翻）
见 DECISIONS.md

## 明确不做的事
- 不做云端同步
- 不做多人在线协作
- 不做素材在线编辑

## 给 AI 的协作规则
1. 每次开始前先读 PROGRESS.md
2. 每次结束前把进展写回 PROGRESS.md
3. 改代码前先说清楚要改哪些文件、为什么
4. 不要一次改超过 3 个文件
5. 报错先给我看原文，不要自己猜着改
6. 保持每一步结束时软件能正常启动
```

### 9.2 `PROGRESS.md`

```markdown
# 进度台账

## 当前状态
阶段：环境搭建
完成度：0%

## 已完成
- [x] 2026-09-23 需求文档定稿（docs/素材管家-需求文档.md）

## 进行中
- [ ] 开发环境搭建

## 下一步（下次开工从这里开始）
1. 执行 npm 镜像配置
2. 用 electron-vite 建脚手架
3. 跑通 npm run dev

## 已知问题
（暂无）

## 会话日志
### 2026-09-23
- 做了什么：…
- 改了哪些文件：…
- 遗留：…
```

### 9.3 `DECISIONS.md`

```markdown
# 技术决策记录

记录格式：日期 / 决定 / 为什么 / 放弃的方案

## 2026-09-23　选 Electron，不用 Tauri
- 决定：桌面框架用 Electron
- 原因：Tauri 需要会 Rust，招人和外包都贵；Electron 生态成熟，出问题能搜到答案
- 放弃：Tauri（体积小但技术门槛高）

## 2026-09-23　选 electron-vite 脚手架
- 决定：用 electron-vite 建项目
- 原因：自带 React + TS 模板，热更新配置现成，对新手最省事
- 放弃：手动搭 webpack（配置复杂）
```

---

## 十、一句话总纲

> **上下文会满，但硬盘不会。**
> 把项目写进文件，AI 每天来读写——这就是长周期开发的全部秘密。
