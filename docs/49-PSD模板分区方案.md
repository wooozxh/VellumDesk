## 0. 一句话

在软件里**单列一个「模板」分区**（不与通用素材库同入口），专收带参考线的 PSD 模板；
按契约把清单写成 `tpl.json`（+ `thumb\p<id>.png`），并在插件点「用模板建稿」时

## 1. 为什么 / 依据

### 1.1 用户原话（**不改需求**）

> 「我想在软件侧再加一个分区，专门用来储存我们常用的、建好的 PSD 模板，
>   然后也把这个参考线打好，直接调用就可以。但是呢，和素材我不建议在一个功能入口里，
>   应该是单列出一个功能，就是不和素材库这个功能在一起。」

⇒ 两条硬约束：

1. 模板在软件侧**单列一个分区**（**不是**通用素材库里的一个分组）；
2. 模板 PSD 要**自带参考线**（出血线 / 安全线），同事点了就能直接用。

### 1.2 插件侧已拍板的五项（**已定，不再问**）

## 3. 磁盘结构与数据模型（迁移 23）

### 3.1 磁盘

```
D:\vellum_workspace\
├─ _通用素材库\          ← 既有（第 62 批；本批一并放开到多层）
└─ _PSD模板库\            ← 本批新增
   ├─ 易拉宝 80×180（含3mm出血）.psd     ← 直接躺在根下 = 未分组
   └─ 易拉宝\                            ← 第 1 层（任意层，最深 5 层）
      └─ 2026春季\
         └─ 海南\
            └─ 集团版\
               └─ 展架 100×200.psd       ← 第 5 层（允许）
                  └─ 更深\ …            ← 第 6 层：**不收录**，扫描跳过并提示
```

- 根名 **`_PSD模板库`**（下划线开头 → 任务扫描自动跳过，与 `_通用素材库` / `_thumbs` / `_system` 同一路数）。
- **只有它自己的扫描器**（只扫这一个根），与任务扫描互不干扰；`_` 开头也让任务扫描**不会把它当成"待归类任务"**
  （第 55 批那个"待归类任务散架"的坑，正是根目录下**不带下划线**的目录被判成项目/任务才发生的）。
- **深度上限 = 5 层**（契约 §5.3 第 1 条，两侧一致）；**第 6 层及更深的文件不收录**，
  扫描跳过并进「未收录名单」提示条（形态与 20 MB 卡口一致，**不静默**）。
- 文件丢了 → 打 `missing_at` 标记、**不删记录**（照第 8 批口径）。
- ⚠️ **中间层被删时的截断规则**（插件侧提醒的真坑，两侧都要守）：
  磁盘上某中间目录被删，**不能把它下面整支丢掉** —— 要**截断到仍然存在的最长前缀**，
  否则用户在深目录里一刷新就被弹回顶层。

### 3.2 数据模型（迁移 23 · 两张表）

**多层分组 ⇒ 与通用库同构的两张表**（`tpl_folders` + `tpl_assets`）：

```sql
-- ① 分组表：照 brand_folders，但**去掉两层封顶**（深度由代码卡在 5）
CREATE TABLE IF NOT EXISTS tpl_folders (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  parent_id   INTEGER REFERENCES tpl_folders(id) ON DELETE CASCADE,  -- NULL = 顶层
  name        TEXT    NOT NULL,
  sort_order  INTEGER NOT NULL DEFAULT 0,        -- **同层**单调（契约 §5.3 第 2 条）
  rel_path    TEXT    NOT NULL DEFAULT '',       -- 相对工作区根
  created_at  TEXT    NOT NULL,
  UNIQUE(parent_id, name)                        -- ⚠️ 对 parent_id IS NULL **不去重**，顶层靠应用层查重
);

-- ② 素材表
CREATE TABLE IF NOT EXISTS tpl_assets (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  folder_id    INTEGER REFERENCES tpl_folders(id) ON DELETE SET NULL,  -- NULL = 未分组
  file_name    TEXT    NOT NULL,
  ext          TEXT    NOT NULL DEFAULT '',      -- psd / psb
  size         INTEGER NOT NULL DEFAULT 0,       -- 字节（收录时已卡 ≤20 MB）
  abs_path     TEXT    NOT NULL UNIQUE,
  rel_path     TEXT    NOT NULL DEFAULT '',
  thumb_path   TEXT,
  width        INTEGER,                          -- 画布像素宽（收录时必读到，否则不收）
  height       INTEGER,
  color_mode   TEXT,                             -- CMYK / RGB…
  resolution   REAL,                             -- ppi（读不到则 NULL）
  guides       INTEGER,                          -- 参考线条数（IRB 1032；读不到 NULL，0 = 确认无线）
  missing_at   TEXT,
  created_at   TEXT    NOT NULL,
  modified_at  TEXT    NOT NULL,
  scanned_at   TEXT    NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_tpl_folders_parent ON tpl_folders(parent_id);
CREATE INDEX IF NOT EXISTS idx_tpl_assets_folder ON tpl_assets(folder_id);
```

> 📌 **没有 `usage` / `frame_mm` / `bleed_mm` 三列**（2026-10-17 定稿）：分类由**分组路径**表达（Q1），
> 成品尺寸/出血 PSD 里没有、v1 不手填（Q2）。**不建永远空着的列** —— 少一列就少一处"看起来有其实没有"的坑。

- 迁移号 **23**，追加在 `db.ts` 的 `migrate()` **末尾**（现最高 22，`db.ts:854-904`）。
- **新表可以自带索引**（本批不 ALTER 老表）。
- **刻意不复用 `assets` / `brand_assets`**（docs/46 §3.1 的同一理由）：复用会往未归属池 / 文件视图 /
  统计 / 标签计数里掺进模板 → 又是一轮「隐身类语义改动要全量过 SQL」的高危活。
- **`tpl_assets.id` 独立从 1 起** ⇒ 镜像缩略图必须用命名空间 **`p<id>`**（契约 §5.5，与 `t`/`b` 同理）。

### 3.3 五条硬约束（契约 §5.3 已落正文，软件侧要逐条守住）

| # | 约束 | 软件侧怎么做 |
|---|---|---|
| 1 | **深度 ≤ 5 层** | 建组时拦住第 6 层（父组到第 5 层就不再给"新建子分组"）；扫描跳过第 6 层及更深并进未收录名单 |
| 2 | **同层 `sortOrder` 单调** | 建组 = 同层 `max+1`；置顶/排序 = 同层重排 `0..n`（现有 `brandLib` 逻辑照抄，**不跨层混排**） |
| 3 | **同层不允许同名** | ⚠️ `UNIQUE(parent_id, name)` 对 `parent_id IS NULL` **不去重**（SQLite 把 NULL 当互不相等）⇒ **顶层必须靠应用层显式查重**（现有 `createBrandFolder` 已如此），并补 accept 断言防将来重构掉 |
| 4 | **素材可挂任意层** | 不要求只挂在叶子组；`folder_id` 指向任意层都合法 |
| 5 | **脏数据容错，绝不丢素材** | 写方不产脏数据；但**扫描侧要守"截断到仍存在的最长前缀"**（见 §3.1 最后一条） |
| — | **成环** | 软件侧**目前没有"移动分组"功能**（只有 建/改名/排序/置顶/删除）⇒ **当前不存在成环入口**。**将来加"移动分组"时必须做子树包含检查**（把父组拖进自己子树要拒绝）—— 已列为遗留约束 |

## 4. 收录规则（**卡口都在这一步**）

| 规则 | 行为 |
|---|---|
| **只收 PSD** | `psd`（含 `psb`）；其余扩展名一律**拒绝收录**并明说原因（界面上给一行） |
| **20 MB 上限**（拍板 ④） | 超限**不落盘、不登记**，累积成一份「未收录名单」，界面给提示条「N 个文件超过 20 MB 未收录」+ 可展开看清单，附「请瘦身」文案。**绝不静默放过、也绝不静默删别人的文件** |
| **尺寸必填**（拍板 ⑤） | 收录前先读画布 `width` / `height`；**读不到 → 拒绝收录并说明原因**（"无法读取画布尺寸"）。这是模板与通用库的关键差别 —— 通用库允许 `width/height = null`（契约 §5.4），模板不行 |
| **深度上限 5 层**（契约 §5.3-1） | 第 **6 层及更深**的文件**不收录**（跳过 + 进未收录名单提示条）；建组时父组到第 5 层就不再给"新建子分组" |
| 两条收录路径 | ① **导入**（软件里挑文件 / 拖入 → **复制**进库，不动源文件）；② **扫描磁盘**（资源管理器里手放 → 扫一次自动认领）。**无文件监听**（与通用库一致：手放后要点一下扫描，或打开视图时自动扫一次） |
| 同名 | **组**：同层不允许同名（应用层查重）；**文件**：自动 `-2` / `-3`（照 `brandLib.uniqueFile`） |

> ⚠️ **顺序很关键**：导入时**先读尺寸 + 判体积，再复制**。反过来会留下"复制进来又被拒"的半成品文件。

## 7. `handoff` 支持 `scope:"tpl"`

插件写 `handoff/req.json`（`{ assetId, scope: "tpl" }`）→ 软件在 **tpl 表内**反查 → 拷成
`handoff/incoming.psd` → 盖 mtime → 写 `res.json` → 插件 `app.open`。

**代码改动只有两处**（`src/main/linkHandoff.ts`）：

| 位置 | 现状 | 改为 |

  ③ `groups[]` 能表达**空分组**与**分组顺序**（`sortOrder`），`groupPath` 表达不了（空目录在插件里会凭空消失）；
  ④ 模板库正好"启用"那个原本"先留空不用"的 `groups[]`（改拍板 ③ —— 要多层，这条必然要让）。
- 排序：`groups[].sortOrder` 表达分组顺序（两库统一）；组内模板顺序后续可加 `items[].sortOrder`。

### 15.2 【变更 ②】模板的用法是「**新建一张 PSD**」，不是「置入到当前稿」

> 用户原话：「我在还没有创建 PSD 的时候，我通过这个现在这个模板功能，我选中一个模板，
> 我点击创建，它就能新建一个 PSD。」

- **可以实现，而且插件侧本来就是这么规划的**：`docs/53` §4.4 + §五 写明
  `lib/ps.js` 新增 **`openTemplate()`**：「handoff 拉 PSD → **`app.open`**」。
  且 §二 已实测 **`app.open(Entry)` 可用**（模态内），**重开 PSD 后参考线仍在（guides=4）**。
- **关键澄清**：handoff 只是一条"把文件送过去"的通道，**它不决定用法** ——
  同一份 `incoming.psd`，插件既可 `placeEvent`（置入图层），也可 **`app.open`（打开成新文档）**。
  用户担心的"导入到一个已建好的 PSD 里"**不是**插件侧的设计。
- **⇒ 软件侧工作量完全不变**：还是 §7 那两处改动（scope 白名单 + 选表）。
  怎么用是插件侧的事，软件侧只负责"把原件送到位"。
- 唯一要跟用户说清的副作用：**`Document.name` 不可改** ⇒ 打开后文档名一定是 `incoming.psd`。
  插件侧给了三个缓解选项（`docs/53` §六：A 如实提示"请另存为" / B 打开后立刻 `saveAs` / C 改软件侧命名），
  **要用户选**（插件侧的题，不是软件侧的）。
- 补充：**创建动作在 PS 里完成** —— 软件侧点不了"用模板新建 PSD"（它不驱动 PS）。
  软件侧模板视图是本批的**管理界面**（收录 / 改名 / 删除 / 预览）。

### 15.3 【疑问 ③】"那个 JSON 只能写一个还是可以写多个" —— 软件侧的事实

- `manifest.json` **只有一个**（总索引，插件只 stat 它）。
- **每个库 = 一个明细文件**：`task.json` / `brand.json` / `tpl.json` —— **现在是 3 个**。
- **模板分多少层、有多少条，都在这一个 `tpl.json` 里** —— 多层是**文件内部**的结构
  （每条带 `groupPath`），**不会变成多个 json**。
- ⇒ 「库的数量」决定文件数；「模板的层级 / 数量」不增加文件。
  用户要在插件侧确认的是**"插件怎么按路径渲染成树"**，那确实是插件侧的事。

### 15.4 顺带提醒（插件侧会遇到，先垫一句）

插件侧 `docs/53` §五 已指出：素材库页的「库」标签是**完全由 `manifest.scopes[]` 动态生成**的，
软件侧一写出 `tpl` scope，素材库页会**自动多出一个「模板」标签** ——
所以插件侧**必须主动把 `tpl` 排除**出素材库。这是插件侧唯一一处"必须违反既有自动机制"的地方，
用户跟插件侧对齐时可以直接提这条，省一轮。

### 15.5 【变更 ③】通用素材库也要改成**多层**（2026-10-17 用户提）

> 用户原话：「多层目录这个事儿我还想复用到通用素材库里，就是我想把通用素材库也改成多层目录，
> 现在两层确实有点不够用。」

🔴 **这条不能只改软件侧** —— 是个硬事实，读契约 §5.3 得到：

> 「插件侧读法（2026-10-11 两侧确认）：`parentId` **缺失 / `null` / 空串 / 指向不存在的分组 /
> **超出两层** → **一律当顶层，且绝不丢素材**（插件 v0.2.8 已按此实现）。软件侧**两层封顶**，

⇒ 若**只**把软件侧的多层打开，插件侧会把**第 3 层及以下全部拍平到顶层** ——
界面上看着像数据错乱，**比现在更糟**。典型"两边不同步就会看到怪东西"。

**影响面**：

| 处 | 怎么改 |
|---|---|
| 契约 §5.3 | 「软件侧两层封顶」这句**承诺要改**（改成不限层）；插件侧"超出两层→顶层"的降级**要删** |
| 契约 §十 判定 | 判为**加法（放宽）**：2 层以内的数据行为**完全不变**，3 层以上从"降级"变"正确渲染" ⇒ **不升版本**，但两侧各自记 `DECISIONS`（此判断需插件侧确认） |
| `src/main/brandLib.ts` | `BRAND_MAX_DEPTH` 常量 + `createBrandFolder` 的 `depth` 校验 + `listBrandFolders` 里 `depth = parent_id === null ? 1 : 2` 的算法 |
| `src/main/brandLib.ts` `scanBrand` | 现在有「三层及以上：跳过并计数 `skippedDeep`」⇒ 改为不跳 |
| 界面 | `brand-tree` 现在是两级缩进 ⇒ 要改成任意层级（**与模板库共用同一套树渲染**） |
| 文案 | 「只做两层」相关提示（`COPY.brand.depthLimit` / `skippedDeep`）要改 |

> 分两批会把渲染和契约各改两遍。

### 15.6 🔴 开工顺序（★ 2026-10-17 15:40 **已按插件侧时序修订**）

**结论：拆成两件事看 —— 模板库「软件侧先」，通用库多层「插件侧先」。**

| # | 事项 | 谁先 | 为什么 |
|---|---|---|---|
| 1 | **模板库（全新功能）** | ✅ **软件侧先** | 软件侧是**生产端**：它不写出 `tpl.json`，插件侧没有任何真数据可读（只能拿假镜像自测 —— 那是开发手段不是验收）。插件侧 `docs/53` §七 自己也是这个结论 |
| 2 | **通用库/模板库改多层** | ✅ **插件侧先**（兼容改动可先发） | `MAX_DEPTH 2 → 5` 对**现有两层数据行为完全不变** ⇒ 可安全先发布。这样"新数据撞旧插件"的窗口**根本不存在** |
| 3 | **契约正文** | 软件侧起草 | §十 要求"两侧同时知悉 → 改正文 → 两侧记 DECISIONS"，起草与落文由软件侧做（**唯一权威源在 `D:\vellum-link\`**） |
| 4 | 插件侧「JSON 规范建稿」 | 可**并行** | `docs/53` §七 步骤 ③ **不依赖软件侧**，插件侧不必干等 |
| 5 | 插件侧「面包屑下钻 UI」 | 等有真三层数据 | 没有三层数据时只能拿假镜像验收 |

> ⚠️ **修订说明（诚实留痕）**：上一版本我写的是"通用库多层**两侧同时**改"。
> 插件侧提出更优解：**先发兼容改动**（阈值 2→5，对现有数据零影响）→ **软件侧再放开产出** →
> 插件侧再上 UI。这比"同时"更好 —— 它把"新数据撞旧插件就会降级"的窗口**彻底消除**，
> 而不是靠两边同时上线来赌时间差。**采纳插件侧方案，我原来的写法作废。**

**推荐推进顺序**：

```
① 两侧把契约落到正文（✔ 2026-10-17 已落 §5.3 + §十；tpl scope 的 §5.1/5.7 待定稿后一次性补）

```

> 一句话记住：**模板库是"生产端先"，多层是"读方先"** —— 前者因为没数据可读，
> 后者因为读方先学会读多层，写方才好放开。
