# 第 51 批：已忽略记录清理（「清掉记录」出口）方案

> 起因：用户实测报告 —— 删掉 V1 里一个 PPT 文件后，任务包的版本卡片上一直挂着一张
> 「未分版本 · 1 个文件」，去不掉。要求「只删卡片、不删文件」。
> **排查结论：用户描述的解法（加「删除版本」按钮 + 给文件夹加后缀）解决不了这个现象，
> 根因在别处。** 本方案给对症的做法。

---

## 1. 根因（已实机复现并查库确认）

用户的包「培训PPT」（`D:\vellum_workspace\总部\培训PPT`）库内实况：

| 事实 | 值 |
|---|---|
| `pack_versions` | 只有 1 条：`V1`（`is_current=1`） |
| 磁盘 `V1\03-工程` | **只有 2 个文件**（其中 `~$xxx.pptx` 是 Office 锁文件） |
| `assets` 里 `version_id IS NULL` | **1 条** ← 就是那张「未分版本」卡片 |
| 这条记录（id=4）| `营销中心-内部培训.pptx`，`missing_at=2026-10-08T11:42:46Z`，`missing_ignored_at=2026-10-08T12:32:24Z` |

**它是「已删除文件的僵尸记录」**：用户删掉 PPT → 扫描标记为**丢失** →
用户点了**忽略** → 从此这条记录

- 不出现在左栏「文件已丢失」（那儿的数字只算**未忽略**的丢失）
- 不出现在左栏「已忽略」列表里？—— **在的**（`ignored=1`），但它只是个只会「撤销忽略」的单向门
- **但仍然占着版本卡片**：版本卡片的统计口径是 `version_id IS NULL`，**不看文件还在不在**

所以那张「未分版本」卡片 = 这条幽灵记录，**它不是版本，删不掉也不该删**。

## 2. 为什么用户的解法不行（记录下来，避免以后重走）

| 用户设想 | 问题 |
|---|---|
| 在版本卡片上加「删除版本」按钮 | 删的是**版本**，而这张「未分版本」卡片是界面**自动分组的产物**，不是可删的记录 |
| 只删卡片不删文件 | 真版本（V1）下面 5 个文件都好好在盘上；删掉版本会让**活文件**的归属错乱 |
| 给绑定文件夹加后缀以区分 | V1 文件夹里全是**活文件**，改名会让扫描认不出 → 变成一堆新「丢失」，南辕北辙 |
| 刷新不扫描改后缀的版本 | 等于让软件对某些文件夹装看不见，与「扫描是唯一事实来源」的既有铁律冲突 |

**症结不在版本，在「已忽略」这个功能只进不出。**

## 3. 目标（用户已拍板：方案 A）

给「已忽略」补一个**出口**：把这条已经没用了的记录**从库里彻底清掉**，
从而让那张幽灵版本卡片随之消失。

**一句话口径：只删数据库记录，磁盘零改动。**

## 4. 安全性论证（这是本方案能成立的关键）

允许清掉的记录**必须同时**满足：

1. `missing_at IS NOT NULL` —— 扫描已确认**文件不在磁盘上**
2. `missing_ignored_at IS NOT NULL` —— 用户已明确说过「不打算找回了，别再提醒我」

由此推出两个保证：

- **不可能误删用户文件**：文件本来就不在盘上，删库记录不碰磁盘一个字节。
- **这不是不可逆的数据丢失**：万一文件以后又出现在目录里（用户自己放回去 / 从别处拷回来），
  下一轮扫描会**重新建一条记录**并重新生成缩略图。也就是说：**清掉 = 丢弃一条失效的索引，
  事实来源（磁盘）不动，随时可以重新索引回来。**

**不给「待处理的丢失」这个出口**：那些行还有「重新定位」可用，用户并没有说放弃 ——
保持 `missing_at 非空 + missing_ignored_at 非空` 这个双重门槛，宁可少给一个按钮，
也不越界替用户丢东西（沿用「软件永不悄悄扔东西」的铁律）。

## 5. 做什么 / 不做什么

**做**

- `purgeIgnoredAssets(ids)`：删 `assets` 行（`asset_tags` 有 `ON DELETE CASCADE`，标签自动跟着清）
- 行尾出口：已忽略的行从「只有撤销忽略」变成 **撤销忽略 + 清掉记录**（垃圾桶图标 + 二次确认）
- 批量出口：在「已忽略」筛选下勾选若干行 → 出现「清掉记录 (n)」
- 文案、类型、preload 通道

**不做**

- **不碰磁盘**（不删文件、不改文件夹名、不给文件夹加后缀）
- **不删缩略图缓存**（`_thumbs/*.webp`）：与既有「删包」路径保持一致
  （那条路也只删库记录、不清缩略图），不为本批单独引入文件删除动作
- 不动版本绑定的任何逻辑（`V1` 这些真版本完全不受影响）

## 6. 界面

沿用既有约定（第 47 批那一套）：

- 单条：`FileRow` 的「已忽略」态行尾 → `[撤销忽略] [清掉记录]`
- 批量：文件视图工具条右侧，`pickedIgnoredCount > 0` 时出现「清掉记录 (n)」
- 二次确认：`window.confirm`（与「移除工作区」等破坏性操作同一套做法），
  文案必须**明确写出「只删记录、不删文件」**，且提示「文件以后放回来会重新入库」

## 7. 验收口径

**accept（自动）**

- 双重门槛：待处理的丢失（未忽略）**清不掉**（`changed=0`）
- 正常路径：已忽略的能清掉，`changed` 数正确，记录确实从库里消失
- 标签级联：清掉前后 `asset_tags` 对应行数归 0（外键级联生效）
- **磁盘零改动**：清掉后原 `abs_path` 所在目录内容不变（它本来就没有文件）
- **可恢复**：把文件重新写回原路径 → 再扫描 → 记录**重新出现**（证明"清掉≠数据丢失"）
- 幂等：对已清掉的 id 再清一次 → `changed=0`，不报错

**界面场景（missing 场景）**

- 已忽略行行尾有**两个**出口（撤销忽略 + 清掉记录）
- 点「清掉记录」弹二次确认；确认后该行消失
- 清掉后那张「未分版本 / 幽灵」不再出现
