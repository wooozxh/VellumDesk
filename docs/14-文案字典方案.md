## 3. 设计：`src/shared/copy.ts` 长什么样

### 3.1 文件形态

纯数据文件，嵌套对象，按**界面区域**分组（不是按源文件分组 —— 你要改的时候是按「顶栏 / 左栏 / 版本条」找的，不是按文件名找）。

```ts
/**
 * 软件全部界面文案 —— 改文案只改这个文件，不用动组件代码。
 *
 * 用法：  import { COPY, fmt } from '@shared/copy'
 *         COPY.top.search                  →  '搜索包名称…'
 *         fmt(COPY.pack.createdTip, { seq: 3 })  →  '已建第 3 稿'
 *
 * 三条规矩：
 *   1. {xxx} 是变量占位符，改文字时别删掉它
 *   2. 这里只放文案，不放任何逻辑
 *   3. 带 ⛔ 的别改 —— 那是磁盘目录名，改了软件找不到文件
 */

export const COPY = {
  // ==================== 通用 ====================
  common: {
    ok: '确定',
    cancel: '取消',
    save: '保存',
    close: '关闭',
    remove: '移除',
    retry: '重试',
    delete: '删除'
  },

  // ==================== 顶栏 ====================
  top: {
    searchPack: '搜索包名称…',
    searchFile: '搜索文件名…',
    viewPacks: '包视图',
    viewFiles: '文件视图',
    rescan: '刷新扫描',
    rescanTip: '重新扫描素材工作区',
    newPack: '新建任务包'
  },

  // ==================== 左栏 ====================
  side: {
    filterTags: '筛选标签',
    projects: '项目',
    all: '全部',
    loose: '待归类',
    looseTip: '这些包的文件夹直接躺在工作区根目录，还没选项目 —— 点包卡片右上角的入库按钮就能归位',
    unbound: '已解绑',
    unboundTip: '结项留底的项目：软件里不显示，本地文件全在 _已解绑的项目 里，可一键还原',
    ...
  }
  ...
}
```

### 3.2 编号（key）命名规则

`区域.用途`，全小驼峰：

| 例子 | 读作 |
|---|---|
| `top.searchPack` | 顶栏 · 搜索包 |
| `side.looseTip` | 左栏 · 待归类 · 悬停提示 |
| `version.bindTitle` | 版本条 · 绑定文件夹 · 标题 |
| `toast.packCreated` | 操作反馈 · 包已创建 |

编号**只增不改**：以后加文案就往后加，已发出的编号永远不动 —— 这样你手上那份旧表格任何时候都能用。

### 3.3 带变量的文案怎么表达

```ts
// 字典里（你看到的）
packCreated: '包「{name}」已创建，文件夹已建好',

// 代码里（我来写）
toast(fmt(COPY.toast.packCreated, { name: r.pack?.name }))
```

表格里就是 `包「{name}」已创建，文件夹已建好` —— 你改文字，`{name}` 原样留着。

## 4. 三类特殊情况的处理

### 4.1 简单变量（约 104 条）—— 正常抽

`${seq}` → `{seq}`，`${name}` → `{name}`。你照常改文字。

### 4.2 表达式复杂的（15 条）—— 抽成「文案函数」，单独标记

这类长这样：

```ts
`项目「${name}」已删除，${r.moved} 个包已${action.moveTo !== null ? '转移' : '变为待归类'}`
```

里面既有变量、又有代码逻辑。做法：**只把其中的固定中文抽出来**，逻辑留在代码里：

```ts
// 字典
project.deleted: '项目「{name}」已删除，{count} 个包已',
project.moved: '转移',
project.becameLoose: '变为待归类'
```

表格里这 15 条会标上 `⚠ 复杂`，旁边写明「这句由 3 段拼成，改完我确认拼起来通顺」。
→ **不需要你操心技术细节，照常填新文案即可。**

### 4.3 数据库种子数据（31 条）—— 单独一张表，你决定要不要改

`main/db.ts` 里有一批**新建数据库时的初始化数据**（不是界面文案）：

```
默认项目：集团通用 / 海南升学规划中心 / 海南升学初三集训营（含各自的一句话说明）
默认标签维度：物料类别 / 使用渠道 / 状态（含各自说明）
默认标签：海报 · 折页 · 详情长图 · 短视频 · 宣传片 · 直播物料 · 字体 · 图标素材 · 参考图
         公众号 · 朋友圈 · 视频号 · 抖音 · 线下门店 · 官网
         草稿 · 待审核 · 已交付 · 已归档
```

**关键区别**：这批只影响**以后新装的软件首次建库**，**你现在电脑上这个库完全不受影响**（要改现有库里的标签名，是在软件左栏「管理」里改，不走这里）。

所以单独做一张表 `Sheet2 · 默认数据`，你要改就填，不想动就留空。

## 7. 改完文案的连锁影响（重要，先讲清）

验收里有**一批断言是直接检查「某句话有没有出现」**的，例如：

```
accept.ts      ：!eBase.includes('视频') && !eBase.includes('推文配图') && ...
界面场景       ：ok(infoBannerText.includes('目录结构已升级'), ...)
                 ok(bannerText.includes('里面的东西一件没动'), ...)
```

你把「目录结构已升级」改成别的说法，这些断言会**集体报红**。

**这不是你把软件改坏了** —— 是断言没跟上。处理办法：

1. 我按新文案**逐条更新断言里的字面值**（保持断言强度不变，只换字，绝不改成「永远通过」）
2. 输出一份 **「因文案变更而更新的断言清单」** 给你过一眼（哪条、原来查什么、现在查什么）
3. 断言的**数量**只增不减（当前 619 项），不会靠删断言来「变绿」

> 这也是为什么建议「先抽字典 + 跑全绿，再改文案」：把「搬家」和「改字」两件事分开，
> 出问题时能一眼看出是哪一步引起的。

### 12.3 踩过的坑（都写进 README 了）

| 坑 | 表现 | 正解 |
|---|---|---|
| AI 沙箱批量删除护栏 | 场景/验收大面积假失败（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，`count` 按轮次累计） | 跑测试前 `CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=20000` |
| `core.autocrlf=true` | `git checkout` 把 CSS 写成 CRLF，构建产物比 LF 版大 2.5KB → 误以为样式被改 | CSS 属构建产物且不压空白，比对前统一去 `\r`；**换行符不是「用户看到的字」** |
| `mcporter` 是 sh 包装 | Node 里 `spawn` 它必失败（EBUSY / 非可执行）；`spawnSync` 在沙箱里一律 EBUSY | 起 `node <...>/mcporter/dist/cli.js`，且**用异步 spawn + argv 数组** |
| 临时诊断用「移动」而非「拷贝」 | 一次 `rmtree` + `move` 次序失误，把改造后的 `src` 整个吃掉了（详见 12.4） | 改源码树一律 `copytree`，不 `move`；改前先落受保护快照 |

### 12.4 一次真实的数据丢失与恢复（教训）

接线完成后做「前后对照」实验时，为了换成 HEAD 版本构建，用了
`rmtree(src)` → `move(src_after → src)` 的**移动**写法。该 `src_after` 实际上捕获的是
checkout 之后的状态，导致**改造后的 src 全量丢失**（未提交、未备份）。

恢复方式（约 40 分钟，全自动可复算）：

1. 用 `_junk/src_backup_before_rich`（Rich 接入前的全量副本，**字典接线 100% 完成**）重建 `src`
2. 重放 `codemod_rich2.cjs --write` → 重新接入 **38 处** `<Rich/>`（内建不变量自检：0 处未通过）
3. 重放 4 处手工编辑（`App.tsx` / `TagManagerModal` / `TagPanel` / `VersionModal`）的模板字面量
4. 重放 `copy.ts` 的 5 处字典值微调
5. 复验：未引用条目 0、等式证明 74/74、JSX 树比对 12/13（唯一 ❌ 是 Rich.tsx 自身）、
   accept 619 全过、9/9 场景、48 个屏幕状态逐字一致

**结论**：修复结果与丢失前**逐字等价**（`git diff HEAD -- src` = 22 文件 / 648 增 / 552 删，
与丢失前的 22 文件 / 644/575 同量级，差异来自这次走 codemod 而非手工补，渲染文字完全一致）。

**规矩（已写进 README）**：
> 改源码树只许 `shutil.copytree`，不许 `shutil.move`；动 `src` 之前先落一份受保护快照
> （本次快照：`_junk/src_SAFE_orig_backup`、`_junk/src_RECOVERED`）。

### 12.8 长期使用：表格是常驻控制台，不是一次性对账单

第一版表格交付时是「一次性对账单」——回填之后代码变了，表里的「现在的文案」就过期了。
现在改成**常驻控制台**：

- 落地之后跑一次 `node tools/copy-sheet/publish.cjs`：把 `copy.ts` 重新导出并覆盖写回**同一张表**，
  `现在的文案` 更新为最新值、`改成` 列清空。**文档链接永远不变**，收藏一个链接就够。
- 工具链收进项目：`tools/copy-sheet/`（`README.md` 写了完整流程），
  不再依赖 `_junk/proj_tmp` 那堆临时脚本。
- 每次循环：**表上改 → `pull` → `diff` → `apply --write` → 验收 → `publish`**。

**边界（表改不了的东西）**：磁盘目录名（`01-成品` / `_回收站`）、数据库状态值（`成品` / `未归属`）
不在字典里 —— 它们不是文案，改了软件会找不到文件。详见 `copy.ts` 文件头的三条规矩。
