## 0. 一句话

扫描时**发现文件没了，不删记录，改成打「文件已丢失」标记**；界面上能看见这些行、能一键重新定位，文件挪回来标记自动消失。

## 1. 为什么做

### 1.1 需求文档怎么写的

- **M8-03（P0）**：「失效检查：原文件被删除或移动后，标记为"文件已丢失"，并提供重新定位功能」
- **验收清单第 560 条**：「故意删除一条素材的原文件，软件能正确提示"文件已丢失"」

### 1.2 现在是怎么做的（正好反着）

`workspace.ts:805-815`（第 1 批就写成这样）：

```ts
// 5. 清理：磁盘上已不存在的记录 → 从索引里摘掉（但绝不删磁盘文件）
if (rootReadable) {
  const allKnown = db.prepare('SELECT id, abs_path FROM assets').all()
  const del = db.prepare('DELETE FROM assets WHERE id = ?')
  for (const a of allKnown) {
    if (!existsSync(a.abs_path)) del.run(a.id)
  }
}
```

**文件一丢，素材记录直接删掉**。后果：

1. 用户**永远不知道文件丢了**——行没了就是没了，无从对比
2. 更糟的是 `asset_tags` 有 `ON DELETE CASCADE`（第 7 批加的），记录一删，**标签关联跟着蒸发**——用户辛苦打的标签无声消失
3. 想重新定位？没有记录可以定位

### 1.3 为什么独立成批

`docs/08` §16 的原话：

> 需求文档写的是"标记为文件已丢失并提供重新定位"，而实现是**直接删素材记录**。
> 两者相反：**该删的包记录不删，该留的素材记录却删了**。
> 这一条要动 `assets` 表结构 + 文件视图 + 新增重新定位对话框，独立成批。

**第 7 批修了前半句**（包记录不再乱删，改为带留痕地摘），**这半句还欠着**——两件事是同一个母题的两面，第 7 批做完正好接上。

### 1.4 有一条老断言会被打脸（按规矩要先说明）

`accept.ts:481`：

```ts
ok(stillThere.c === 0, '手动删除的文件，扫描后从索引摘除')
```

这是第 1 批写的，与 M8-03 直接冲突。第 8 批要把它改成：

```ts
ok(stillThere.c === 1, '手动删除的文件，记录仍在（不再摘除）')
ok(stillThereRow.missing_at !== null, '并且被打上「文件已丢失」标记')
```

按 `docs/08` §13 的规矩，改老断言必须说明理由——理由就是需求文档 M8-03。

## 2. 设计

### 2.1 数据模型（迁移 8）

`assets` 表加**一列**：

```sql
ALTER TABLE assets ADD COLUMN missing_at TEXT   -- NULL = 正常；有值 = 这个时刻发现丢了
```

写法沿用迁移 4 的老套路（逐列判断，缺才补），并建部分索引：

```ts
// ---- 迁移 8：assets 加 missing_at（第 8 批：文件已丢失标记）----
const cols8 = d.prepare('PRAGMA table_info(assets)').all() as Array<{ name: string }>
if (!cols8.some((c) => c.name === 'missing_at')) {
  d.exec('ALTER TABLE assets ADD COLUMN missing_at TEXT')
}
d.exec(`
  CREATE INDEX IF NOT EXISTS idx_assets_missing ON assets(missing_at)
   WHERE missing_at IS NOT NULL
`)
```

**为什么不存"丢之前在哪"**：`abs_path` 本来就是原路径，不需要第二份。

**为什么不用 `missing` 布尔字段**：跟第 7 批解绑用 `archived` 一个道理——时间戳比布尔多一个信息（什么时候丢的，界面能显示"9-29 发现丢失"），成本一样。

### 2.2 扫描第 5 步重写：标记 / 恢复，不再删

**三道门**（与第 7 批 `cleanupMissingPacks` 的设计对称）：

| 门 | 判据 | 为什么 |
|---|---|---|
| 门一 | `rootReadable` 为真 | 安全阀。移动硬盘没插、网络盘断线 → 根读失败，**整段跳过**。不设这道门，拔一次硬盘全库变"丢失"——这是这类软件最致命的事故 |
| 门二 | 文件确实不在磁盘上（`!existsSync`） | 基本判据 |
| 门三 | 该素材**可见**（`VISIBLE_PACK_SQL`，即所属项目未解绑） | 解绑项目的文件夹在 `_已解绑的项目` 下，扫描本来就不扫那里。不豁免的话，**解绑当天那个项目几十条记录集体"丢失"** —— 与第 7 批"解绑即在软件里隐身"直接矛盾 |
| 门四 | 所属**包文件夹还在** | 包文件夹整个没了 → 交给第 6 步包清理统一处理（见 §2.3），不在这里标 |

**核心逻辑**：

```ts
const rows = db.prepare(
  `SELECT a.id, a.abs_path, a.missing_at, a.size, a.modified_at, k.folder_path
     FROM assets a LEFT JOIN packs k ON k.id = a.pack_id
    WHERE ${VISIBLE_PACK_SQL}`
).all()

const markLost   = db.prepare('UPDATE assets SET missing_at = ? WHERE id = ?')
const markBack   = db.prepare('UPDATE assets SET missing_at = NULL, size = ?, modified_at = ? WHERE id = ?')

let markedMissing = 0, restored = 0
db.transaction(() => {
  for (const r of rows) {
    if (r.folder_path && !existsSync(r.folder_path)) continue   // 门四：交给包清理
    const onDisk = existsSync(r.abs_path)
    if (!onDisk && r.missing_at === null) { markLost.run(ts, r.id); markedMissing++ }
    if (onDisk && r.missing_at !== null) {
      // 文件回来了（用户重新定位、或自己挪回来）→ 清标记，顺手更新大小/时间
      const st = statSync(r.abs_path)
      markBack.run(st.size, st.mtime.toISOString(), r.id); restored++
    }
  }
})()
```

**两个细节**：
- 标记只在 `NULL → 有值` 时写，避免每次刷新都把"丢失时间"刷成现在（时间戳要保留第一次丢的时刻）
- 文件回来了要**自动清标记**（不需要用户手动"取消丢失"），同时刷新 `size`/`modified_at`（内容可能换了）

`ScanResult` 加两个字段：`markedMissing: number`、`restored: number`。界面 toast 用得上。

### 2.3 与第 7 批「包记录清理」的交互（关键）

第 7 批：用户把**整个包文件夹**删了 → `cleanupMissingPacks` 摘掉包记录，留痕 `_system/backup/packs-<时间戳>.json`。

那包里的 N 条素材记录呢？现在 `assets.pack_id` 是 `ON DELETE SET NULL`，光删包记录会把它们**变成 pack_id = NULL 的孤儿**——第 7 批之前它们会先被第 5 步删掉，所以没暴露；第 8 批第 5 步改成"不删"之后，这个洞就露出来了。

**处理**：`cleanupMissingPacks` 摘包记录前，先把包内素材一并摘掉，**留痕 JSON 里补上文件清单**：

```json
{
  "at": "2026-09-29T...",
  "packs": [
    {
      "name": "海南招生海报-2026秋季",
      "folder_path": "D:\\素材工作区\\海南升学规划中心\\海南招生海报-2026秋季",
      "files": ["01-成品/海报终稿.png", "02-素材/底图.psd"]
    }
  ]
}
```

顺序：查文件清单 → 写留痕 → `DELETE FROM assets WHERE pack_id = ?` → 删包记录。整个动作在一个事务里。

**判据边界（互不打架）**：

| 情况 | 谁管 | 结果 |
|---|---|---|
| 包文件夹在、个别文件没了 | 第 5 步 | 素材记录**留**，打「已丢失」 |
| 包文件夹整个没了 | 第 6 步 | 包记录 + 包内素材记录一起摘，留痕带文件清单 |
| 项目已解绑 | 都不管（门三） | 记录原样不动，软件里隐身 |
| 根目录读失败 | 都不管（门一） | 整段跳过 |

### 2.4 界面

**文件行**（`FileRow.tsx`）：

- 丢失行加 `.missing`：整行压暗（opacity）+ 文件名后挂一个红色角标 `文件已丢失`
- 缩略图：`_thumbs` 下的缩略图是**独立文件**，原图丢了一般还能显示（正好帮用户认出丢的是哪张）；没有缩略图的图片读原图会拿到 `null` → 显示扩展名块，正好
- 双击文件名：不再调 `file:open`（必然报错），改成弹「文件找不到了」+ 引导重新定位
- 行尾按钮：`↗ 打开文件` 换成 `🔍 重新定位`（保留 📁 打开所在文件夹 → 但文件夹可能也没了，交给已有的错误提示）

**左栏「筛选」区**新增一个入口（与 `📥 未归属 N` 并列）：

```
📥 未归属           12
⚠️ 文件已丢失        3      ← 新增，只在 N > 0 时出现
📄 全部文件        168
```

点它 → 切文件视图 + 只看丢失的。**与项目筛选可叠加**（`listAssets` 的 where 本来就是叠加的）。

**包卡片**：文件数仍算上丢失的（记录还在），但如果有丢失，卡片角上挂个 `⚠ N` 小标；封面选取 SQL 加 `AND missing_at IS NULL`，避免封面指向一个读不出来的文件。

**扫描后 toast**：`本次扫描：2 个文件丢失、1 个文件找回`（只在有变化时提示，别打扰）。

### 2.5 重新定位

**单条**：
1. 行尾 `🔍 重新定位` → 系统文件选择框（`dialog.showOpenDialog`，已有先例）
2. 选中 → **校验**（§3.2 已定：文件名 + 扩展名 + 大小，三者全对）→ 通过则 `UPDATE assets SET abs_path=?, rel_path=?, file_name=?, size=?, modified_at=?, missing_at=NULL WHERE id=?`
3. 校验不过 → 明确告知哪儿不对（"文件名不同：期望 `海报终稿.png`，选中的是 `海报终稿-副本.png`"）

**边界：只允许指到工作区内的文件**。理由：`rel_path` 是"工作区相对路径"，指到工作区外这个字段就没意义了，而且下次扫描又会把这条记录标成丢失（扫描只遍历工作区），变成死循环。
用户选到工作区外的文件时，提示一句话：**「这个文件在工作区外面。要不要把它搬回工作区原位置 `01-成品/海报终稿.png`？」** —— 一键搬回来（`renameSync`，复用第 6 批的搬运核心），比让用户自己挪更顺手。

**批量**（已拍板：做，先预览再确认）：整个文件夹被搬走的情况（用户在资源管理器里挪了目录）。

设计：选一个目录 → 对每条丢失记录按 `rel_path` **逐级降级**匹配：

```
原 rel_path: 海南升学规划中心/海南招生海报-2026秋季/01-成品/海报终稿.png
用户选的目录: E:\备份\2026秋季
① E:\备份\2026秋季\海南升学规划中心\海南招生海报-2026秋季\01-成品\海报终稿.png   ← 完整结构
② E:\备份\2026秋季\海南招生海报-2026秋季\01-成品\海报终稿.png                     ← 去掉项目层
③ E:\备份\2026秋季\01-成品\海报终稿.png                                          ← 只剩组名
④ E:\备份\2026秋季\海报终稿.png                                                  ← 只有文件名（最宽松，最危险）
```

**先预览再落库**：弹一个列表，逐条显示「记录 → 匹配到哪个文件 / 没匹配上」，用户勾选后才执行。绝不静默批量改路径。

## 3. 用户拍板（2026-09-29，四项均按推荐执行）

### 3.1 包文件夹整个被删 → 包记录 + 包内素材记录一起摘，留痕带文件清单

- **✅ 甲（拍板）**：包记录 + 包内素材记录**一起摘掉**，留痕 JSON 补上文件清单。理由：用户删的是整个包，意图明确；留痕里能查账，不会真的"丢信息"
- **放弃 乙**：只摘包、包内素材标记为「已丢失」留着 —— 库里会堆一堆 `pack_id` 悬空的"丢失素材"，跟普通丢文件混在一起，用户分不清"我删了整包"和"我挪走了一个文件"

### 3.2 重新定位匹配：文件名 + 扩展名 + 大小，三者全对才接受

- **✅ 乙（拍板）**：三者都对上才接受。理由：大小相同能挡住"选错文件"的绝大多数误操作，且不用读文件内容（快）
- **放弃 甲**：只要文件名对上就接受 —— 太宽松，选中同名文件也能过
- **放弃 丙**：算内容指纹（SHA-256 前 1 MB）—— 大文件慢，且指纹是 M8-02「重复文件检测」的地盘，不该提前引进来

### 3.3 批量重新定位：做，先预览再勾选落库

- **✅ 甲（拍板）**：做，但**必须先预览匹配结果、用户勾选后才落库**。价值大（整个项目文件夹被手动搬走、换盘整理时一次解决），风险靠"预览 + 勾选"控制
- **放弃 乙**：只做单条 —— 用户真遇到"我把整个文件夹挪了个位置"时要一条条点几十次

### 3.4 统计口径：条数算、容量不算

- **✅ 甲（拍板）**：
  - 「全部文件 N」**算**（记录还在，另给提示"其中 N 条文件已丢失"）
  - 容量统计**不算**（文件已经不在本地占空间了，算进去会让"占用 X GB"虚高，误导用户去清理）
  - 包卡片文件数**算**（另挂 `⚠ N` 角标）
- **放弃 乙**：全都算（占用虚高）
- **放弃 丙**：全都不算（等于让丢失的素材在统计上"不存在"，与"记录留着"矛盾）

## 6. 验收检查点

### 6.1 新增 `[27]` 段（计划 40+ 条）

**标记与恢复**
- 删一个文件 → 扫描 → 记录仍在、`missing_at` 有值、包内其它文件不受影响
- 再扫一次 → `missing_at` **时间戳不变**（不刷新）
- 把文件放回去 → 扫描 → `missing_at` 清空、`restored` 计数对
- 文件**换了个内容**放回去 → `size` / `modified_at` 跟着更新

**四道门**
- 【门一】根目录读失败 → 一条都不标（回归第 7 批的安全阀断言）
- 【门三】解绑项目下的文件"消失" → **不标丢失**（回归钉子，防第 7 批语义被推翻）
- 【门四】包文件夹整个删 → 记录由包清理摘掉（不是标记），留痕 JSON 里有文件清单；包里素材记录数为 0，**没有 pack_id 悬空的孤儿**

**标签关联**
- 文件丢失 → `asset_tags` 关联**一条没少**（这是本批最大的收益：以前直接蒸发）
- 重新定位后 → 标签还在

**重新定位**
- 单条：选对文件 → 路径改对、`missing_at` 清空、`rel_path` 重算、标签还在
- 单条：选错文件（大小不符）→ 拒绝 + 明确原因
- 单条：选到工作区外 → 拒绝并提示（或按拍板结果搬回来）
- 批量：逐级降级匹配对（构造 4 种层级各命中一条）+ 预览列表条数对 + 勾选后只落勾上的
- 幂等：重新定位后再扫描 → 不再次标记丢失

**统计口径**
- `countMissing()` 与文件视图 `missingOnly` 条数相等（第 7 批教训：**筛选器数字必须与筛选结果严格一致**）
- 容量：丢失的不计入（按拍板结果）
- 包卡片 `fileCount` 含丢失、`missingCount` 正确

## 7. 已知代价与风险

1. **记录会堆积**：用户真的不要某个文件了（不打算找回来），记录会一直留着打"丢失"标记。**本批不做"删除记录"入口**（那又是一套确认流程），先看实际使用情况；真需要时下一批加。

4. **容量口径变化会打脸旧断言**：`assetTotals` 的 size 口径改写后，第 7 批那条"总容量"断言可能数字变化——**要提前确认它是怎么写的**，改了要说明理由。

## 10. 实际落地时的三个发现（2026-09-29 施工中）

### 10.1 claimFiles 是全项目最后一个"靠重扫兜底"的搬运点（第 1 批老 bug）

方案阶段没料到：把第 5 步从"删"改"标"之后，**认领（A-09）立刻露馅** ——
它搬完文件只调 `scanAll`，不重写路径。以前靠第 5 步把旧路径的记录删掉兜底；
现在旧记录留着打"丢失"标记，新路径又登记成一条新记录 → **一条文件两条记录**，
而且旧记录 id 一没，`asset_tags`（ON DELETE CASCADE）把认领前打的标签全带走。

修法与第 7 批 `movePackTo` 同一规矩：搬完立刻在**原记录上**重写 abs_path / rel_path /
pack_id / role，再 scanAll。全项目 6 处搬运点早就都用了 `reprefixPaths`，只有它漏网。

### 10.2 "重新定位撞 UNIQUE"不是异常，是常态

用户把文件挪到**工作区内**的新位置后，那一轮扫描已经把它登记成一条新记录
（未归属、多半没标签）—— 新路径被占住，`relocateAsset` 直接 UPDATE 必撞 UNIQUE。
处理：把占用者身上可能有的标签转挂到老记录（`INSERT OR IGNORE INTO asset_tags ... SELECT`），
删掉占用者，老记录改路径。一条文件永远一条，标签一张不丢。
accept [27] 有专门断言钉住这个合并行为。

### 10.3 老库加列时，索引不能放进建表段

`CREATE INDEX ... ON assets(missing_at)` 写在建表段的话，**老库**（表已存在，
CREATE TABLE IF NOT EXISTS 跳过）跑到这句时列还没被迁移 8 ALTER 出来 →
`no such column`，openDb 直接崩。索引挪到迁移 8 的 ALTER 之后建。
