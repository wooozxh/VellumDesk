## 2. 总体设计

### 2.1 数据流向（只读起步）

```
企微审批（同事提交）
   │  企微官方自动同步（与我们无关，已在跑）
   ▼
智能表格 · 两个子表（同事实时维护；设计人/项目列人工填）
   │  软件点「同步」时，wecom-cli 只读拉取（异步，绝不写表）
   ▼
本地 SQLite · tickets 工单表（子表+编号 幂等入库）
   │  派给本机使用者 & 状态∈{审批中,已通过} & 新单（首次同步快照之后出现的）
   ▼
自动新建任务（复用 createPack：建文件夹 + V1 + 三组）
   │  设计师照旧往任务里丢物料文件、入库
   ▼
工单面板：这张单 → 哪个任务 → 物料齐不齐、状态到哪了
```

### 2.2 三条核心规则

**① 唯一键 = 审批单编号（单键）；sheet_id 只是"出生地"属性。**（2026-10-01 修订，原设计为「子表+编号」组合键——但用户明确**会重新拉表**，sheet_id 一变组合键全部失配：旧单被当成新单进来一遍、甚至重复建任务。编号经 257 条实测表内跨表零重复，本身够格当唯一键。）规则：同编号 = 同一张单（更新，含更新其 sheet_id 出生地）；**同一批数据里同编号出现两行**（人工改错/真重复）→ 两张都收、标「编号重复」警告，绝不悄悄合并。

**② 本机身份 = wecom-cli 的授权身份。** 每台机器装 CLI 时授权一次（登自己的企微账号），软件读出授权身份（userid + 姓名）作为"这台机器是谁"。**工单建任务的唯一条件链**：

> 设计师(userid) = 本机身份(userid) **且** 状态 ∈ {审批中, 已通过} **且** 不是历史单 **且** 不在「待确认」里（§2.2 ④）

（2026-10-01 用户拍板修正：原门槛"已通过才建"是错的——审批流两道，**一审通过就开工**，二审通过时活已经干完了；所以单子**提交进审批中就该建任务**。已驳回/已撤销不建。）

**状态流转的处理**（任务建了之后状态变了）：

| 表里状态变化 | 软件 behavior |
|---|---|
| 审批中 → 已通过 | 正常完结：徽标更新为已通过，任务照旧（活干完了） |
| 审批中 → **已驳回 / 已撤销** | 工单标灰 + 徽标更新，**任务与文件完整保留**（中途变故/需求取消/业务调整，设计师做到一半的东西也是劳动成果——2026-10-01 用户拍板"全部保留"）。工单面板在关联任务旁**纯告知**「审批已驳回/撤销，任务及文件已保留」——软件只报告事实，不引导删除；真要删由人自己在任务视图手动删 |

别人的单、未指派的单：**工单列表可见、不建任务**——全局可见性本身有价值（谁没开工一眼看到），磁盘上只长自己的任务。

**③ 历史单 = 首次同步快照时已在表里的单（2026-10-01 加固，替代原"启用时间打点"方案）。** 软件连真表的**第一次同步**看到的全部记录（当前 257 张），无差别整体标「历史单」，**一张任务都不建**；之后的同步里**新出现**的编号（本地库从未见过）才参与建任务判定。工单详情里留一个「为这张单补建任务」手动按钮兜底（万一有一张旧单真要做）。

> 为什么弃用"启用时间打点"：按提交时间和启用时间比大小，存在边界算不清的情况（如打点前提交、打点后才审批通过的单）。快照规则**没有边界**——第一次看见你就是旧的，判定键就是"编号是否在本地库见过"，与幂等机制同源，零新增逻辑，**表里也不需要加任何标记列**（加列 = 同事每单都得记得打标记，忘打就漏单，比自动判定更危险）。
>
> 用户核心顾虑（2026-10-01 原话大意）："很怕开发完那一刻，表里所有旧工单全部被建成任务。"——快照规则直接消除该风险，且开发期自动测试全喂假数据、真表不进测试（§4.3），人工验收首连真表时快照规则已生效。

**④ 重新拉表（子表重建）不破坏任何本地数据。**（2026-10-01 补，用户预告"以后会重新让审批同步到智能表格"；同日按用户"怕复杂出 bug"的反馈，把原"确认弹窗"方案**简化为"待确认"降级**）

- **匹配只认审批编号**：新表里旧编号进来 → 本地按编号查到"见过" → 原地更新（含出生地 sheet_id），任务、历史标记、任务关联**原封不动**
- **子表重建 → 新单一律不自动建任务（简化版防护）**：同步时按**标题**识别子表（sheet_id 只当缓存指纹）；标题对上但 sheet_id 变了 = 检测到重建 → **数据照常收**（旧编号原地更新，无重复），**但本次新出现的编号全部标「待确认」、不进建任务判定**；工单面板给「确认这批新单」批量按钮，用户点过才按正常规则判定建任务。设计取向：宁可不建（多点一下），绝不误建（多出任务文件夹）——出错方向是安全的
- **本地有、新表没有的编号**：留底标「已不在表中」，已建任务绝不删
- 一句话：**编号是身份证，子表只是住址——搬家不换人；换了住址，新面孔先站着，等户主点头**
- 配套纪律（用户已认）：**非必要不重新拉表**；真要重拉，先在软件里点完一次同步再操作

### 2.3 多机协作模型（单机软件的本质不变）

- 每台电脑的软件各拉各的、各建各的本地任务，机器之间不通信
- **表格就是跨机器的汇总层**：A 标了状态写回（二期）→ 表里更新 → B 同步后可见
- 同事用上工单功能的三步：装软件 → 装 CLI + **登自己的账号**授权一次 → 表格管理员把他加进文档成员（只看单给"可阅读"，要标印刷状态的给"可编辑"）
- 纪律：**一人一号授权**。谁拿别人的账号授权，那台机器就"变成"别人，派单会派错

## 4. 同步引擎

### 4.1 触发时机

一期：**手动**——工单面板「同步」按钮。二期候选：启动时自动拉 + 每隔 N 分钟定时（企微没有免费推送，不做实时指望）。

### 4.2 拉取流程（一次点同步）

1. 异步 spawn wecom-cli（**异步是硬规矩**：沙箱 spawnSync 全 EBUSY，正式应用也不该阻塞主进程）——先 `sheets list` 拿子表清单做**结构校验**（按标题识别启用的子表；标题对上但 sheet_id 变了 → 本次同步标记 `structure_changed=true`，见步骤 3），再逐个启用的子表翻页拉全量记录
2. 按「审批单编号」upsert 进 `tickets`：本地见过该编号 → 更新可变字段（含出生地 sheet_id、record_id）；本地没见过 → 插入。**重新拉表时旧编号原地更新，任务/历史标记/关联不动**（§2.2 ④）
2.5 **首次同步快照**：若 `ticket_first_sync_done` 未置位 → 本次拉到的**全部记录**标 `is_history=1`（一张任务都不建），然后置位；已置位 → 跳过。之后任何同步里"新出现"的编号才可能是新单
3. **建任务判定**（仅新插入或设计人从空变有的单）：先看 `structure_changed`——**若本次检测到子表重建，新插入的单全部跳过建任务判定、标「待确认」**（§2.2 ④，工单面板「确认这批新单」批量放行）；否则满足条件链（§2.2 ②）→ 调现有 `createPack` 建任务（项目按 `project_name` 匹配 `projects.name`；匹配不上 → 落「待归类」+ 工单标「项目未匹配」）
4. **改派检测**：已有 `pack_id` 的单，设计人变成别人 → **不删任务**（铁则：不悄悄动用户的东西），工单标「已改派给 XX」
5. **删行处理**：表里某行没了（record_id 消失）→ 工单**留底标「已在表中删除」**，关联任务不动——留痕不删，同"文件丢了不删记录"的口径
6. 同步结果 toast：新增 N 张 / 建任务 M 个 / 改派 K 张 / 警告若干

### 4.3 可测试性设计（硬要求）

同步核心写成**纯函数 + 可注入数据源**：`applySync(records, config, identity)` 不碰网络，wecom-cli 只是一个"给记录的适配器"。accept 断言全部喂假数据；真企微只在人工验收时点一次。**真实外部依赖不进自动测试**。

### 4.4 异常处理（每一种都要有明确出口）

| 异常 | 表现 | 处理 |
|---|---|---|
| 授权过期（850003） | CLI 返回明确错误码 | 界面弹「企微授权已过期，请在企业微信里重新授权」+ 指引；本次同步中止，本地数据不动 |
| CLI 未安装/未授权 | spawn 失败 / 身份读不出 | 工单面板降级提示「本机未配置企微同步」，其余功能不受影响 |
| 表列改名/删除 | 映射的列拉不到 | 缺失列置空 + 同步结果带「字段缺失：XXX」警告，**不崩不中断**（raw_json 里有原始数据） |
| 同子表编号重复 | upsert 撞键 | 两张都收、标「编号重复」，绝不静默合并 |
| **重新拉表（sheet_id 变化）** | 结构校验发现标题对上但 sheet_id 变了 | 数据照常收，**新出现的编号全标「待确认」不建任务**，面板「确认这批新单」批量放行（§2.2 ④ 简化版） |
| 网络失败/超时 | CLI 超时 | 报错重试，本地数据不动 |

## 5. 数据库设计（迁移 10）

```sql
CREATE TABLE IF NOT EXISTS tickets (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  sheet_id   TEXT NOT NULL,      -- 出生地属性（当前 'tlD2Vr' 印刷 / 'tlzJfN' 电子；重新拉表会变，只更新不参与唯一性判定）
  ticket_type TEXT NOT NULL,     -- 'print' 印刷 / 'digital' 电子
  ticket_no  TEXT NOT NULL,      -- 审批单编号
  record_id  TEXT,               -- 企微记录 id（删行判定）
  -- 业务字段（§3 映射，全可 null）
  title TEXT, approval_state TEXT,
  applicant_userid TEXT, applicant_name TEXT, department TEXT,
  purpose TEXT, size_text TEXT, print_qty INTEGER,
  material_form TEXT, use_scene TEXT,
  due_date TEXT, submit_time TEXT, done_time TEXT,
  remark TEXT, source_url TEXT, approval_url TEXT,
  receiver_name TEXT, receiver_phone TEXT, deliver_date TEXT,
  designer_userid TEXT, designer_name TEXT, project_name TEXT,
  reviewer_names TEXT, material_category TEXT,  -- §3.1 物料审核人 / 物料类别
  raw_json TEXT,                -- 原始 values 快照（后补字段不用重拉）
  dup_json   TEXT,              -- 撞号时第二份记录的原文（两份都留，绝不悄悄合并）
  -- 同步状态
  first_seen_at TEXT, last_sync_at TEXT,
  is_history INTEGER DEFAULT 0, -- 历史单：首次同步快照时已在表里的（永不建任务）
  dup_warn INTEGER DEFAULT 0,   -- 编号重复警告
  reassigned_to TEXT,           -- 改派：后来的设计人
  row_gone INTEGER DEFAULT 0,   -- 表里这行被删了（留底）
  need_confirm INTEGER DEFAULT 0, -- 子表重建后的新单：待用户确认才参与建任务（§2.2 ④）
  pack_id INTEGER,              -- 建了任务后的关联（任务删了置 NULL）
  print_status TEXT,            -- 二期：印刷状态（本地值，写回表）
  UNIQUE(ticket_no)              -- 唯一键=审批单编号（§2.2 ①）；同批撞号两张都收、标 dup_warn
);
```

配置存 `meta` 表（工单配置跟工作区走，不进全局配置）：`ticket_docid` / `ticket_sheets`（启用的子表与类型映射 JSON，**以子表标题为主键、sheet_id 为缓存指纹**）/ `ticket_identity`（本机 userid+姓名，读自 CLI）/ `ticket_first_sync_done`（首次同步快照是否已做——做过之后新出现的编号才算新单）。
