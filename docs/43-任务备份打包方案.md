# 第 58 批 · M8-04「任务备份打包」—— 细化方案

> 状态：**已拍板（2026-10-10），待施工**

## 0. 一句话

在任务视图给任务打「备份包」：多选若干任务，各打一个原样 zip 到指定目录；  
打完的任务标记「已备份」，之后任务内的文件**随便删**——软件不再报「文件丢失」。

---

## 1. 为什么做

### 1.1 需求文档怎么写的

**M8-04（P0）一键备份**：把素材库整体备份出去，便于归档与灾难恢复。

前面几轮试过两条路，都放弃了：

| 试过的路                  | 为什么放弃                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------ |
| 百度网盘「同步空间」            | 是**双向镜像**：本地删 = 云上删，语义上根本不是备份                                                                    |
| 百度网盘「自动备份该文件夹」        | 实测卡在「正在请求中」；且同一目录被两条产品线同时管，产生一堆 `(1)` 副本                                                         |
| FreeFileSync / rclone | 能跑，但要用户理解 `Update`/`Mirror`/`copy`/`sync` 的差别，门槛高；rclone 官方已移除百度网盘后端（`rclone.org/baidu/` 返回 404） |

**用户最终定的路子**：备份这件事**拆成"软件管一半、人管一半"**——  
软件负责「把任务打成包」，人负责「把包传到网盘」。这样软件不碰任何网盘协议，  
既没有同步语义的坑，也不受网盘客户端改版影响。

### 1.2 现状：引擎已有，但语义不同

项目里**早有一整套打包引擎**（第 15 批 M5 交付打包）：

- `src/main/exportPack.ts` —— `buildPackExportPlan()` / `executePackExport()`  
  （zip 生成、文件名清洗、重名去重、防崩的空窗期 error 监听，全踩过坑了）
- `src/renderer/src/components/PackExportModal.tsx` —— 打包选项面板（版本/分组/命名模板/结构预览）

**但它不能直接拿来做备份**，两者是三件不同的事：

|          | 交付打包（已有）                        | 备份打包（本批）             |
| -------- | ------------------------------- | -------------------- |
| 目的       | 把成品交给客户                         | 把整份存档留底              |
| 包内结构     | **改名 + 按成品/素材/工程重排**            | **原样**（原始目录层级、原始文件名） |
| 谁打包      | 一次一个任务                          | **一次多个任务**           |
| 打完的副作用   | 写 `delivery_records`、把版本标成「已交付」 | 标记「已备份」，**不写交付记录**   |
| 打完后的本地文件 | 照旧留着                            | 用户可以全删掉              |

**关键决定：备份打包走独立代码路径，绝不复用 `executePackExport`。**  
理由：`executePackExport` 会写 `delivery_records` 并把版本 `delivered_at` 置上，  
界面就挂出「已交付」徽标——那是给客户交付用的。备份要是混进去，  
以后用户分不清"这任务交付出去了没有"。

### 1.3 为什么独立成批

要动：`packs` 表结构（迁移 21）、扫描的丢失标记逻辑（加一道门）、  
任务视图工具条 + 卡片多选态 + 新组件、新增一条批量打包 IPC。  
四块都动，且第 3 点直接改第 8 批（M8-03）的核心判定，独立成批。

## 2. 设计

### 2.1 全流程

```
【人】网盘上按 工作区/项目 两级建空目录，根目录挂设计师姓名后缀
   │   （软件完全不介入；以后把 zip 丢进对应项目目录）
   ▼
【软件】任务视图 → 点「备份打包」→ 全部卡片进入打勾模式
   │                                    （按钮变「批量打包」，旁边冒「取消」）
   ▼
【软件】勾选要备份的任务 → 点「批量打包」→ 系统目录选择框
   │
   ▼
【软件】每个任务各打一个 zip，输出成：
          <所选目录>/<项目名>/<任务名>-backup.zip
   │
   ▼
【软件】成功的那几个任务：写 backed_up_at → 卡片置灰 + 挂「已备份」徽标
          → 顺手清掉该任务里残留的「文件丢失」标记
   │
   ▼
【人】手动删任务里的文件（任务文件夹本身留着）
   │
   ▼
【软件】下次扫描：已备份任务**整任务豁免**，文件没了也不进「文件丢失」
```

### 2.2 数据模型（迁移 21）

`packs` 表加**两列**（幂等：缺列才 ALTER，与迁移 8/9/13/17/18/19 同一模式）：

```sql
ALTER TABLE packs ADD COLUMN backed_up_at TEXT   -- NULL = 未备份；有值 = 最近一次备份成功的时刻
ALTER TABLE packs ADD COLUMN backup_path  TEXT   -- 最近一次备份 zip 的绝对路径（详情弹窗展示用）
```

- **为什么用时间戳不用布尔**：跟 `missing_at` / `delivered_at` 一个道理——  
  时间戳多一个信息（什么时候备的），成本一样，界面能显示「已于 10-10 14:30 备份」。
- **为什么记 `backup_path`**：用户包删了/挪了之后能告诉他上一次打哪去了。  
  这只是"记录"，不是"保证"——路径失效时界面要能优雅降级（文件不存在就不给跳转）。

⚠️ 与迁移 8 同一个坑：**索引不能写进建表段**（老库建表被 `IF NOT EXISTS` 跳过，  
索引那句会跑在 ALTER 之前 → `no such column` 崩库）。本批加的列**不需要索引**  
（查询都是按 `pack_id` 走，已有 `idx_assets_pack`），所以没有这个问题，但仍需注意别手滑加。

### 2.3 后端：备份打包（新建 `src/main/backupPack.ts`）

**为什么新建文件而不是塞进 `exportPack.ts`**：见 §1.2——语义完全不同。  
放一起以后必然有人误调用。新文件只依赖 `archiver` 与 db。

```ts
export interface PackBackupInput {
  packIds: number[]
  outputDir: string
  suffix: string          // 默认 '-backup'
}

export interface PackBackupItemResult {
  packId: number
  packName: string
  ok: boolean
  outputPath?: string
  fileCount?: number
  totalSize?: number      // zip 实际大小
  error?: string
}

export interface PackBackupResult {
  items: PackBackupItemResult[]
  okCount: number
  failCount: number
}
```

**单个任务的打包步骤**：

1. 取 `pack.folder_path`。**目录不存在或里面一个文件都没有** → 记 `error: 空任务` 跳过  
   （不阻断其它任务，最后汇总里报）
2. 算输出路径：
   - 项目名 = `pack.projectName`，为空时用常量 `未归类`（新增文案）
   - 目录名与文件名都过 `sanitizeFileName()`（**复用 `exportPack.ts` 里那个**——  
     它踩过坑：`10*1000cm` 的星号会把 `createWriteStream` 干成 ENOENT 且崩软件）
   - 完整路径：`<outputDir>/<项目名>/<任务名><suffix>.zip`
   - 重名 → `uniqueFileName()`（**同样复用**，`xxx-backup (1).zip`）
3. `mkdirSync(dirname, { recursive: true })`
4. **原样打包**：`archive.directory(packFolder, 任务名)`
   - 第二参数传任务名 → zip 内**顶层套一个任务名文件夹**，解压不散落
   - `filter` 排除 `_` / `.` 开头的条目（`_thumbs` 之类，与 `collectFiles` 同一规则）
   - **不做任何重命名、不重排目录、不按版本分层** —— 这就是"原样"
5. 沿用 `exportPack.ts` 那套**防空窗期崩软件**的写法：  
   `createWriteStream` 之后**同步**挂 `error` 监听（挂晚了 = 无监听的 error = uncaughtException）。  
   失败时 `unlinkSync` 清掉半成品 zip。
6. 成功 → 在**一个事务**里：
   - `UPDATE packs SET backed_up_at = ?, backup_path = ? WHERE id = ?`
   - `UPDATE assets SET missing_at = NULL, missing_ignored_at = NULL WHERE pack_id = ?`  
     （备份前就丢了的文件，备份后不该继续挂"丢失"——任务已经整份存下来了）
7. **确保封面有缩略图缓存**（见 §2.7）
8. **绝不写 `delivery_records`、绝不碰 `pack_versions.delivered_at`**

**批量执行**：串行循环（`for...of` + `await`），一条失败继续下一条。  
不并行——同时开几个 `archiver` 会抢磁盘 IO，且失败面变大。

**进度**：先不做逐条进度推送（见 §8）。界面一个 busy 态 + 结束汇总 toast。

### 2.4 后端：扫描加「门五」（`workspace.ts markMissingAssets`）

现有 `markMissingAssets(rootReadable)`（`workspace.ts:1145`）已有四道门：  
门一 根目录可读、门二 文件确实不在、门三 项目未解绑、门四 包文件夹还在。

**加第五道门：所属任务已备份 → 整任务豁免。**

改动很小，就在查询里多带一列：

```ts
const known = db.prepare(
  `SELECT a.id, a.abs_path, a.missing_at, k.folder_path, k.backed_up_at
     FROM assets a
     LEFT JOIN packs k ON k.id = a.pack_id
    WHERE ${VISIBLE_PACK_SQL}`
).all() as Array<{ /* ... 加 backed_up_at: string | null */ }>
```

循环里，**放在门四之后**：

```ts
for (const a of known) {
  if (a.folder_path !== null && !existsSync(a.folder_path)) continue  // 门四
  if (a.backed_up_at !== null) continue                               // 门五：已备份，豁免
  ...
}
```

**为什么是"整任务豁免"而不是"只豁免备份时刻的文件"**：按用户拍板（§3.2）。  
实现上简单一个 `continue`，且完全符合实际用法——备份是任务的**收尾动作**，  
之后就是删文件腾空间，不会再往回加。

**注意**：门五**只挡"打标记"，不影响"清标记"**。  
已备份任务里不会产生新标记；而备份动作本身已经顺手清了一遍（§2.3 第 6 步）。

**回归钉子**：未备份的任务一切照旧——这条必须有断言，防止门五写宽了把 M8-03 废掉。

### 2.5 界面：批量备份模式

**工具条**（`App.tsx:1114`，「新建任务」按钮后面）：

```tsx
{!backupMode ? (
  <button className="btn" onClick={() => { setBackupMode(true); setBackupSel(new Set()) }}>
    <Icon name="archive" size={13} /> {COPY.backup.enter}
  </button>
) : (
  <>
    <button className="btn primary" disabled={backupSel.size === 0 || backupBusy} onClick={doBackup}>
      {backupBusy ? COPY.backup.packing : fmt(COPY.backup.doBatch, { n: backupSel.size })}
    </button>
    <button className="btn" disabled={backupBusy}
      onClick={() => { setBackupMode(false); setBackupSel(new Set()) }}>
      {COPY.common.cancel}
    </button>
  </>
)}
```

新增 state：`backupMode` / `backupSel: Set<number>` / `backupBusy`。

**进入模式时**：顶部或工具条下方出一条提示条 `COPY.backup.selectHint`（"勾选要备份的任务"），  
避免用户不知道现在点卡片是勾选而不是打开。

**卡片**（`PackCard.tsx`）加四个可选 props：

| prop         | 作用                                |
| ------------ | --------------------------------- |
| `selectable` | 左上角显示勾选框；**整卡点击 = 切换勾选**（不再开详情）   |
| `selected`   | 勾选态样式                             |
| `backedUp`   | 已备份 → 挂 `.backed-up`（置灰）+ 「已备份」徽标 |
| `backupTime` | 徽标悬停提示里显示备份时间                     |

**必须保留一个「打开详情」的口子**：多选模式下卡片点击是勾选，  
但用户可能想先看看任务里有啥再决定备不备。方案：多选模式下，  
卡片原有的编辑按钮区域**保留**，另加一个"眼睛"按钮 → 单独打开详情弹窗。  
（不做也行，用户可先退出模式看完再进来——先按"保留编辑按钮 + 眼睛按钮"实现，更顺手。）

**打包流程**：

```ts
const doBackup = async (): Promise<void> => {
  if (backupSel.size === 0) { toast(COPY.backup.noneSelected, 'err'); return }
  const picked = await window.api.pickOutputDir('')            // 复用已有通道
  if (!picked.ok || !picked.dir) return
  setBackupBusy(true)
  const res = await window.api.packBackupBatch({
    packIds: Array.from(backupSel), outputDir: picked.dir, suffix: '-backup'
  })
  setBackupBusy(false)
  toast(汇总文案, res.failCount > 0 ? 'info' : 'ok')
  await reloadAll()                    // 刷新卡片（置灰 + 徽标）
  setBackupMode(false)
  setBackupSel(new Set())
}
```

只是文件在磁盘上没了——详情里给一句说明即可，不做特殊渲染。

### 2.7 封面与缩略图（第 4 点）

**结论：不需要额外复制成品原图，只要确保封面图的缩略图缓存存在。**

理由（这是调研后的优化，与用户原始设想效果一致但更干净）：

1. 卡片封面取的是 `coverPath = thumb_path || abs_path`（`workspace.ts:3155`）
2. 缩略图缓存是**独立文件**（`_thumbs/*.webp`），项目一贯**不删缩略图缓存**  
   （见 `workspace.ts:3429` 注释）
3. 备份后文件被删，但门五让 `missing_at` 保持 NULL →  
   封面 SQL（`workspace.ts:3122`，带 `missing_at IS NULL`）**仍能选中这条 asset**
4. 于是只要这条 asset 的 `thumb_path` 有值且缓存文件在 → **卡片照常有图**

**所以本批要做的只有一件事**：备份成功时，挑出"将来会当封面"的那张图  
（复用封面 SQL 的排序规则：成品优先），调 `ensureThumb()`（`thumbs.ts:124`）  
确保缓存生成，并把 `thumb_path` 写回 `assets`。

- 挑不到图（任务里没有任何可做封面的文件）→ 卡片显示占位图标，正常
- 生成失败 → 同上，不阻断备份

**为什么不复制原图**：复制一份 PSD 可能几十上百 MB，而缩略图通常几百 KB；  
用户要看成品有两条路——网盘上的 zip、或 `_thumbs` 里的缩略图。  
占空间且污染任务文件夹的复制方案，收益不值。

## 3. 用户拍板（2026-10-10，四项均按推荐执行）

### 3.1 zip 内结构：**原样打包**

保留任务文件夹的原始目录层级与原始文件名。备份就该是"原封不动的一份"，  
将来从 zip 里取文件不会认不出。  
**放弃**：复用交付打包那套改名 + 按成品/素材/工程重排（包内结构与本地不一致，取文件要对照）。

### 3.2 丢失豁免范围：**整个任务豁免**

只要任务有「已备份」标记，任务内任何文件丢失都不报警、不置灰。  
**放弃**：只豁免备份时刻已有的文件（更严谨但要留一份"备份时刻文件清单"，复杂且不符用法）。

### 3.3 输出目录组织：**按项目自动分目录**

输出成 `<所选目录>/<项目名>/<任务名>-backup.zip`，正好对应网盘的项目目录，  
可以整个文件夹直接拖上去。  
**放弃**：全部平铺在一个目录（之后要手动分拣）。

### 3.4 缩略图：**保留**（实现上优化为"保留缩略图缓存"，见 §2.7）

卡片继续有图，一眼认得出是哪个任务。  
**放弃**：不留、显示统一占位图标。

## 8. 明确不做（本批）

- **网盘上传 / 任何云盘协议**：用户明确要"软件管一半、人管一半"，本批只做本地打包
- **定时自动备份**：手动触发（与用户给的流程一致）
- **逐条打包进度推送**：先一个 busy 态
- **重新备份覆盖原 zip**：一律生成新文件
- **「取消已备份标记」入口**：用户要重新启用任务时，重新备份一次即可（刷新时间）
- **自动检测"备份后又改了"**：见 §7.1
- **清理历史备份 zip**：见 §7.3
- **单个任务右键备份**：本批只做批量入口
- **M8-04 的其余部分**（整库级备份、类型占用统计补完）：不在本批
