# 第 69 批·续：把信息卡渲染成图给 PS 插件（`card_path`）

> 日期：2026-10-17　｜　迁移号：**25**（`tpl_assets` 加 `card_path`）

---

## 1. 问题：HTML 卡片，插件吃不到

软件界面用 HTML 渲染信息卡（`docs/51`）—— 矢量、清晰、改样式即时生效。但 PS 插件是 **UXP**：

**UXP 没有 CSS 引擎**。它不是浏览器，只有一套受限的 DOM + Spectrum 组件。
`container-type` / `cqw` / flex 布局在插件里全都不认。

而插件读的**不是界面**，是磁盘上的图片文件：

```
软件 → _thumbs/<hash>.webp   →  镜像复制  →  PluginData/.../thumb/p<id>.png
                                              ↑ tpl.json 的 items[].thumb 指向它
```

所以只改界面的话：**插件照旧显示那张 160px 的糊图**（`ensureTplThumb` 没动），两端不一致。

## 2. 决策：软件把卡渲染成图，插件零改动

| 方案 | 插件改动 | 效果 |
|---|---|---|
| **A. 软件离屏渲染成 png，写进 `thumb`（采用）** | **零** | 两端一致、同样清晰 |
| B. `tpl.json` 加字段，插件用 UXP 组件自己画 | 大改 | 排版能力弱，**两套代码必然漂移** |
| C. 维持现状 | 零 | 插件永远糊 |

选 A 的关键理由：**`tpl.json` 的格式一个字节都不用改** —— 还是 `thumb: "thumb/p<id>.png"`，
插件甚至不知道底下换了内容。UXP 的 `<img>` 照旧工作。

> 这也回答了用户最初的直觉：「扫描后帮我生成缩略图」——**那个需求本来是对的**，
> 只是它服务的是**插件**，不是软件界面。软件界面用 HTML 实时渲染，插件必须吃一张渲染好的位图。

## 3. 实现

### 3.1 样式只有一份（`shared/tplCardMarkup.ts`）

把信息卡的 CSS + 数据映射从 React 组件里**抽到 shared**：

- `TPL_CARD_CSS` —— 唯一的样式来源
- `tplCardView(data)` —— 数据 → 卡面字段（`titleCqw` / `size` / `bleed` / `colorMode`）
- `tplCardHtml(data, { size })` —— 生成完整独立 HTML 文档（给离屏渲染）

界面侧：`TplInfoCard.tsx` 用 `tplCardView` 渲染结构，`TplLibraryView` 注入一次 `<style>{TPL_CARD_CSS}</style>`。
主进程侧：直接把 `TPL_CARD_CSS` 拼进 HTML。

**为什么必须这样**：两边各写一份样式，改了一边忘了另一边，插件里就会慢慢变成旧样子。

### 3.2 渲染器（`main/tplCardImage.ts`）

```ts
renderTplCardPng(data, outAbs): Promise<boolean>
```

- 一个**离屏 BrowserWindow**（`offscreen: true`，1024×1024 —— 正好是 `cqw` 的 100% 基准）；
- `loadURL(data:text/html,...)` → 等 `did-finish-load` + 90ms（等字体/布局稳定）→ `capturePage`；
- `sharp` 压到 **512×512** png（单张 34-38KB）；
- **串行化**：离屏窗口只有一个，并发 `loadURL` 会互相打架 ⇒ 用 promise 链排队；
- **失败不抛**：返回 false 并 `console.error` 留痕（不能因为一张图挡住入库）。

> ⚠️ `offscreen: true` 是关键：普通隐藏窗口会被当成后台页节流，`capturePage` 经常抓到空白。

### 3.3 依赖注入（`tplLib` 不碰 electron）

`thumbs.ts` / `tplLib.ts` 刻意**不依赖 electron**（accept 才能在纯 node 下跑）。
所以渲染能力由 ipc 层注入：

```ts
// ipc.ts 的 registerIpc 开头
setTplCardRenderer(renderTplCardPng)
```

没注入时 `ensureTplCardImages` 直接返回 0（accept 环境即如此）。

### 3.4 缓存：按内容签名

文件名 = `sha1(文件名|像素|ppi|色彩模式|关键词|丢失态)` 前 16 位 + `.png`。

- 内容没变 → 文件已存在 → **跳过**（重复扫描几乎零耗时）
- 内容变了 → 新签名 → 新文件；旧文件在函数末尾按"未被引用"清掉
- 两个模板内容完全相同 → 签名相同 → **共用一个文件**

⚠️ **样式变化不在签名里** —— 改了 CSS / logo 必须点「**重建卡片图**」（`force: true`），
否则缓存命中旧图，插件里还是老样子。

### 3.5 镜像与契约

`linkMirror.ts`：

```sql
SELECT id, card_path, thumb_path FROM tpl_assets
 WHERE card_path IS NOT NULL OR thumb_path IS NOT NULL
```

`thumb` 取 `card_path ?? thumb_path` —— **卡片图优先，PSD 内嵌预览兜底**（渲染失败时不会没图）。

**契约影响**：字段名、路径形态、文件名规则**全都不变** ⇒ 不需要升 `vellum-link` 版本。
但图的内容变了（160px PSD 预览 → 512px 信息卡），已在 `LINK-LOG` 告知插件侧，并请他们确认
"模板格子没有对 160px / 4:3 的硬编码假设"。

## 4. 迁移 25

```sql
ALTER TABLE tpl_assets ADD COLUMN card_path TEXT
```

**为什么和 `thumb_path` 分开而不是复用**：
`thumb_path` 是 PSD 内嵌预览（软件界面已不用，但留着当兜底），`card_path` 才是给插件的那张。
两列各管各的，渲染失败时镜像自动回退，不会出现"没图"。

## 5. 验收

| 项 | 结果 |
|---|---|
| typecheck（node + web） | 0 错 |
| accept | **1417 → 1419**（+2：`thumb` 指向卡片图 / 镜像里那张图的字节数与源一致） |
| `tpllib` 场景 | 全绿（+2：扫描后生成 4 张卡 / 512×512） |
| 实拍 | 4 张 512×512 png，34-38KB，视觉与界面一致 |

**关键断言**：给 `rowA` 造一张卡图写进 `card_path` 后，`tpl.json` 里 `thumb` 必须变成
`thumb/p<id>.png`，且镜像里那份文件的**字节数与源一致**（证明用的就是卡图，不是 PSD 预览）。

## 6. 边界

| 项 | 状态 |
|---|---|
| logo 仍是占位（橙方块 + `vellum` 字标） | 等用户给透明底 PNG，换掉后点一次「重建卡片图」 |
| 首次扫描 100 个模板约 10 秒（每张 ~100ms） | 可接受；之后靠缓存几乎零耗时 |
| 离屏窗口常驻内存 | 一个 1024×1024 的隐藏窗口；`will-quit` 时销毁（否则会拖住进程不退出） |
