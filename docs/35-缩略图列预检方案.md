## 1. 起因

第 49 批收尾时，用户提供了工单表链接、据此实探真表，**顺手查出一个设计缺口**：

「缩略图」列（工单队列里的 image 列）

- **列名写死**：`COL.thumb = '缩略图'`，`thumbColName()` 直接返回常量，**不可配**
- **没有任何可用性预检**：不像设计师列那样有 `evaluateDesignerCol`

后果：用户把列改名 / 把列建成 text·url 类型时，
要等点「完成任务」、**生成完缩略图、逐张上传完之后**，写回那一步才现场报错 —— **白跑一趟上传**。

对比：设计师列（第 17 批）早就有 `evaluateDesignerCol` 预检，缺失/改名会让指派入口提前置灰。
缩略图列一直缺这一层，属第 19 批留下的尾巴。

## 2. 做什么

1. **`evaluateThumbCol()`** —— 同步时读 `sheets list` 的 fields，判两件事：
   - ① 列在不在（按列名精确匹配）
   - ② **类型是不是 `image`**（比设计师列多判一项 —— 建成 text/url 时
     `{title, imageUrl}` 会被服务端拒收）
   结果写 meta `ticket_thumb_ok`（`'1'`/`'0'`）
2. **列名可配**：meta `ticket_thumb_col`（默认仍是「缩略图」），`thumbColName()` 改读它 ——
   沿用 `designerColName()` 的同一套路子
3. **同步读列名同源**：原先同步时用 `v[COL.thumb]` 写死 → 改成 `v[thumbColName()]`。
   否则列一改名，**写回读新列、同步读旧列**，`thumb_url` 永远空
4. **「完成任务」先判列再干活**：`ticket:completeByPack` 开头判 `thumbColUsable()`，
   不可用直接回 `thumbColBad` —— **不生成缩略图、不上传**
5. **设置弹窗常驻一行橙色警示**（`initial && !thumbColOk`）

## 3. 口径（与设计师列严格一致）

- `fieldsBySheet` 拿不到（CLI 版本差异）→ **不设防**（不写标记，当可用）—— 宁可放过也不误伤
- 一个启用子表都没查到 → **不写标记**（"没数据" ≠ "列坏了"）

## 4. 真表实测依据

2026-10-08 实探「营销物料设计工单队列（2.0）」，确认两个生产子表
（电子物料 `tlzJfN` / 印刷物料 `tlD2Vr`）**列名精确为 `缩略图`、类型 `image`** ——
与默认值一致，所以**默认配置在真表上开箱可用**。

## 6. 施工中踩到的两条坑（已写进 NEXT 坑表）

1. **场景壳加载的是 `out/test/ipc.cjs`，不是 `out/main/index.js`**
   （`_shotapp/v4/main.cjs` 第 715 行 `require(...).registerIpc()`）。
   改完 `ipc.ts` 只顾着重打给 accept 用 → 界面场景拿旧 IPC 跑，
   症状是**新增字段整个从 status 载荷里消失**（不是值不对，是 key 都没有）→
   一度误判成"代码没生效"。
2. **场景中途改 meta 无效**：软件启动后主进程**自己持有 DB 连接**，
   另一个连接写进去当场读得到，但主进程那份看不到。
   正解：标记一律**布景期**写，要验两支就用环境变量选。
