## 0. 一句话结论

插件侧的判断**只对了一半**：

- **通用库**（docs/46）：每个写操作后 `void syncNow()` —— **已经是"变更后自动"**，但**没有合并**，批量导入会连续写盘。
- **任务库**（导入素材 / 改项目 / 改任务 / 打标签 / 新建版本…）：**完全没有自动重写** —— 只有「同步到插件」按钮（手动）和软件启动首扫。**这就是"连点刷新刷不出新素材"的根因**。

**做法** = 在 `ipcMain.handle` 上套一层：**除了明确只读的通道，任何 IPC 成功后都排一次同步**；同步**节流 1.5 秒**并**串行**执行，内容没变时签名短路、一个字节不写。

## 2. 方案（已落地）

### 2.1 `linkService.ts`：节流 + 串行

```
scheduleMirror(reason?)   ← 任何写通道成功后调它
  ├─ 已经排上了？ → **直接返回，不往后推**（节流，不是防抖）
  └─ 否则 setTimeout(1500) → flush()

flush(): 串行链上 await syncNowCore()   ← 一把锁，绝不并发进同步
```

- **节流 1.5 秒**（不是防抖）：保证「**改动后最迟 1.5 秒写盘**」是硬保证。
  若用防抖，界面上的轮询类调用会把已排的写**一直往后顶**，写盘被无限推迟（插件侧提醒的真问题）。
- **串行**：杜绝"两个 `syncNow` 交错 → 读到同一个 `prevRev` → 两次都写 `revision = prev+1`，甚至把旧内容配上新 revision"。
- **`plugin:syncNow`（手动按钮）立即执行**，但仍走同一条串行链。
- **退出兜底**：`before-quit` 时若还有待写的变更，`flushMirrorNow()` 冲刷完再退。

### 2.2 触发判据：**反着写**（不枚举"像内容变更的操作"）

在 `ipc.ts` 里给 `ipcMain.handle` 套一层 `handleIpc`：

```
NO_MIRROR_CHANNELS = { 明确只读/纯弹框的通道 }        // 39 个：view:* / *_list / *_status / pick* …
其余通道（约 64 个）成功后一律 scheduleMirror()
```

- **为什么不列白名单**：插件侧指出得对 —— 枚举"像内容变更的操作"**一定会漏**
  （初版就漏了 `project:update`（改名/改色）、`archived` 归档一类）。
  改成「**除了这几个明确只读的，其余全排**」后，**将来新增的写通道自动被覆盖**，不会再漏。
- **多排没成本**：同步内部有内容签名短路，内容没变就一个字节都不写。
- **换工作区**（`ws:switch` / `ws:setRoot` / `ws:add` / `ws:move`）：先 `refreshLinkWorkspace(新根)`
  把服务指向新根（**否则写的是旧工作区的内容**），再排同步。

### 2.3 revision 语义

- 每 scope **独立计数、单调递增、内容变则必变**；`manifest` 合并写，保留另一条 revision 原值。
- 插件侧必须以 `scopes[].id` 为键分别记忆 —— 已写进契约 **§5.6**（采用插件侧给的措辞）。

### 2.4 缩略图增量

写 `thumb/t<id>.png` 前先比**源 `_thumbs\*.webp` 与目标**的 `mtime`：目标**比源新**就跳过。
（png/jpg 是直接拷贝、`copyFileSync` 会把源 mtime 一起搬过来 → 两者相等 → 同样命中跳过。）
没有这一步，接上"自动同步"后每次改动都要把所有缩略图重转一遍，大库会很卡。

### 2.5 写入顺序（已满足，仅确认）

**缩略图 → `task.json`/`brand.json` → `manifest.json`**；`manifest` 不引用缩略图 →
"manifest 指向还没写出来的图"不可能发生；缩略图失败时 `asset.thumb = null`，插件画占位。

### 2.6 换工作区：**强制重写**（本批修掉的真 bug 🔴）

镜像目录在磁盘上是**多个工作区共用**的，而签名短路用的 `meta` 是**按工作区各存一份**的。
于是「切到 B 再切回 A」时：A 的签名与 A 的内容仍一致 → **短路 → 不写盘** → 插件**一直显示 B 的数据**
（"数据是旧的、界面却一切正常"，最难归因 —— 插件侧 v0.3.2 吃过一份 stale `brand.json` 的亏）。

**解法**：短路之前先读 `manifest.json` 里的 `workspaceRoot`，**不是当前工作区就强制重写**。
（manifest 本来就带这个字段，零新增。）

### 2.7 防呆：手填的插件目录落在工作区内部 → 不认

2026-10-11 用户实测踩过：把「插件数据目录」填成 `D:\vellum_workspace\通用素材`，
结果①镜像被写进工作区、②那个文件夹被任务扫描**当成 3 个假任务**。
现在 `discoverTargets` 会**跳过落在工作区内部的目录**，设置弹窗给出明确提示。

## 6. 附带修正：设置里那个开关的名字（2026-10-11）

原勾选框文案是「**变更时自动同步**」，但它实际是**整个插件联动的总开关** ——
`startLinkService()` / `refreshLinkTargets()` 在 `enabled === false` 时**直接 return**：
镜像不写、**handoff 轮询也停**（插件既看不到素材、也无法把图插进画布），启动时也不再首扫。
名字看着像"自动 / 手动"的切换，实际是"开 / 关整个联动"，**极易误关**。

**已改**（用户 2026-10-11 拍板：只改名 + 加说明，**不动逻辑**）：
- 文案 →「**启用插件联动**」，下面补一行说明："关掉后插件将看不到素材、也无法把图插进画布。
  开着时，软件里的改动约 1.5 秒自动同步，无需手动点下面的按钮。"（`copy.ts` 的 `pluginLink.autoLabel` / `autoHint`）
- 弹窗把说明**单独一行**渲染（`.pl-hint`），不再塞进 `（…）` 里。

**⚠️ 遗留（未修，已知）**：`enabled === false` 时行为**不一致** —— 启动不服务、轮询停，
但任意一次写操作后 `syncNowCore()` 仍会自己重新发现目标并写镜像（"关掉"没真的完全停写）。
若将来要提供真正的"手动模式"，应**拆成两个开关**（总开关 + 变更自动同步），并统一 `disabled` 语义。
