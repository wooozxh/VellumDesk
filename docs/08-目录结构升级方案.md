# 08 · 目录结构升级方案（三级：工作区 / 项目 / 包）

> 第 6 批方案文档。定稿日期 2026-09-25。
> 本批是**地基级改动**：改的是磁盘布局与扫描判定方式。
> 前置：`docs/03`（两级结构的原始定义）、`docs/07`（工作区管理）、需求文档 5.8 节 M8-04/M8-05。
> 铁律：本文档定稿并经用户确认后才动代码；施工中改主意先改本文档。

## 0. 一句话

把磁盘布局从「工作区 / 包 / 三子文件夹」升级为「**工作区 / 项目 / 包 /〔版本〕/ 三子文件夹**」，
让**软件里的目录层级与本地文件夹层级完全一致**，并把现有数据一次性、可回滚地迁移过去。

---

## 1. 为什么做（背景与拍板）

### 1.1 用户提出的原始动机

1. 建包时新建的文件夹被软件硬塞进「排序第一的项目」——软件显示一个假归属，磁盘上却看不出任何项目结构；
2. 用户希望"软件上的结构和本地磁盘的结构一致"，看到目录就知道东西在哪；
3. 项目结项后需要一个"留底但不碍眼"的处置方式（解绑 / 删除）。

### 1.2 用户拍板的六件事（2026-09-25）

| # | 事项 | 结论 |
|---|---|---|
| 1 | 层级演进 | **工作区 / 项目 / 包 /〔版本〕/ 三组**；本批只做前三层，但实现方式必须留门 |
| 2 | 游离的包 | **甲**：根目录下发现的包 → 软件里归「待归类」，用户手动选项目归位（不自动塞） |
| 3 | 删除的处置 | 新建 **`_回收站`** 目录专门收被删除的项目（与解绑区分开） |
| 4 | 项目改名 | **要连带改文件夹名**，保持一致 |
| 5 | 现有数据 | **迁移**到新结构 |
| 6 | 批次拆分 | **按推荐**：结构升级前置（下详 §16） |

### 1.3 查证结果：这不算"改需求"

需求文档 605 个段落全扫过，**从头到尾没有定义过工作区的目录层级**。最接近的第 402 条只是理念
（"素材本体不进仓库……图片视频就放在硬盘原来的文件夹里，仓库只记它在哪"）。
所以在铁律意义上，这属于「需求文档没写到」→ 用户拍板名正言顺。

但 `docs/03`（MVP 入库功能方案）里白纸黑字写的是**两级**：
- §2.3 包文件夹下三个子文件夹
- §2.4 未归属池 = 工作区根目录下的散文件

**这份要同步修改**，否则两份文档打架。

## 2. 目标结构

### 2.1 磁盘布局

```
D:\素材工作区\                       ← 工作区根（可换盘、可有多个）
│

├── _thumbs\                        ← 缩略图缓存                         扫描跳过
├── _已解绑的项目\                   ← 解绑的项目挪这儿（记录保留，可恢复）  扫描跳过
├── _回收站\                         ← 删除的项目挪这儿（记录已删）        扫描跳过
│
├── 海南升学规划中心\                 ← 项目文件夹（项目名 = 文件夹名）
│   ├── 海南招生海报-2026秋季\         ← 包文件夹
│   │   ├── 01-成品\
│   │   ├── 02-素材\
│   │   └── 03-工程\
│   └── 招生折页-A4\
│       ├── 01-成品\ …
│
├── 海南升学初三集训营\
│   └── 测试\
│       ├── 01-成品\ …
│
└── 某个游离的包\                     ← 根目录下直接带三子文件夹 → 归「待归类」
    ├── 01-成品\ …
```

### 2.2 与交付包结构同构（顺带验证方向的正确性）

需求文档第 274 条定义的**交付包**（导出给客户的成品）结构是：

```
项目名 ／ 交付日期 ／ 01成品 ／ 02素材 ／ 03工程文件 ／ 04清单
```

**第一层就是「项目名」** —— 与本次定下的三级结构同构。
将来从工作区生成交付包，几乎是"照搬目录再补一张清单"。
软件结构、磁盘结构、交付物结构三者统一，这是本次升级最大的隐性收益。

### 2.3 版本层的预留（本批不实现，但必须不挡路）

层级最终形态是 `工作区 / 项目 / 包 /〔版本〕/ 三组`（`包\V1\01-成品\`）。
**本批实现方式必须写成"不认层级深度"**，见 §5.2。
成本几乎为零，省下的是一次推倒重来。

## 3. 三个区域 + 一个状态的语义

| 磁盘位置 | 软件里 | 数据库 | 可恢复 |
|---|---|---|---|
| `工作区\项目名\包名\` | 正常显示在项目下 | 记录正常 | — |
| `工作区\某游离包\`（根下） | 归入「**待归类**」 | `project_id = NULL` | — |
| `_已解绑的项目\项目名\` | 「已解绑」入口里可见 | 项目 `archived=1`、包保留 | ✅ 一键还原 |
| `_回收站\项目名\` | 看不见 | 项目与包的记录已删 | ❌（文件还在，手动捞） |

**两个下划线区都不真删文件**，这是「软件永远不悄悄扔掉用户放的东西」铁则在本批的落地形态。
真想彻底清掉，用户自己去 `_回收站` 里删——那才是"不要了"的正确姿势。

> `_` 开头即被扫描跳过（现有规则：`name.startsWith('_') || name.startsWith('.')`）。
> **零代码实现"扫不进去"**，这是选下划线前缀的核心理由。

## 4. 数据模型改动

### 4.1 `projects` 表：新增 `folder_name`

```sql
ALTER TABLE projects ADD COLUMN folder_name TEXT NOT NULL DEFAULT '';
CREATE UNIQUE INDEX IF NOT EXISTS idx_projects_folder
  ON projects(folder_name) WHERE folder_name <> '';
```

**为什么必须有这个字段，不能靠"算"**：
项目改名 → 文件夹要跟着改 → 必须知道**旧文件夹名叫什么**。
有包时可以从 `packs.folder_path` 反推，但**空项目**（0 个包）无从反推。
而"新建工作区时预设几个项目"（用户明确提到的发行形态）天然就会产生空项目文件夹。

回填：迁移时 `folder_name = sanitizeFolderName(name)`，冲突加 `-2/-3`。

### 4.2 `meta` 表：记录布局版本

```sql
CREATE TABLE IF NOT EXISTS meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- 迁移完成后写入：layout_version = '3'、layout_migrated_at = <ISO>
```

**放在工作区自己的数据库里，不放全局配置**：多工作区各自有各自的结构状态，
配置文件是全局的，管不了这个。

### 4.3 `packs` 表：本批不动

`folder_path` 仍是全库 UNIQUE —— 三级下不同项目可以有同名包（路径不同，天然不冲突）。
**这是升级带来的顺带好处**：以前全库不能重名，现在同项目内不重名就够了。

`archived` 列留到第 7 批（配合包记录清理与解绑）再加，本批不做。

## 5. 核心算法

### 5.1 目录判定：项目文件夹 vs 包文件夹

**判据只有一条，看直接子级**：

```
根目录下的文件夹 F：
  F 直接包含 01-成品 / 02-素材 / 03-工程 之一  →  F 是【游离的包】（待归类）
  否则                                        →  F 是【项目文件夹】

项目文件夹的直接子文件夹                        →  【包文件夹】
```

为什么这条判据够用：`项目\` 的直接子级是包文件夹（如 `ces\`），不含三组名；
`项目\ces\` 的直接子级才含 `01-成品`。天然互斥，不需要额外标记。

### 5.2 文件归位：深度无关

**现状（要改掉）**：`detectRoleFromPath` 靠数段数 —— `parts[0]` 是包、`parts[1]` 是子文件夹。
将来包下插一层 `V1\` 会直接全崩。

**新算法**（两段式，先定位包、再定位 role）：

```
1. 遍历根目录 → 项目文件夹列表 → 各自的直接子文件夹 = 包文件夹列表
   建立 map：包文件夹绝对路径 → pack_id（最长前缀优先）

2. 对每个文件 abs：
   pack = 匹配到的最长包文件夹前缀
   if (pack) {
     relInPack = 文件相对包文件夹的段数组
     idx = relInPack 里第一个匹配三组名的下标
     role = idx 存在 ? FOLDER_TO_ROLE[relInPack[idx]] : 未归属
   } else {
     role = 未归属        // 根目录散文件、项目文件夹下的散文件
   }
```

验证：
- `项目\包\01-成品\a.png` → 相对包 = `[01-成品, a.png]` → idx 0 → **成品** ✅
- `项目\包\V1\01-成品\a.png` → 相对包 = `[V1, 01-成品, a.png]` → idx 1 → **成品** ✅（未来版本层白送）
- `项目\包\随手丢.png` → 相对包 = `[随手丢.png]` → 无匹配 → **未归属**（但 `pack_id` 指向该包）
- `项目\散文件.txt` → 无包匹配 → **未归属**，`pack_id = NULL`
- `工作区\散文件.txt` → 无包匹配 → **未归属**，`pack_id = NULL`

### 5.3 根目录读失败必须中止（安全阀）

现有 `scanAll` 把 `readdirSync(工作区根)` 包在 `try/catch` 里，**失败时返回空数组**。
若直接拿它判定"文件夹不存在"，那么**工作区在移动硬盘上、硬盘没插时，一次刷新会清空所有记录**。

**规则写死**：本轮扫描中，根目录读取失败 → 直接返回、**不做任何记录层面的删除判定**。
（这条在第 4 批已有 `workspaceOk` 兜底，本批把它贯彻到扫描内部。）

## 6. 一次性迁移（v2 → v3）

### 6.1 触发与幂等

放在 `initWorkspace(root)` 内、`openDb` 之后调用 `ensureLayoutV3(root)`：

```
读 meta.layout_version
  === '3'  → 只做 syncProjectFolders(root)（保证每个项目都有文件夹），返回
  !== '3'  → 走迁移
```

新工作区（空库）直接写 `layout_version = 3`，跳过迁移。

### 6.2 步骤

```
① backupDb(root) → _system/backup/     失败即中止，不冒险
② 回填 projects.folder_name（sanitize + 唯一化）
③ 算迁移计划：对每个 pack
     目标 = root \ <其项目 folder_name> \ <包文件夹名>
     源   = pack.folder_path
     跳过：源不存在（记录悬空）或 源已在目标位置（幂等）
④ 逐个 rename（同盘瞬间完成），记下每一步
   —— 任一步失败：把已完成的逐个 rename 回去，库未动，一致性保住
⑤ 单事务改库：
     UPDATE projects SET folder_name = ?
     UPDATE packs    SET folder_path = ?（逐条）
     UPDATE assets   SET abs_path / rel_path = ?（逐条，两步走规避 UNIQUE 碰撞）
   —— 事务失败：回滚事务 + 把 ④ 全部 rename 回去
⑥ 写 meta：layout_version = 3、layout_migrated_at
⑦ syncProjectFolders(root)：给所有项目（含归档）补齐文件夹
```

**为什么 rename 全做完再改库**：文件系统没有事务，数据库有。
把不可回滚的那部分（rename）放前面并保留逆向操作，把可回滚的部分（SQL）放后面，
出任何问题都能回到起点。

### 6.3 用户机器上的实际迁移量

| 包 | 现位置 | 项目 | 迁到 |
|---|---|---|---|
| 元信息演示包 | `工作区\元信息演示包` | 集团通用 | `工作区\集团通用\元信息演示包` |
| 测试 | `工作区\测试` | 海南升学初三集训营 | `工作区\海南升学初三集训营\测试` |
| ces | `工作区\ces` | 海南升学规划中心 | `工作区\海南升学规划中心\ces` |

三个都是同盘 `rename`，**瞬间完成**，不管里面有多少文件。

## 7. 项目 CRUD 改造

### 7.1 创建项目 `createProject`

- 名称校验：非空、不重名、**不允许以 `_` 或 `.` 开头**（否则会被扫描跳过，等于凭空消失）
- 生成 `folder_name`（sanitize + 唯一化，含 Windows 保留名黑名单 CON/PRN/AUX/NUL/COM1-9/LPT1-9）
- **同时创建工作区下的项目文件夹**（`工作区\<folder_name>`）

### 7.2 项目改名 `updateProject`（拍板第 4 件）

用户改项目名 → **文件夹跟着改名**，否则软件与磁盘不一致，正好违背本次升级的初衷。

```
① 校验新名（非空 / 不重名 / 不以 _ . 开头）
② 计算新 folder_name
③ backupDb
④ rename 项目文件夹 旧 → 新
⑤ 单事务：改 projects.name / folder_name；重写该项目下所有 packs.folder_path
           与 assets.abs_path / rel_path
⑥ 失败：rename 回去 + 事务回滚
```

只改颜色 / 备注时**不碰磁盘**（`name` 未变则整段跳过）。

### 7.3 删除项目 `removeProject`（本批只做一致性，语义调整留第 7 批）

现有签名 `action: { moveTo: number | null }` 保留，但**磁盘动作必须同步**：

| 分支 | 磁盘动作 | 数据库 |
|---|---|---|
| `moveTo: N`（转移到其他项目） | 把包文件夹 rename 进目标项目文件夹 | `packs.project_id = N` + 路径重写 |
| `moveTo: null`（变成未归属） | 把包文件夹 rename 到**工作区根目录**（= 待归类状态） | `packs.project_id = NULL` + 路径重写 |

`moveTo: null` 落到根目录而非留在原地，是**刻意的**：
这样"未归属的包"与"根目录下的游离包"是同一种东西，界面上统一叫「待归类」。

改项目名 / 删项目都要**先备份数据库**（复用第 5 批的 `backupDb`）。

## 12. 验收检查点

### 12.1 新增 `[24]` 段（计划 30+ 条断言）

**结构判定**
- 根目录下带三子文件夹的文件夹 → 判定为「游离的包」（`project_id = NULL`）
- 根目录下不带三子文件夹的文件夹 → 判定为「项目文件夹」
- `项目\包\01-成品\a.png` → role = 成品
- `项目\包\V1\01-成品\a.png` → role = 成品（**版本层预留的决定性证据**）
- `项目\包\随手丢.png` → role = 未归属，且 `pack_id` 指向该包
- `项目\散文件.txt` → role = 未归属，`pack_id = NULL`
- `工作区\散文件.txt` → role = 未归属

**建包 / 建项目**
- 建包落在 `工作区\<项目文件夹>\<包名>`，三子文件夹齐备
- 同项目内重名 → `-2` 后缀；**不同项目的同名包 → 各自独立，不冲突**
- 建项目 → 磁盘上立刻出现同名文件夹
- 项目名以 `_` 开头 → 被拒

**改名联动**
- 改名后：旧文件夹不存在、新文件夹存在、里面文件一个不少
- 该项目下所有 `packs.folder_path` / `assets.abs_path` 都已指向新路径
- 改名前后 `asset_tags` 条数不变（标签一条不丢）
- 改名失败（目标已存在）→ 报错且磁盘与库都回到原状

**删除一致性**
- `moveTo: N` → 包文件夹真的搬到了目标项目文件夹下
- `moveTo: null` → 包文件夹真的搬到了工作区根下（待归类），`project_id` 为 NULL
- 两种情况下磁盘文件数都不变

**迁移**
- 老结构库（包在根下、有 project_id）→ 迁移后全部落在对应项目文件夹下
- 迁移前自动备份存在
- 迁移幂等：再跑一次，零改动
- 迁移后 `layout_version = '3'`
- 空库（新工作区）→ 直接标 v3，不迁移
- 迁移后素材条数 / 标签关联条数不变

**安全阀**
- 根目录不可读时不误判：所有包记录保留

## 14. 已知代价与风险

| 项 | 说明 |
|---|---|
| **磁盘布局变了** | 用户（和同事）在资源管理器里看到的目录结构不同了。老版本软件读新结构会怎样？——旧版 `scanAll` 靠数段数，会把 `项目\` 当包、把包当子文件夹，**读出乱码级的结果**。所以本批要更新软件；用户机器上的旧安装包（第 4 批版）**不要再装**，装新包前先确认工作区已迁移 |
| **首次启动会动磁盘** | 迁移会 rename 用户文件夹。已通过"先备份 + 可回滚 + 只 rename 不复制不删除"把风险压到最低，但**首次启动前建议用户自己再拷一份工作区**（软件会把这句话写进提示条） |
| **空项目文件夹** | 项目建了但没包 → 磁盘上留个空文件夹。可接受（结构一致性优先），但用户要知道这是正常的 |
| **迁移耗时** | 同盘 rename，与体积无关，**瞬间完成** |
| **旧断言改动** | 2 条，理由见 §13 |

## 16. 后续批次蓝图（已拍板结论留档，避免决策丢失）

### 第 7 批：记录的生命周期

- **包记录自动清理**（用户已批"甲"）：扫描发现包文件夹不在 → 清理记录。
  两道安全阀：① 根目录读成功才判定（§5.3）；② 清理前把包信息落 `_system/backup/`；
  ③ **已归档（解绑）的包豁免**——它们本来只是留底，文件夹挪走了也不能清记录
- **包信息可编辑**：包卡片给「编辑」入口，可改所属项目 / 类别
  （改项目 = 搬文件夹，复用第 6 批的 rename + 路径重写）
- **待归类归位**：点「待归类」里的包 → 选项目 → 搬进该项目文件夹
- **解绑**（左栏悬浮区 `✎` 与 `✕` 之间加一个）：
  rename 项目文件夹 → `_已解绑的项目\`；项目 `archived=1`；包记录保留、路径重写；
  界面上进「已解绑 N 个项目 · 真实占用 X GB」入口，可一键还原
- **删除**（现有 `✕`）：rename 项目文件夹 → `_回收站\`；项目与包的记录删掉；
  弹框要写清"文件不会消失，只是移入回收站"
- `asset_tags` 孤儿修复（`asset_tags` 表**一个外键都没有**，素材记录被删时关联行变孤儿）

### 第 8 批：M8-03 文件已丢失标记 + 重新定位

需求文档写的是"标记为文件已丢失并提供重新定位"，而实现是**直接删素材记录**。
两者相反：**该删的包记录不删，该留的素材记录却删了**。
这一条要动 `assets` 表结构 + 文件视图 + 新增重新定位对话框，独立成批。

### 版本模型的风险提示（做 M6 时要先解决）

需求文档 5.6 节说：**版本挂在「物料」上**（一个文件自己有 v1/v2/v3），数据库设计里也有一张
独立的 `versions` 表（编号 / 所属物料 / 版本号 / 路径 / 说明）。
但同一份文档第 283 条的交付文件名模板 `{项目名}_交付_{日期}_v{版本}` 里，
`v{版本}` 又明显是**批次级**的。

**两种版本概念文档里都有，关系从没定义过。** 本批不填这个洞，
但层级演进已确认为「工作区 / 项目 / 包 /〔版本〕/ 三组」，M6 时先定"版本到底挂谁"。
