## 0. 一句话

让每条记录都有出生、改名、搬家、退场、回收的完整路径：**磁盘上不在了的记录自动摘除，还在的都能改名搬家，退场的只搬不删。**

## 1. 为什么做

### 1.1 用户实测报障（第 6 批完成后）

| # | 现象 | 定性 | 根因 |
|---|---|---|---|
| 1 | 在资源管理器里删掉包文件夹，点「刷新扫描」后包里还挂在界面上 | **bug** | `scanAll` 六步里没有任何一步清理 `packs`，全项目也不存在 `DELETE FROM packs` |

| 3 | 项目结项后没法「留底但不碍眼」 | **缺失功能** | `archived` 字段早就有，但没有任何地方写它 |

### 1.2 用户拍板的六件事（2026-09-29）

| # | 事项 | 结论 |
|---|---|---|
| 1 | 包记录自动清理 | 做。两道安全阀 + 清理前留痕 |
| 2 | 包信息可编辑 | 改名称 / 类别 / 所属项目；**改名连带改文件夹名** |

### 1.3 删除项目的三个出口（用户拍板第 1 条）

第 6 批的 `✕` 是「二选一（转移到项目 / 变成未归属）」，本批**加第三个出口**而不是替换：

| 出口 | 磁盘 | 数据库 | 语义 |

## 2. 六件事逐一细化

### 2.1 ① 包记录自动清理

**触发点**：`scanAll`（刷新扫描 / 建包 / 认领 / 项目改名等一切走扫描的路径）。

**新增第 6 步（在"摘掉失效素材记录"之后、更新 `updated_at` 之前）**：

```
判定：包记录该清理  ⇔  三道门全过
  门一 rootReadable        —— 根目录这次读成功了（读不到 ≠ 里面没有）
  门二 !existsSync(folder_path) —— 磁盘上确实没有这个文件夹
  门三 该包所属项目 archived = 0 —— 解绑的项目只是留底，包文件夹挪走了也不能清记录
```

- 门二用 `existsSync` 而不是"不在本次扫描到的包目录集合里"，是**刻意保守**：包被用户手动挪到不合法位置（比如项目文件夹更深一层）时，记录留着、让用户还能在列表里看到它，比默默摘掉更符合铁则。
- 门三的豁免不依赖 ④ 的实现，只读 `projects.archived`。

**清理前留痕**：把被清掉的包信息（`name / folder_path / project_id / project_name / category / created_at / fileCount`）追加写入
`_system/backup/packs-<时间戳>.json`。有清理才写文件；**永不自动删除**。
`_system` 下划线开头，扫描自动跳过，不会出现在用户眼皮底下。

**连带**：包记录删掉后，其名下 `assets` 的 `pack_id` 由已有的 `ON DELETE SET NULL` 置空；
这些素材的 `abs_path` 已不存在 → 同一轮扫描的"摘素材"步骤或下一轮会摘掉它们；
`asset_tags` 的关联行由 ⑥ 的新外键 `CASCADE` 同步清除（**不再留孤儿**）。

**返回**：`ScanResult` 加 `cleanedPacks: number`，界面给一条轻提示。

### 2.2 ② 包信息可编辑 + ③ 待归类归位（共用同一个核心）

两件事本质是同一个动作：**把包从一个父目录搬到另一个父目录**。

```
movePackTo(workspaceRoot, packId, targetProjectId | null, newName?)
  ① 目标父目录 = targetProjectId === null ? 工作区根 : 工作区\<项目.folder_name>
     若项目不变、只改类别 → 整个磁盘段跳过
  ② 目标文件夹名 = sanitizeFolderName(新名字 ?? 原名)，同父目录内重名自动 -2 -3
  ③ backupDb
  ④ rename（同盘瞬间；失败即中止，库里不动）
  ⑤ 单事务：UPDATE packs(name, category, folder_path, project_id, updated_at)
              + reprefixPaths(旧路径 → 新路径)   ← 重写 assets.abs_path / rel_path
  ⑥ 失败：rename 回去
```

**`updatePack` 的入参**：`{ name?, category?, projectId? }`，三者都可选。

- **改名称** → 连带改文件夹名（与项目改名一个规矩："软件里看到什么，硬盘上就是什么"）
- **改类别** → 纯数据，不碰磁盘
- **改项目** → 搬文件夹（②③ 走这里）
- **`projectId: null`** → 搬回工作区根目录 = 变「待归类」（这就是"变成未归属"的正向操作，之前只有删项目时能用）
- 名称留空 → 报错（编辑是明确动作；建包留空才有兜底名）

**③ 待归类归位** 就是 `projectId: null → N`。界面上等价于对游离包点「✎ 归位」，弹窗里选一个项目。

**冲突处理**：目标项目里已有同名包 → 自动 `-2`（搬移是用户主动动作，加后缀比报错友好）。
`asset_tags` / `assets.id` 全程不变（这是用 rename + 路径重写而不是重新扫描的全部理由）。

### 2.3 ④ 项目解绑

```
unbindProject(id, workspaceRoot)
  ① 校验：解绑后至少要剩 1 个未解绑项目（否则建包没有默认归属可选）
  ② backupDb
  ③ rename  工作区\<folder_name>  →  工作区\_已解绑的项目\<folder_name>   （重名自动 -2）
  ④ 单事务：projects.archived = 1  +  reprefixPaths（包的 folder_path 与素材路径一起改）
  ⑤ 失败：rename 回去
```

**"软件里不显示"的落地方式**：不是给包加 `hidden` 字段，而是**在查询里排除 `archived` 项目**：

| 查询 | 处理 |
|---|---|
| `listPacks()`（包视图） | `WHERE k.project_id IS NULL OR p.archived = 0` |
| `listAssets()`（文件视图） | 排除挂在 archived 项目包下的素材 |
| `countUnassigned()`（未归属计数） | 同上 |
| `view:packs` 的 total（条数 / 容量） | 同上 |
| `listProjectsWithCount()` | 本来就只列 `archived = 0`，无需改 |
| `syncProjectFolders()` | **必须排除 `archived = 1`**（见下） |

**为什么不用 `hidden` 字段**：要改的查询点一样多，但每加一处新查询就漏一次；集中在 `archived` 一个语义上，漏了更容易发现。

**界面验证抓出来的一处漏网**：`syncProjectFolders()`（每个 IPC 调用前的 `initWorkspace` 都会跑）最初不过滤
`archived`，解绑后一刷新就在根目录把同名文件夹重新建出一个**空壳** —— 空壳一出现，「还原」会被自己建的壳挡住
（`restoreProject` 见根目录同名即拒绝）。已改为 `WHERE folder_name <> '' AND archived = 0`，
并在 accept.ts `[25]` 加回归钉子：解绑后跑一遍 `initWorkspace`，根目录不得重建。

**还原**：
```
restoreProject(id, workspaceRoot)
  rename  _已解绑的项目\<folder_name> → 工作区\<folder_name>
  （根目录已有同名文件夹 → 报错让用户先处理，**不自动加后缀**：那是用户自己放的东西，改名会让找不到）
  单事务 archived = 0 + reprefixPaths
```

**入口**：左栏项目面板底部一行「📦 已解绑 N 个项目」→ 弹窗列表（项目名 / 包数 / 占用 / 还原按钮）。
占用大小取库里 `SUM(assets.size)`，不去扫盘。

### 2.4 ⑤ 项目删除（进 `_回收站`）

```
removeProject(id, { toTrash: true }, workspaceRoot)
  ① 校验：不删最后一个项目（与老分支一致）
  ② 留痕：包信息写 _system/backup/packs-<时间戳>.json（复用 ① 的函数）
  ③ backupDb
  ④ rename  工作区\<folder_name>  →  工作区\_回收站\<folder_name>   （重名自动 -2）
     项目文件夹**整体搬走** —— 里面没进过扫描的手工文件夹也跟着走，绝不漏
  ⑤ 单事务：DELETE FROM assets WHERE pack_id IN (该项目下的包)   ← 连同 asset_tags 级联
            DELETE FROM packs  WHERE project_id = id
            DELETE FROM projects WHERE id = id
  ⑥ 失败：rename 回去
```

- 老的 `moveTo` 分支（转移 / 待归类）**保持原样**，见 §1.3。
- 文件始终一个不少：只是从 `工作区\项目名\` 变成 `工作区\_回收站\项目名\`。
- `_回收站` 下划线开头 → 扫描永远跳过 → 不会又被登记回来。
- **不提供"从回收站彻底删除"**（用户拍板）：删文件让用户去资源管理器自己决定，软件只负责"绝不弄丢"。

### 2.5 ⑥ `asset_tags` 加真外键（迁移 7）

现状：`asset_tags` 是张**裸关联表**，对 `assets` 和 `tags` 都没有外键。
后果：删素材记录时关联行留成孤儿（`AssetRow` 被删、`asset_tags` 里还挂着它的 id）。

**处理（一次性重建表，SQLite 不支持 ALTER 加外键）**：

```sql
-- 迁移 7（幂等：靠 PRAGMA foreign_key_list(asset_tags) 是否为空判定）
DELETE FROM asset_tags WHERE asset_id NOT IN (SELECT id FROM assets);   -- 清历史孤儿
DELETE FROM asset_tags WHERE tag_id   NOT IN (SELECT id FROM tags);     -- 清历史孤儿
CREATE TABLE asset_tags_new (
  asset_id INTEGER NOT NULL REFERENCES assets(id) ON DELETE CASCADE,
  tag_id   INTEGER NOT NULL REFERENCES tags(id)   ON DELETE CASCADE,
  PRIMARY KEY (asset_id, tag_id)
);
INSERT INTO asset_tags_new SELECT asset_id, tag_id FROM asset_tags;
DROP TABLE asset_tags;
ALTER TABLE asset_tags_new RENAME TO asset_tags;
CREATE INDEX idx_at_asset ON asset_tags(asset_id);
CREATE INDEX idx_at_tag   ON asset_tags(tag_id);
```

重建时先 `PRAGMA foreign_keys = OFF`（该 PRAGMA 在事务内无效，必须在事务外），重建完再开回来。
`openDb` 本来就 `foreign_keys = ON`，所以建表后 CASCADE 立即生效。

**为什么值得动表结构**：第 8 批 M8-03 会大量删素材记录（"文件已丢失"改语义），
不做外键就得在每个删除点手写清理，漏一处就是永久孤儿。

## 7. 验收检查点

### 7.1 新增 `[25]` 段（实际落地 10 组 / 83 条；344 → 427，另有 2 条回归钉子）

**⑥ 外键**
- `PRAGMA foreign_key_list(asset_tags)` 两行、`on_delete` 均为 `CASCADE`
- 删一条素材 → 它的关联行同步消失（**不再留孤儿**）
- 删一个标签 → 该标签的关联行同步消失
- 历史孤儿（手工插一条指向不存在素材的行）→ 重开库后被清掉

**② 包信息可编辑**
- 只改类别 → `folder_path` 不变、磁盘文件数不变
- 改名称 → 旧文件夹消失、新文件夹存在、里面文件一个不少
- 改名称 → 该项目下所有 `assets.abs_path` 指向新路径、`asset_tags` 条数不变
- 改项目 → 包文件夹落在目标项目文件夹下、`project_id` 变了、文件一个不少
- 目标项目里已有同名包 → 自动 `-2`，不覆盖

**③ 待归类归位**
- 游离包（`project_id = NULL`）→ 归位后进项目文件夹、`project_id` 有值、文件一个不少

**④ 解绑 / 还原**
- 解绑后：项目 `archived = 1`、文件夹在 `_已解绑的项目` 下、`listPacks()` 不含其包、`countUnassigned()` / `listAssets()` 不含其素材、total 统计也不含
- 解绑前后：磁盘文件数不变、`asset_tags` 条数不变
- `listUnboundProjects()` 的包数与占用对得上
- 允许只剩最后一个项目时拒绝解绑
- 还原后：回工作区根、`archived = 0`、包视图又能看到、文件一个不少
- 【回归钉子】解绑后跑一遍 `initWorkspace`（模拟任意 IPC 调用），根目录不得给已解绑项目重建空壳文件夹、`_已解绑的项目` 里原封不动

**⑤ 删除进回收站**
- 项目记录消失、该项目的包记录消失、项目文件夹落在 `_回收站` 下
- 磁盘文件数不变（一个不少）
- 该项目的素材记录已清、`asset_tags` 无孤儿
- 老分支（转移 / 待归类 / 拒绝删最后一个）行为不变
- 留痕 JSON 存在

**① 包记录自动清理**
- 删掉包文件夹 → 扫描后记录摘除，`cleanedPacks > 0`
- 包文件夹还在 → 一次也不清（幂等：连扫两次第二次为 0）
- 解绑项目的包 → 文件夹挪到 `_已解绑的项目` 后依然不清理（豁免生效）
- 根目录读不到（传一个不存在的根）→ 一条都不清理
- 留痕 JSON 里能查到被清掉的包名与路径

| 项 | 说明 |
|---|---|
| 删项目会删记录 | 用户明确要求；文件全在 `_回收站`，且删前留痕 JSON 可查 |

| 解绑项目的包在界面彻底隐身 | 想找回只能走「已解绑」入口或资源管理器 —— 这是"留底但不碍眼"的代价 |
| 包改名会改用户看得见的文件夹名 | 与项目改名同规矩；改前 `backupDb` |

## 11. 验收后补丁：左栏标签计数口径（2026-09-29，用户实测反馈）

### 11.1 用户的问题

> 左侧「筛选标签」下标签后面的数字，是包数还是物料数？是所有项目还是选中项目？感觉不太对。

实测确认（布景：2 个项目 2 个包 3 个文件，都贴同一个标签）：

| 现象 | 实测 |
|---|---|
| 数字含义 | **贴了该标签的物料（文件）条数**，不是包数（包只有 2 个，数字是 3） |
| 范围 | **全库**，不随左栏选中的项目变化（选中甲项目：数字 3、右侧只有 2 条） |
| 解绑项目后 | **数字纹丝不动**（还是 3，点开只剩 2 条）← 这条是真 bug |

### 11.2 两个问题、两个定性

1. **解绑后数字不减 = 真 bug**。第 7 批做「解绑后软件里全隐身」时列的查询点清单（§2.3 那张表）**漏了 `listTagDimensions`** —— 它是全项目最后一处没过滤 `archived` 的查询。数字虚高、与点开结果对不上。
2. **选了项目后数字对不上 = 口径设计问题**。数字是全库口径、右侧列表是项目口径，天生对不上。

### 11.3 用户拍板（2026-09-29）

1. **数字跟随当前项目**：选中项目 → 按该项目算；「待归类」→ 只算没挂项目的包；「全部」→ 全库。
2. **0 条的标签仍然列出、置灰**（不隐藏 —— 别让用户以为标签丢了）。

### 11.4 落地

| 改动 | 内容 |
|---|---|
| `workspace.ts` | `VISIBLE_PACK_SQL` 导出共用（别再各写一份） |
| `tags.ts` | `listTagDimensions(scope?)`：计数 SQL JOIN packs + visibility + scope 过滤；`projectId: null` 用 `k.id IS NOT NULL AND (k.project_id IS NULL OR 悬空)` —— **必须排除未归属散文件**，否则会算进「待归类」 |
| `ipc.ts` / `preload` / `shared/types` | `tag:dimensions` 透传 scope（不传 = 全部） |
| `App.tsx` | `loadTags(scope)`；新增 effect：`projectFilter` 变化 → 重算标签；`tagScope()` 把左栏筛选映射成 scope |
| `TagPanel.tsx` | 0 条加 `.zero` 置灰；悬停提示写明范围（`海报 · 「海南升学规划中心」范围内有 2 条素材`）；维度标题右边的数字加 title（那是"有几个标签"） |
| `TagManagerModal.tsx` | 删除确认文案明确**全库**口径（含已解绑项目 —— 删标签确实会波及它们） |

**刻意不改的**：`tagUsage`（删除标签时的用量告知）保持**全库口径** —— 删除会波及已解绑项目里的关联，必须如实告知；界面文案已写明"全库共 N 条（含已解绑项目里的）"。
