# GitHub 仓库功能说明（对照本仓库 VellumDesk）

> 顶上那一排标签（Code / Issues / Pull requests / Agents / Actions / Projects / Security and quality / Insights / Settings）
> 是 GitHub 给**一个仓库**的九个功能面——不是九个都必须用。
> 下面每条都标了「**咱们要不要用**」，按 VellumDesk 的实际情况（Electron 桌面软件、单人 + AI 协作、公开仓库、手工出包）来写。

---

## 一、Code（代码）

**是什么**：仓库的主页。文件树、当前分支 / 标签（tag）切换、每个文件的修改历史、README 渲染，右侧 About 里能看到描述、Releases、贡献者。

**常用操作**：
- 绿色 `Code` 按钮 → 拿克隆地址（HTTPS / SSH），或直接 **Download ZIP**（下载源码）
- 点进某个文件 → `History` 看这个文件被谁、在什么时候改过
- 分支下拉框里能切换分支和 tag（比如切到 `v1.8.2` 看当时那版代码）

**咱们**：日常就在这个页面看代码和让 AI 推代码。README 是别人进来第一眼看到的东西——发版后把「怎么装、怎么用」写进 README 比较值。

---

## 二、Issues（议题 = 任务 / 缺陷清单）

**是什么**：一条条可以讨论的条目。能贴图、加标签、指派给某人、关联到某次提交或某个 Pull Request；每条都是一个独立的讨论串。

**常用操作**：
- `New issue` → 写标题 + 详细描述（能拖进截图）
- 提交信息里写 `fixes #12` → 合并后自动关掉第 12 条
- 用标签分类（bug / 需求 / 待确认），用 Milestone 归到某个版本

**咱们**：**建议开始用**。你反馈的 bug、临时想到的需求都丢这儿，比记在微信群里强；下次开工 AI 直接把 Issues 列表当待办清单读。

---

## 三、Pull requests（PR = 提改动的申请单）

**是什么**：把某个分支的改动「申请合并」到 `main`（或别的分支）。带逐行 diff、评论、审查结论（Approve / Request changes），以及自动检查（测试、构建）的结果。

**常用操作**：
- 从 `feature/xxx` 分支开 PR → 在 `Files changed` 里逐行看改了什么、点行号写评论
- 审查通过 → `Merge pull request` 合并（可选合并方式：merge / squash / rebase）

**咱们**：现在是一条线直接推 `main`。以后如果**多人或多个 AI 会话同时改**，建议走「开分支 → 提 PR → 审一眼 → 合并」：好处是**合并前能看到全部改动**，出问题能整单回退。单人开发也可以只把 PR 当「改前对照」用。

---

## 四、Agents（AI 代理任务面板）

**是什么**：GitHub 在 2025 年上线的新功能（公开预览）。把任务派给 **Copilot coding agent**，它在 GitHub 云端的沙箱里自己开分支、写代码、跑测试，最后开一个**草稿 PR** 等你审核；进度、日志、文件改动都能在面板里看。也能把某个 Issue 直接指派给 Copilot 让它干。

**前提**：需要 **Copilot 订阅**（Pro / Pro+ / Business / Enterprise），并且它干活会消耗 GitHub Actions 的分钟数。它只能往自己创建的分支推（`copilot/*`），PR 必须人工审核才能合并。

**咱们**：**暂时用不上**——你们已经有本地 AI 协作流程，而且这个要额外付费订阅。知道它是干什么的就行。

---

## 五、Actions（自动化 = CI/CD）

**是什么**：让 GitHub 的服务器替你跑流程。配置写在小文件里（`.github/workflows/xxx.yml`），触发条件可以是「推代码 / 开 PR / 打 tag / 定时」。

**典型用途**：自动跑测试、自动构建、自动把产物挂到 Release 上。

**咱们**：**可以以后做，但现在有个硬前提没解决**——`resources/ffmpeg`（约 268 MB）和 `resources/wecom-cli/wecom-cli.exe`（10 MB）**都不在仓库里**（它们被 gitignore 排除，打包时靠本地手动带进去）。云端构建拿不到这些文件，自动出的包就是残包（正是 1.8.1 那次翻车的原因）。所以目前**手工出包（本地两步法）+ 手工发 Release** 更稳。

---

## 六、Projects（项目板）

**是什么**：看板（Todo / In progress / Done），卡片可以是 Issue、PR，也可以是随手写的笔记；还能切成表格视图。属于「账号级」功能，可以挂到具体仓库上。

**咱们**：等 Issues 用起来了、条目一多，配一个 Projects 板排期很直观。注意你们现在用**企微智能表格**管的是「素材工单」；这个板适合管**软件开发待办**，两回事别混。

---

## 七、Security and quality（安全与质量）

**是什么**：安全相关的一组功能——依赖漏洞告警（Dependabot）、代码扫描（CodeQL）、**密钥泄露扫描（Secret scanning）**、安全策略文件（SECURITY.md）。

**咱们**：**建议至少确认「Secret scanning」是开着的**。仓库是公开的，万一有人（或某个脚本）把企微密钥、token 之类提交上去，这个功能会报警；公开仓库这项默认自动开启。你们的企微凭据存在系统目录（`~/.config/wecom`）、不入库，这个做法是对的，继续守着。

---

## 八、Insights（洞察 = 统计）

**是什么**：仓库的统计面板——提交活跃度、贡献者、代码频率、访问 / 克隆流量、依赖图、网络图（提交时间线）。

**咱们**：想知道「这个公开仓库被多少人看过、被克隆过多少次」就看 **Traffic**；也能看谁在贡献代码。

---

## 九、Settings（设置，只有管理员可见）

**是什么**：仓库名、**可见性（public / private 一键切换）**、协作者与权限、**分支保护规则**、Webhook、Secrets、Pages，最下面是 Danger Zone（改名 / 转移 / 归档 / 删除）。

**咱们**：三件最值得动的：
1. **分支保护**（`Rules` / `Branches` → 给 `main` 加规则）：防止误推、误删 `main`；可以要求「必须走 PR」才准合并。
2. **Collaborators（协作者）**：给同事开只读或写权限。**只是看代码不需要协作者**（公开仓库人人可看），需要提交代码才要加。
3. **仓库描述 / Topics**：About 右上角齿轮，或 Settings 顶部的 Description——你打算调整的就是这里。

---

## 附：优先级建议

| 功能 | 建议 | 理由 |
|---|---|---|
| **Releases** | ✅ 已在用 | 把安装包发给同事，链接固定可反复下载 |
| **Issues** | ✅ 建议开始用 | 收 bug、记需求，比微信群可靠，AI 能直接当待办读 |
| **Settings → 分支保护** | ✅ 建议开 | 保护 `main`，防误推误删 |
| **Security → Secret scanning** | ✅ 确认已开 | 公开仓库防密钥泄露 |
| **Projects** | ⭕ 可选 | 待办多了再上，别和企微工单表混 |
| **Pull requests** | ⭕ 多人协作时启用 | 合并前可审、可整单回退 |
| **Actions** | ⏸ 暂缓 | ffmpeg / wecom-cli 不在仓库里，云端出包会出残包 |
| **Agents** | ⏸ 暂不需要 | 要 Copilot 付费订阅 |
| **Insights** | 👀 偶尔看 | 看流量与活跃度 |
