## 0. 一句话

把「审核」从「集中到审核人本人、手动看图审」改成「软件自动把物料送进 WorkBuddy，由 WorkBuddy 的多模态 Skill 审稿、出报告、回传」，本质是给「营销中心-素材库」加一条通往 WorkBuddy 的**连接器**，让 AI 审稿变成一条可（半）自动化的流水线。

## 1. 需求源头（用户原话，2026-10-04）

> 之前讨论过审核的问题，现在想「不集中到我这儿审核了」，能不能做一个「软件和 WorkBuddy 的连接器」，把物料自动提到 WorkBuddy 里，用它的 Skill 审核。后续可能做。

## 2. 与 docs/21 的关系（承接 + 转向）

`docs/21` 定的是「审核人 = 用户本人，手动在 WorkBuddy 里审，手敲评语」，AI 审稿是**人触发的辅助动作**。

本文是把这一步往前推：**不再靠人手动切 WorkBuddy、手动说「审这张图」**，而是靠一个「连接器」把物料自动送进 WorkBuddy、由 Skill 自动（或半自动）审。二者关系：

| | docs/21 审核平台 | docs/23 连接 WorkBuddy 审稿 |
|---|---|---|
| 审核主角 | 人（用户本人） | AI（WorkBuddy Skill），人退到「复核 / 放行」 |
| 物料怎么进 WorkBuddy | 人手动切过去、手动看图 | 连接器自动送 |
| 审稿触发 | 人手动说「审一下」 | automation 定时扫（全自动）或人点一下（半自动） |
| 结果回传 | 人手动选报告 + 填评语 | 报告 + 评语自动回写 |

> 结论：本文是 docs/21 §9 里那句「以后可升级自动审」的正式立项方向；如果走通，docs/21 的「手动审」降级为兜底，主体换成自动化。

## 3. 核心链路

```
营销中心-素材库（设计师点「送审」）
        │  送物料（成品图 + 工单信息）
        ▼
    【连接器】  物料自动进 WorkBuddy
        │
        ▼
WorkBuddy 审稿 Skill（多模态读图 → 按标准挑问题 → 出 HTML 报告 + 评语）
        │  回传
        ▼
  软件（读回报告 + 评语，展示给设计师）
```

「连接器」不是 WorkBuddy 里现成的可点项——它是两个独立应用（素材库桌面软件 ↔ WorkBuddy Agent）之间的通道，要自己搭。整件事要解决**三件事**：

1. **物料怎么过去**（传输通道）；
2. **谁触发审核**（触发方式）；
3. **结果怎么回来**（回传 + 软件回显）。

## 4. 三个关键决策点（当前全部待用户拍板）

### 4.1 传输通道：物料怎么「自动提到」WorkBuddy

| 通道 | 做法 | 适合 | 代价 |
|---|---|---|---|
| **A. 本地目录** | 软件点送审 → 成品图 + 工单信息写到约定目录（如 `D:\审稿队列\`），WorkBuddy 读 | 本机单人（软件和 WorkBuddy 同一台机器） | 最省事，但**跨机器 / 多设计师不适用** |
| **B. 企微微盘** | 软件上传微盘共享文件夹，WorkBuddy 经 wecom-cli 读 | 多人、多机 | 微盘使用规范卡点仍在（docs/21 §7） |
| **C. WorkBuddy 云服务** | 软件传 WorkBuddy 云存储，Skill 读 | 想彻底摆脱本机依赖 | 架构最重，需看云服务开放程度 |

### 4.2 触发方式：全自动 vs 半自动

- **全自动**：软件点送审 → WorkBuddy **automation（定时任务）** 定时扫目录 → 自动用 Skill 审 → 报告自动回传。人最后只看结果、只在「审不过」时介入。
- **半自动**：软件点送审 → 生成待办 / 通知 → 人打开 WorkBuddy 手动说「审这批」→ Skill 跑。灵活，但没省掉「人」这一环。

### 4.3 连接器形态：WorkBuddy 这边长什么样（软件端要开发什么）

| 形态 | 做法 | 开发量 |
|---|---|---|
| **自研 Skill + automation（倾向）** | 用 skill-creator 写「审稿」Skill（固化审稿标准 → 多模态读图 → 出 HTML 报告 → 回传），automation 定时触发；软件端只做「送审 / 收报告」 | 小 |
| MCP server | 软件起本地 MCP 服务，WorkBuddy 经 MCP 工具直接读物料库 | 大 |
| 纯文件约定 | 软件只负责放文件，WorkBuddy automation 只负责读文件，不写接口 | 最小 |

## 5. 倾向建议：先走最轻闭环验证

别一上来做「重连接器」。先走**零云、零微盘、零 MCP 接口**的最轻闭环，验证「WorkBuddy 审稿 Skill 到底好不好用、报告格式满不满意」：

> **软件点「送审」→ 写本地目录（通道 A）→ 自研审稿 Skill + automation 定时扫（4.3 倾向项）→ 全自动审 → 报告 HTML + 评语回写目录 → 软件读回显。**

等审稿质量和流程定了，再决定要不要升级到微盘（多人）或云服务（跨机）。

## 6. 待确认项（决定路线走向，当前全部未定）

- **单人本机 vs 多人多机**：决定走通道 A 还是 B/C。这是最优先要定的问题。
- **全自动 vs 半自动**：人要不要在「送审」和「报告回传」之间过一眼。
- **审稿标准从哪来**：Skill 里的审稿规则（改什么 / 缺什么 / 品牌规范）需要用户提供或确认，这是 Skill 质量的关键。
- **报告回传后软件如何展示**：HTML 报告查看 / 下载，评语是否进企微表字段（复用 docs/22 缩略图 image 列那套写回能力）。

## 8. 刻意不做（当前讨论范围）

- 不买模型 API / 不内嵌 AI 引擎——审稿能力全部来自 WorkBuddy 现有 Skill。
- 不做「重连接器」（MCP server / 云服务）起步，先用本地目录 + Skill + automation 跑通。
- 不做多级会签 / 设计师互相审（沿用 docs/21「审核人 = 一人」基调，人退到复核位）。
- 版本号、迁移号、落库表结构：留待正式施工方案再定（本稿只锁方向，不锁实现细节）。
