## 0. 一句话

把第 17 批的「单设计师指派」升级为「多设计师指派」：一张工单可以指派给**多位**设计师，**每位被指派的设计师都在自己的机器上建出各自的任务包**（任务名用后缀区分），写回企微表的「设计师」成员列（多选）。

## 1. 需求源头（用户原话，2026-10-04）

> 部分大型工作单人难以完成，需要多人协作。将指派下拉改为多选，被指派的设计师都需要建新任务包，但任务名后缀可以有所区别，后缀最好可以由指派端编辑并作为设计师端任务包命名后缀。UI 更新尽量不要太啰嗦。

## 2. 核心结论：两个技术问题先钉死

### 2.1 多选成员列的读写 API（第 0 步真表实探，2026-10-04 已钉死）

> 实探对象：`营销物料设计工单队列（2.0）` 两个子表的「设计师」列（真表，非 mock）。

- **列类型**：`field_type = user`，`property_user.is_multiple = true` —— **「设计师」列本身就是多选成员列，无需改表结构**。
- **读侧**：成员列读回是数组 `[{userId, userName}, ...]`，空单元格缺键（代码里 `takeUserNames` 早已证明，零风险）。
- **写侧（多值，已实测）**：写回 `"设计师": [{ "userId": "<a>" }, { "userId": "<b>" }]`（嵌套对象数组、多个元素）→ `errcode=0` 且读回 `[{userId:a,userName:…},{userId:b,userName:…}]`，两个人都存进去了。
- **写侧（单值，第 17 批已钉死）**：`[{ "userId": "<a>" }]`。
- **⚠️ 边界（实测踩到，重要）**：成员列**无法通过 `records update` 清空**——传 `[]` 或 `null` 都会被服务端"人员字段全部被剔除、已跳过更新"（errcode 仍是 0，但实际没清）。**推论**：软件"移除某位设计师"只能写回**剩余的非空数组**（≥1 人）；"移除到最后一个人/清空"这个操作 API 层做不到，软件**不提供**「清空到未指派」的入口，UI 上最后一个人不可 × 移除，提示去表格手工清。

### 2.2 「自定义后缀」能不能仅靠 wecom-cli 实现 —— **不能干净地实现**

- 后缀要传到**每个设计师自己的机器**，而多机之间唯一汇总通道是企微表。
- 企微成员列值结构固定为 `{userId, userName}`，**塞不进自定义后缀字段**。
- 要传自定义后缀，只能加一个文本列存映射串（如 `张三:主视觉;李四:延展`）——脏、同事表格里难维护、手改易坏，违背「UI 别啰嗦」与「表格是唯一权威但别逼人填难懂的东西」。

**推荐路 A：后缀 = 设计师姓名**。设计师端建任务时用本机身份姓名做后缀（`物料名称-张三`），零传递、零成本、天然区分，完全不需要 wecom-cli 传任何新东西。

## 4. 落库结构（迁移 14）

```sql
-- 子表：一张单的多位设计师（ticket_no 为逻辑键，与 tickets.UNIQUE(ticket_no) 对齐）
CREATE TABLE IF NOT EXISTS ticket_designers (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  ticket_no TEXT NOT NULL,
  userid    TEXT NOT NULL,
  name      TEXT,
  seq       INTEGER NOT NULL DEFAULT 0,  -- 顺序，0 = 主设计师
  FOREIGN KEY(ticket_no) REFERENCES tickets(ticket_no) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_td_ticket ON ticket_designers(ticket_no);
CREATE INDEX IF NOT EXISTS idx_td_userid ON ticket_designers(userid);
```

**为什么子表不 JSON**：可查、可索引、无并发写冲突，与「数据要能 SQL 对账」的项目一贯风格一致；JSON 列查询/统计别扭。

**单值列去留**：`designer_userid / designer_name` **保留**，语义降级为「主设计师冗余」——每次写子表后同一事务里回写（空集合 → NULL）。理由：① 未指派判定、顶栏徽标、列表行显示等现有查询**零改动**；② 单一真源仍是子表，冗余列由引擎强制同步，不漂移。

**老数据迁移**：把现有 `designer_userid IS NOT NULL` 的单值记录搬进子表（seq=0），单值列原样保留。

## 5. 同步引擎改动（tickets.ts）

1. **读多值**：新增 `takeUsers(v)` → `{userid,name}[]`（`takeUser` 保留给申请人等单值列，不动）。
2. **落子表**：`extractRow` 产出设计师数组 → upsert 后 `replaceTicketDesigners(ticket_no, list)`（先删后插，同一事务）。
3. **建任务条件链**：`本机身份 ∈ 设计师集合`（查子表 `SELECT 1 FROM ticket_designers WHERE ticket_no=? AND userid=?`）。命中 → 建任务，任务名带后缀（§6）。
4. **改派检测**：原来「designer 变别人 → 标 reassigned_to」改为「**本机身份被移出集合** → 标 reassigned_to（任务保留）」。本机仍在集合内 → 不标。
5. **候选池** `listDesignerCandidates`：改读子表去重 + 在办计数（子表 JOIN tickets）。
6. **未指派计数** `unassignedTicketCount` / `newUnassigned`：沿用 `designer_userid IS NULL`（主设计师冗余列与集合同源，空集合必 NULL）——零改动。
7. **多值指派**：`executeAssignDesigner` 改为 `executeAssignDesigners(ticket_no, [{userid,name}...])`，本地即时写子表 + 回写冗余列 + 标 pending + 留痕；写回失败保 pending，下次同步补写；冲突三态沿用 §19。

## 6. 任务名后缀规则（决策点 #1，见 §8）

- **路 A（推荐）**：后缀 = 本机身份姓名。多设计师（集合 ≥ 2 人）时任务名 = `物料名称-姓名`；**单设计师时任务名 = 物料名称（不变，向后兼容）**。
- 判定依据：设计师端同步时该单的集合大小。若后续从 1 人变多人，先建的旧任务**不改名**（铁则：不悄悄动磁盘），只有新加入者用带后缀的名建。
- **路 B（自定义后缀）**：需要加文本列存映射串，本方案不展开，仅在 §8 供拍板。

## 12. 刻意不做

- 不做自定义后缀（路 B，除非你拍板要）
- 不做自动分配 / 负载均衡（延续铁律③，派谁由人定）
- 不做指派历史流转（只记最后一次）
- 不做通讯录接口（候选池仍用历史设计师去重）
