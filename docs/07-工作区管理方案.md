把「工作区」从一个写死的单一路径，变成**一份可管理的工作区列表**（A1），

## 4. 现状技术事实（已逐项核源码，全部为施工依据）

1. **数据库在工作区内部**：`<root>/_system/media.db`，WAL 模式。缩略图在 `<root>/_thumbs/`。  
   → 搬文件夹 = 库和缩略图一起走，不存在「数据在 C 盘、素材在 D 盘」的半拉子状态。
2. **缩略图存相对路径**：`assets.thumb_path = "_thumbs/xxx.webp"`（`thumbs.ts` 用 `join('_thumbs', name)` 生成），读取时才 `join(root, thumb_path)`。  
   → 搬家**不需要**改缩略图路径。设计本来就对。
3. **素材同时存两种路径**：`assets.rel_path`（相对根）、`assets.abs_path`（绝对，且是 UNIQUE 键）。
4. **包只存绝对路径**：`packs.folder_path`（绝对，UNIQUE）。
5. **`openDb` 是单例**：`if (db) return db` —— 进程内只会真正打开第一个库。
6. **`closeDb` 早已实现但全项目零调用**（见 §5）。
7. **`scanAll` 按 `abs_path` upsert，并剪枝掉磁盘上不存在的记录**。
8. 配置文件 `workspace.json` 存在 appData 目录（`electron` 的 `userData`），不在工作区内 —— 避免鸡生蛋。
9. 启动流程：`app.whenReady()` → `getWorkspaceRoot(userData)` → `initWorkspace(root)` → 后台补媒体元信息。**无单实例锁，无 relaunch**。

### 4.1 由事实 5/7 推出的硬结论

**搬家后绝对不能靠「刷新扫描」重建索引。** 因为：

- 重扫时新绝对路径不在库里 → 按 `ON CONFLICT(abs_path)` 走 INSERT → **生成新的 asset.id**
- 原记录（旧 abs_path）在剪枝阶段被 `DELETE`（`scanAll` 第 4 步）
- `asset_tags` 是裸关联表（无外键约束），删 assets 不会级联 → **标签关联变成孤儿，用户的标签全丢**
- `packs.folder_path` 同样对不上 → 包被**重复登记一份**

**唯一正确做法是「路径重写」：把库里的绝对路径前缀换成新根，保住 asset.id 与 pack.id。** 这是 §6 的全部理由。

## 5. 必修的现存 bug（本批的前置项）

### BUG-1：切换工作区后进程内仍读写旧库

- `db.ts:84` 的 `closeDb()` 定义完好，但**全项目没有任何调用点**
- `openDb()` 首行是 `if (db) return db`
- 后果链：
  1. `ws:setRoot` / `ws:pickRoot` 切换后，**所有数据库操作仍指向旧库**
  2. `initWorkspace(新位置)` 里 `openDb` 提前返回 → **新位置不会创建 `media.db`**（只会建出 `_thumbs`）
  3. 界面却提示「工作区已切到 XXX」并重新加载 —— 加载的是旧库数据
  4. **重启软件后才真正生效**；若新目录是空的，用户看到一个全新空库，会以为素材丢了（正面撞铁则「绝不悄悄扔掉用户放的东西」）
- 定级：**必修，且必须先修** —— 不修，A1 的「切换」是假的，B2 的「搬移」会把库搬丢
- 修法：切换/搬移路径上严格按 `closeDb() → 改配置 → resetWorkspaceState() → initWorkspace(新根)` 的顺序执行（§8）

### BUG-2：选中「搬过来的库」时不会修正路径

- 用户把工作区文件夹复制到新盘后，用「更改位置」指过去：
  - `abs_path` 全是旧根 → 预览/打开文件全部失效
  - 点「刷新扫描」→ 触发 §4.1 的连锁反应（标签丢、包重复）
- 定级：**必修**，即需求文档 M8-05，本批核心交付

## 6. 核心设计：路径重写

### 6.1 旧根怎么算出来

库里**没有**记录工作区根，但每条素材都存了 `rel_path`，而 `abs_path` 一定以它结尾：

```
oldRoot = abs_path.slice(0, abs_path.length - rel_path.length)  → 去掉尾部分隔符
例：abs_path = D:\素材工作区\包名\01-成品\a.jpg
    rel_path = 包名\01-成品\a.jpg
    oldRoot  = D:\素材工作区   ✓
```

**一致性校验（必须做）**：对全部 assets 逐一计算 oldRoot，**必须全都相同**。

- 全部相同 → 正常，可重写
- 出现两个以上不同值 → 说明库里有跨根数据（异常库），**拒绝自动重写**，如实报错给用户，让他手工确认
- 一条 assets 都没有 → 退而用 `packs.folder_path` 的 `dirname` 反推；再没有 → 视为空库，无需重写

### 6.2 重写顺序（两步走，规避 UNIQUE 冲突）

`abs_path` 与 `folder_path` 都带 UNIQUE 约束。虽然理论上「旧值集合以 oldRoot 开头、新值集合以 newRoot 开头」两集合不相交，但若库里存在**混合状态**（部分记录已是新根，例如用户重复执行过），单条 UPDATE 中途会撞 UNIQUE。

故采用**两步走 + 单事务**：

```sql
BEGIN;
-- 第一步：全部改成不可能碰撞的临时值
UPDATE assets SET abs_path = '#migrating#' || id;
UPDATE packs  SET folder_path = '#migrating#' || id;
-- 第二步：写入目标值
UPDATE assets SET abs_path = @newRoot || '\' || rel_path;
UPDATE packs  SET folder_path = @newRoot || '\' || <原 folder_path 去掉 oldRoot 前缀的部分>;
COMMIT;
```

同时把 `rel_path` 里的分隔符统一（历史库可能有 `/`）。

### 6.3 重写前必须自动备份

重写是**改库**操作，动的是用户的目录数据。铁则「绝不悄悄扔掉用户放的东西」的落地：

1. `closeDb()`（先关库，让 WAL checkpoint 落盘）
2. 把 `_system/media.db`（及 `-wal` / `-shm` 若存在）复制到 `_system/backup/media.db.<时间戳>.bak`
3. 备份成功后才允许执行重写；备份失败则**中止**，不冒险

`_system/` 下划线开头，扫描自动跳过，不会污染用户视图。

### 6.4 重写后自检

重写完成后遍历一次 `abs_path`，用 `existsSync` 检查落空情况：

- 落空数 = 0 → 报告「全部 N 个文件核对通过」
- 落空数 > 0 → **如实列出**（很可能是用户自己在资源管理器删过），并说明「只影响预览，索引记录未删」

**绝不自动删除任何记录** —— 与既有 `scanAll` 的「铁则：只登记，永不删除用户文件」保持一致。

## 7. 配置结构 v2（含向后兼容）

### 7.1 新结构

```json
{
  "version": 2,
  "activeId": "ws_m1a2b3c4",
  "workspaces": [
    {
      "id": "ws_m1a2b3c4",
      "name": "素材工作区",
      "root": "D:\\素材工作区",
      "addedAt": "2026-09-25T03:00:00.000Z",
      "lastOpenedAt": "2026-09-25T03:10:00.000Z"
    }
  ],
  "workspaceRoot": "D:\\素材工作区"
}
```

### 7.2 末行那个 `workspaceRoot` 是刻意的双写，不是冗余

两个理由，都必须满足：

1. **第 4 批的验收断言直接读它**（`accept.ts:1290`：`JSON.parse(配置).workspaceRoot === goodDir`）。改掉会让既有回归失败。
2. **用户装回旧版本软件时不至于炸**：旧版 `readConfiguredRoot` 只认 `workspaceRoot`；若读不到，旧版会走「首次启动」逻辑自动择址，**可能凭空建一个新工作区，让用户以为数据没了**。双写让旧版仍能正确读到路径。

### 7.3 老配置自动升级（读时完成，无需用户操作）

读到 `{ "workspaceRoot": "X" }`（无 `workspaces`）时：

- 生成一个 `id`，`name` = `basename(X)`，`addedAt` = 当前时间
- `activeId` 指向它
- **不立即回写**；等到下一次正常的写配置时机（首次择址 / 切换 / 添加）一并写成 v2 —— 避免「只读一次操作就改了用户文件」

### 7.4 兼容性约束（必须保住，否则打破既有回归）

下列导出函数的**签名与语义保持不变**：

| 函数                                                            | 保持的行为                                     |
| ------------------------------------------------------------- | ----------------------------------------- |
| `isUsableWorkspace(root)`                                     | 建 `_system` + 写删 `.write_probe`，不留痕       |
| `resolveWorkspace(appDataDir, documentsDir?, preferredRoot?)` | 返回 `{root, ok, note}`；**已配置但不可用时绝不改配置文件** |
| `getWorkspaceState(appDataDir, documentsDir?)`                | 进程内缓存（同参数返回同一引用）                          |
| `resetWorkspaceState()`                                       | 清缓存，下次重新解析                                |
| `saveWorkspaceRoot(appDataDir, root)`                         | 写「当前工作区的根」，同时双写 `workspaceRoot` 字段        |
| `getWorkspaceRoot(appDataDir, documentsDir?)`                 | 返回当前工作区的根（旧调用点全部继续可用）                     |

## 8. 工作区生命周期

### 8.1 添加（A1 的「＋ 添加工作区」）

用户选一个目录（`dialog.showOpenDialog` + `openDirectory` + `createDirectory`；**选中的目录本身就是工作区根**，不自动建子文件夹）。按目录状态分三种走法：

| 目标目录状态                                       | 行为                                                       |
| -------------------------------------------- | -------------------------------------------------------- |
| 不存在 / 空目录                                    | 初始化新工作区（建 `_thumbs`、`_system`、空库）→ 加入列表 → 切过去            |
| 已有 `_system/media.db`，且路径自洽（oldRoot === 该目录） | 直接登记进列表 → 切过去                                            |
| 已有 `_system/media.db`，但路径指向别处（oldRoot ≠ 该目录） | **弹确认框**说明「这个目录里有一个搬过来的库，记录还指向旧位置」→ 用户同意则先备份再重写（§6）→ 切过去 |
| 已有 `_system/media.db`，但算出多个不同 oldRoot        | **拒绝**自动重写，如实提示异常，让用户手工确认                                |
| 已在列表中                                        | 直接切过去（不重复添加）                                             |

### 8.2 切换

严格四步，顺序不可换（这是 BUG-1 的修法）：

```
1. closeDb()                        // 关掉旧库连接
2. 写配置：activeId = 目标 id
3. resetWorkspaceState()            // 丢缓存
4. initWorkspace(新根)              // 此时 openDb 才会真正打开新库
```

任何一步失败都要给出人话错误，并且**不要留下「配置指向新位置、连接还开着旧库」的中间态**。

### 8.3 搬移位置（B2：同盘）

界面上只对**当前活动工作区**提供「搬移位置」。流程：

```
1. 用户选目标父目录
2. 新根 = 目标父目录 + 当前工作区文件夹名
3. 同盘判定：fs.statSync 的 dev 相同（比盘符比较更准，能处理挂载点）
   - 不同盘 → 明确拒绝 + 给出跨盘引导（§10），不做任何改动
4. 目标已存在 → 拒绝（绝不覆盖）
5. 展示确认：从 X 搬到 Y
6. closeDb()
7. renameSync(旧根, 新根)          // 同盘 = 文件系统层改个名字，瞬间完成
8. 写配置：该工作区 root = 新根
9. resetWorkspaceState() → openDb(新根)
10. 备份 + 路径重写（旧根 → 新根）+ 自检
```

**回滚保证**：第 7 步 `renameSync` 是原子操作，失败即「什么都没变」，配置未改、库未动。第 10 步若失败，`_system/backup/` 里有备份。

**绝不删除任何东西**：搬移只做 rename，新旧位置不会同时存在两份副本，也不产生垃圾。

### 8.4 从列表移除

- 仅从 `workspaces` 数组删掉一条记录，**磁盘上一个字节都不动**
- 删除前弹确认，文案明确写「只是从软件列表里去掉，你的文件夹和素材完好无损」
- 不允许移除最后一个工作区（列表至少留一个，否则软件无处可去）

## 10. 跨盘场景（明确不做软件内复制）

**不做**，理由要写清楚（免得以后有人以为是漏做）：

- 跨盘 = 真复制。几百 GB 要走几十分钟到几小时，软件内自研复制器需要处理：磁盘空间预检、进度与取消、中断续传、超长路径、非法文件名、占用文件……每一条都是坑，而**系统资源管理器/专业复制工具已经把这些都做好了**，且有进度条、可暂停、卡住用户能看见。
- 需求文档的设计意图本就不是软件搬文件：M8-05 原文是「**批量修改库的根目录路径**」，非功能需求说「整个库文件夹**拷到**新电脑即可恢复」。

**软件内给用户的引导文案**（选到不同盘时弹出）：

> 目标位置在另一个磁盘，软件不搬跨盘。  
> 请这样做：用资源管理器把整个「素材工作区」文件夹**复制**过去（复制完先别删原来的），  
> 然后回到软件点「＋ 添加工作区」，选那个新文件夹 —— 软件会自动把库里的路径改成新位置。

同时把「一键备份」（M8-04 完整版）留在后续批次。

## 15. 与既有断言的兼容性（施工红线）

`accept.ts` 第 [22] 段有 6 项断言锁着工作区行为，**必须原样通过**：

1. `isUsableWorkspace(goodDir)` 为真，且 `_system` 被建好、探针无残留
2. 目录建不出来时判定不可用（不误判）
3. `resolveWorkspace` 首次择址用首选位置，且配置文件里 **`workspaceRoot === goodDir`**
4. 首选不可用时兜底到「文档/素材工作区」
5. **【铁则】已配置但连不上时，配置文件一个字都没被改**
6. `getWorkspaceState` 缓存返回同引用；`resetWorkspaceState()` 后返回不同引用

→ 本批新增断言统一编号 `[23] 第 5 批 E-01：工作区管理与迁移`。

## 17. 已知代价与风险

| 项 | 说明 | 处理 |
|---|---|---|
| 重写是改库操作 | 动的是用户目录数据 | 重写前自动备份（§6.3），失败即中止 |
| `rename` 期间可能有文件被占用 | 若工作区内有文件被其他程序独占，rename 可能失败 | rename 原子，失败即无变化；给明确提示让用户关掉占用程序 |
| 老配置双写 | 配置里同时存在 `workspaces` 与 `workspaceRoot` | 刻意为之（§7.2），不是冗余 |
| 无单实例锁 | 两个实例指向同一工作区会写冲突 | 既有问题，不在本批范围；已记入遗留 |
| 跨盘体验 | 用户要自己去资源管理器复制 | 用清晰引导文案补偿（§10），并把「一键备份」留作后续 |
